## 0. 一句话结论

**工程与治理是同类里的第一梯队，短板不在「缺功能」，而在四处：**
① **用了才有意义的东西没被用**（89% 的记忆从未被命中、评审前检索共 10 次且全是探针、👍 一次没点过、团队库 7 天零新增）；
② **开箱不可用**（发行包里没有 ES 引导，6 个阻断项让新用户装完连不上库）；
③ **四条已交付能力是坏的或半坏的**：`as_of` 工具层直接报错（H1）、团队库时间字段不对（H2）、
写入准入可被三种形态绕过且只挂在一条写入路上（H5/H6）、面板写配置接口没有管理员门禁（H7）；
④ **质量闸门本身是坏的**：typecheck 红了 3 个版本、CI 不跑测试、7 个集成用例因账号模型变了而永久跳过。
对比市面 30+ 个 DSH 记忆插件，最大的结构性差距是 **9/12 家都做的「每轮自动召回注入」与 5/12 家做的「生命周期自动捕获」** —— 这两条是刻意没做，代价需要正视；
好消息是检索侧唯一带实测的改进（abstain + 查询扩展）已验证能把契约失败 **10→1**。

## 2. 缺陷清单（本次实测发现）

### 🔴 高

**H1 · `memory_search(as_of=…)` 整条功能不可用（已实测复现）**

```
工具调用 memory_search(as_of=2026-10-20, scope=team)
→ Error: tool "memory_search" returned invalid output:
  "value.asOf" is not a declared property (additionalProperties: false)
```

- 根因：代码返回 `asOf`（`src/memory/search.ts:502/593/613`），输出 schema 声明的是 `as_of`（`search.ts:752`）；
- 单测 `tests/memory-search.test.ts:719` 断言的是内部函数 `result.asOf`，**没有任何测试把 `as_of` 走一遍工具层 schema 校验**（receipt 有工具契约测试，as_of 没有）；
- 影响：阶段 13 批 A（v0.5.9）交付的功能自上线起从未成功执行过一次。

**H2 · 即使修了 H1，团队库也会被 `as_of` 全部滤掉（已实测复现）**

```
team_knowledge 上 range(created_at <= 2026-11-02)  → count = 0
team_knowledge 上 range(updated_at  <= 2026-11-02)  → count = 268
team_knowledge 上 range(source_created_at <= 2026-10-20) → count = 228
```

- 团队索引**没有 `created_at` 字段**，用的是 `source_created_at`（个人原条目的创建时间）；
- `src/es/dsl.ts:138` 无条件给两路都加 `range(created_at)`，团队路必然 0 命中 —— **静默丢掉 268 条团队知识**，正好踩中本项目自己定的红线（「静默回落会让时间点回看骗人」）；
- 修法：DSL 按索引参数化时间字段（个人 `created_at` / 团队 `source_created_at`），并给团队库补一条测试。

**同一查询的自然对照**（本次实测，`scope=team`，query「Elasticsearch 索引 ACL 隔离」）：

| 条件 | 结果 | search_log 记录 |
|---|---|---|
| 不带 `as_of` | 3 条命中 | `12:51:08 · note=low_confidence · hits=3 · routes=team:bm25+knn` |
| `as_of=2026-10-20` | **0 条，`no_match`** | `12:51:16 · note=no_match · hits=0 · routes=team:bm25+knn` |

而团队库 `source_created_at<=2026-10-20` 实际有 **228 条** —— 也就是说这 0 命中是字段名造成的，不是时间条件造成的。

**H3 · 团队库 mapping 落后个人库 29 个字段**

个人有、团队缺：`created_at`、`memory_id`、`summary`、`origin`、`forget_reason`、`quarantine_reason`、`privacy`、`distill_state`、`confirmed_use`、`expires_at`、`evidence_ids`、`day`、`mood_*`、`valence`、`arousal`、`anchor`、`promote_state`、`user_id`、`traits_window_days`、`review_note`、`blocked_reason`、`personal_only_reason` …

- 根因：**所有 `scripts/migrate-*-fields.sh` 只处理 `personal_memory_*`**（脚本里写死 `_cat/indices/personal_memory_*`），`team_knowledge` 是 `init-indices.sh:129` 建完再没跟上；
- 后果：`forget_reason` 留痕（阶段 13 批 B）、`origin` 来源戳、`summary` 分级读取、`as_of` 回看 —— **这些治理能力对团队库要么失效要么报错**；
- ⚠️ **2026-11-02 夜更正**：本报告初稿写「一写新字段就是 400」，这句过重了。团队文档由
  `consolidate/distill.ts:toTeamDoc()` 构造，字段集是**固定的旧集合**（doc_id / content /
  memory_type / domain / topic_key / content_sha256 / source_user / source_memory_id /
  source_created_at / promoted_at / status / review_state / updated_at / embedding），
  不会写 summary/origin/forget_reason，所以**没有 400 风险**。真实影响只有一条：
  团队条目没有摘要，`detail=summary` 对团队库省不到 token。补它要同时改 `toTeamDoc` 与 mapping，
  属于新能力，本轮没做。

**H4 · `npm run typecheck` 红了 3 个版本**（见 §1.1），且 CI 不跑它。

**H5 · 写入准入（quarantine）可被绕过 —— 已复核实测，非推测**

```text
node 直调 checkAdmission：
'这台机器密码是 a very secret thing'          => allow:true
'password：ab cd12345678'（全角冒号）          => allow:true
'ELASTIC_PASSWORD=abc def ghi12345'           => allow:true   ← 关键词命中也放行
'pass​word: SecretValue12345678'（零宽字符）    => allow:true
'password: SecretValue12345678'               => 隔离 ✅
```

- 根因：`src/memory/admission.ts:73-76` 的 `ASSIGN_PATTERN` 要求分隔符后**首个 token ≥6 字符且不含空白**，
  所以「值里带空格」「全角冒号」「关键词被零宽字符切开」三种形态全部放行；
- `tests/admission.test.ts:26-37` 的 11 个正例全是「首 token ≥6 的连续串」，所以测不出来；
- 与该模块自陈的目标（「防的是真实发生过的事：明文口令被蒸馏进库」）直接冲突。

**H6 · 准入只挂在 `memory_save` 一条路上，LLM 产物写库全程无闸**

- `checkAdmission` 全仓唯一调用点是 `src/memory/save.ts:425`；
- `src/memory/traits.ts:386,405`、`src/memory/persona.ts:402,418` 把模型生成正文直接写库，
  `evidence_ids` 还存会话原话（`persona.ts:386-394`）；`src/memory/distill.ts:75-107` 改写正文后也不复检；
- 这些条目 `status=pending` 时不进检索，但**审核采纳后即 active**，全程不再过准入 —— 原始事故路径上没有第二道闸。

**H7 · `POST /config` 没有管理员门禁 + `embedding.url` 可写 = 外发面 —— 已复核**

- `panel/index.js` 里 `requireAdmin` 只出现在 1107/2545/2588/2677/2710 五处；
  `handleConfigWrite`（`:2308`）与 `handleStickerAdd`（`:1582`）都没有，只校验 `confirm:true`；
- `EDITABLE` 白名单里有 `['embedding','url']`（`:2154`）、`['index','team']`、`['distill','enabled']`；
  而同一段注释（`:2145-2149`）正是因为「能把凭据导到任意主机」把 `es.url`/`caCertPath` **移出**了可写面 ——
  `embedding.url` 没带凭据，但插件每次 save/search 都会把**查询与记忆正文** POST 到该地址（`src/embedding.ts:77,109-114`），
  属于同一个威胁族的漏网之鱼。
- 修法：`handleConfigWrite` 加 `requireAdmin`；`embedding.url/dims`、`index.team` 移出可写面（或只允许回环）。

**H8 · 7 个集成用例永久 skip，且 skip 文案是错的**

- `tests/helpers/es-env.ts:67-70` 要求 `MEM_WRITER_PASSWORD`/`ELASTIC_PASSWORD`/`MEM_CONSOLIDATOR_PASSWORD` 都非空，
  而单账号迁移后 `deploy/es/.env` 里**没有这些键**（grep 计数 0）→ 返回 null；
- 于是 `tests/es-integration.test.ts:34` 报「未找到 deploy/es/.env」——**文件其实存在**，真实原因是账号模型变了；
- 影响：TLS CA 校验、401 映射、5 个端点读写、save/search/status/review/export/consolidate 的**真实链路一次都没跑过**；
  `HIT_UPDATE_SCRIPT` 的 painless 语法也从未被真实 ES 验证过（`search.ts:214-221` 记载这坑踩过一次）。

## 5. 还缺什么（按优先级，标注是否刻意不做）

### P0 —— 不做就一直「造了没人用」

1. **自动召回注入（或等价的「被动通道」）**：9/12 家有。我们是纯工具驱动，**模型不查 = 没有记忆**；实测检索 10 次全是探针、89% 条目从未命中，说明「靠 prompt 约定模型主动查」这条链没有成立。
   折中方案（符合路线原则）：**小预算 pre-step 注入**（≤5 条 / 单条 ≤500 字 / 超时 5000ms 跳过）+ `memory_search` 工具兜底，并分别统计**被动命中率 / 工具救回率**。
2. **把闸门接进 CI**：typecheck 红 3 版 + CI 不跑测试是同一件事的两面。
3. **修 H1/H2/H3**（as_of 两个 bug + 团队库 mapping 迁移），并补一条「工具层 schema 校验」的契约测试 —— 这类 bug 的根因是**评测只测内部函数，不测工具契约**。

### P1 —— 治理面补齐（我们本来就是这个定位）

### 明确「不跟」的（避免跑偏）

- 不上 Neo4j / 图库；不做 LLM 每轮自动复盘；不照搬 claude-mem 的 SaaS/订阅路线与 MemOS 的重依赖；AGPL 项目只借机制不拷代码；

## 7. 一句话定位

别人做「记忆引擎」，我们做**「可治理的团队记忆基础设施」**——这条定位在 12 家 DSH 竞品里依然成立（没有第二家有 LAN ES 一人一索引 + ACL + 中文 ik + 审计 + 契约评测的组合）；
但定位要成立，前提是**东西真的被用起来**。当前最大的风险不是被竞品比下去，而是**治理设施越造越全、检索却还停在探针阶段**。
