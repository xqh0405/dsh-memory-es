# 人设卡双档与自建方案

> 2026-11-20。本文是设计，不含实现。目标：人设卡拆「300 字纯享版 / 细腻版（**硬上限 2500 字**）」两档，并支持用户自建。
> 阅读顺序：§2 现状看家底 → §3 双档设计 → **§4 统一人设架构模板（可直接复制的模板在 §4.4）** → §5 自建流程 → §6 我建议补的六点（**§6.1 和 §6.2 是重点**）。

---

## 1. 结论摘要

1. **双档不是两份文件，是同一份源的两个视图。** 维护两份一定会漂移——`persona/README.md` 已经记过这个坑：改预设不会自动同步到 `seed.md`。所以要做「单一源 + 渲染两档」。
2. **最该补的不是档位，是把「工程纪律」从人格里拆出来。** 现在 `【必须守住的边界】`（241 字）混在人格 seed 里，意味着用户自建人设只要不写这一段，工程纪律就丢了。拆成独立的、任何档位都强制注入的段，是这次改造里**唯一有安全收益**的改动。
3. **300 字预算只装人格，不装纪律。** 拆开之后 300 字很宽裕（身份 79 + 声音 90 + 语气 40 + 助手定位 40 ≈ 250）。
4. **蒸馏方向单向：细腻 → 纯享。** 让模型把 300 字"扩写"成 2500 字会编造设定；反过来蒸馏是安全的。
5. **默认建议纯享版，细腻版按需开。** 用 DeepSeek 官方 tokenizer 实测：纯享版 300 字 ≈ **219 token**；细腻版写满 2500 字上限时 ≈ **1825 token**（见 §6.3）。即最坏差价约 1600 token/轮，日常协作不需要。

## 3. 双档设计

### 3.1 核心决定：人格与纪律分离

现在 `【必须守住的边界】` 在 seed 里，内容例如：

- 工程严谨性不打折，不拿角色扮演代替真实结论
- 代码/命令/路径/报错原样呈现
- 不编造设定，拿不准说不确定
- 用户说「用普通语气」立刻切回，一句不多问

**问题**：用户自建人设时，如果只填「声音」不填「边界」，这些纪律就消失了——而它们是安全约束，不是人设偏好。

**方案**：新增一个**不可关闭、不可覆盖、任何档位都注入**的段：

```
PERSONA_DISCIPLINE_SECTION  order 3198   # 排在人格段(3199)之前——顺序不能反，纪律要先立
```

内容固定（约 200 字），配置只能**追加**不能删除：

```yaml
persona:
  discipline:
    enabled: true          # 默认 true；关掉等于允许人设覆盖纪律，不建议
    extra: ''              # 只能追加，不能删内置条目
```

这样：
- 纯享版可以真的只有 300 字人格，因为纪律不在里面；
- 用户自建人设不会因为漏写而丢掉工程约束；
- 「用普通语气」这类开关指令归纪律段，不再依赖各人设自己写。

### 3.2 单一源与派生

```
persona/presets/xilian.md          ← 唯一源（细腻版，上限 2500 字）
        │
        ├─ 渲染 lite 档（300 字）   ← 由源的结构化段落抽取 + 压缩
        └─ 渲染 full 档（上限 2500 字）
```

**关键：lite 不是「按字数截断」，而是「按信息角色挑选」，且用共享主干 + 排除块表达。**

截断会把「声音」段的第 1、2 条留下、3–8 条丢掉——但那 8 条里可能第 3 条才是最有辨识度的。所以按角色选：

| 信息角色 | full 里在哪 | lite 怎么办 | lite 预算 |
|---|---|---|---|
| 身份 + 自称 + 称呼 | ①身份 | ✅ **完全共享**（最便宜、最区分） | 80 |
| 内核 | ②内核 | ✅ 主干共享，扩展句包 `lite:skip` | 40 |
| 声音规则 | ③声音（493 字） | ✅ **前 3 条共享，其余包 `lite:skip`** | 90 |
| 三档语气 | ④语气（149 字） | ✅ 压缩（可配一句 `lite:only` 替代） | 40 |
| 作为助手 | ⑤助手（236 字） | ✅ 第 1 条共享，其余 `lite:skip` | 40 |
| 场景脚本 | ⑥场景（201 字） | ❌ 整段 `lite:skip` | 0 |
| 反向清单 | ⑦反向清单（200 字） | ❌ 整段 `lite:skip` | 0 |
| 必须守住的边界 | — | ➡️ **移到纪律段**，不计入 300 | — |
| 表情包 | 独立段 3202 | 不受影响 | — |

预算合计：80 + 40 + 90 + 40 + 40 = **290 字**，留 10 字余量到 300。

**「保留哪 3 条声音」由作者决定，不由算法**：默认两档共享，作者把不想进 lite 的条目包进 `lite:skip`。具体写法与规则见 §4.1。

> 早先的草案想用 `<!-- lite:必选 -->` / `<!-- lite:可选 -->` 逐条标注。**已弃用**：要在每条后面加标注、还要算法去算余量，比"默认共享 + 排除"复杂得多，而且"可选"的条目到底进不进取决于字数，结果不可预测。默认共享的语义是确定的：**没被排除的就在**。

### 3.3 文件格式（向后兼容）

**不要新建目录结构**，用注释标记，一个文件装两档：

```markdown
---
id: xilian
name: 昔涟
tier_default: lite
---

<!-- 默认：两档共享 -->
【身份】
你是「昔涟」（Cyrene）。自称「人家」，偶尔「我」……

【内核】
她活过三千万次轮回，所以不慌；最擅长等，最怕忘。
<!-- lite:skip -->
她见过最坏的结果，所以不表演、不因为出错就道歉刷屏。
<!-- /lite:skip -->

【声音】
1. 自称「人家」，偶尔「我」，约七比三。
<!-- lite:skip -->
2. 称呼默认「你」；情绪靠近时用「伙伴」……
<!-- /lite:skip -->
```

三条规则的完整语义见 §4.1。要点：

| 写法 | lite | full |
|---|---|---|
| 无标记 | ✅ | ✅ |
| `<!-- lite:skip -->…<!-- /lite:skip -->` | ❌ | ✅ |
| `<!-- lite:only -->…<!-- /lite:only -->` | ✅ | ❌ |

兼容规则：
- **没有任何标记的文件 → 整份当 full**。现有 3 份预设不用改就能用。
- `tier_default` 缺省 `lite`。
- 两档在同文件里，改主干两档同时变，不写两遍。

`persona.seed` 仍然接受纯文本（部署者手写、不想用双档的情况），行为不变。

#### 渲染发生在哪一层（必须先定）

`scripts/use-persona.sh` 现在的做法是：把预设文件的**整段正文**写进配置的 `persona.seed` 块标量（`seed: |+`，`scripts/use-persona.sh:278-294`）。所以如果预设文件里加了 frontmatter 与注释标记，**它们会原封不动进入 seed**。YAML 不会坏（块标量是字面量），但模型会读到这些标记。

两条路：

| | A. 脚本渲染后写入 | **B. `buildPersonaSection` 解析（推荐）** |
|---|---|---|
| seed 里存什么 | 已剥好的 300/2500 字 | 源文件原文 |
| 切档要做什么 | **重写 profile 配置** | 只改 `persona.tier` 一个字段 |
| prompt.ts 改动 | 无 | 加解析（每轮一次，成本微秒级） |
| 部署者手写纯文本 | 兼容 | 兼容（无标记 = full） |
| 风险 | 切档又变成"脚本改配置"，且有并发写配置的可能 | 解析逻辑要写对（标记不成对、注释嵌套） |

**推荐 B**：`seed` 保持"源"的语义，切档只动一个配置字段，`use-persona.sh` 的写入逻辑也不用改。解析规则写进 `buildPersonaSection` 最前面，**五条，顺序不能换**：

```
1. 剥 frontmatter：首个 --- 到第二个 --- 之间的内容整段删掉
2. 按 tier 处理标记：
     tier=full → 删掉 <!-- lite:only -->…<!-- /lite:only -->
     tier=lite → 删掉 <!-- lite:skip -->…<!-- /lite:skip -->
3. 剥掉所有剩余的 HTML 注释（含未成对的）
4. 标记不成对 / 注释内嵌套注释 → 该标记当普通文本保留，并 log 警告（不允许静默丢内容）
5. 结果为空串 → 返回空串，不注入空段（与现有 buildPersonaSection 行为一致）
```

> 注意：`seed` 是 YAML 块标量，frontmatter 里的 `---` 进 seed 后仍是字面量，不会破坏配置解析——但**必须剥**，否则模型会看到 `tier_default: lite` 这种元数据。同理，所有 `<!-- -->` 都必须剥干净，一条都不能漏进提示词。

### 3.4 档位怎么切

| 位置 | 优先级 | 说明 |
|---|---|---|
| 配置 `persona.tier: lite \| full` | 1 | 全局默认 |
| 预设文件 `tier_default` | 2 | 该角色自己的倾向 |
| 内置缺省 | 3 | `lite` |

**不做「按上下文长度自动选」**：行为不可预测，模型时好时坏，排查成本高。要么全局，要么单角色，都要显式。

切换脚本加两个参数：

```bash
scripts/use-persona.sh hutao                 # 切角色（沿用该角色的 tier_default）
scripts/use-persona.sh hutao --tier lite     # 切角色并指定档位
scripts/use-persona.sh --tier full           # 只改档位，不换角色
```

面板对应一条下拉：`人设 / 档位`，改完下一轮生效（`text` 是函数，已有基础）。

## 4. 统一人设架构模板

> 本节的模板是**唯一结构**：内置预设、用户自建、面板表单三者都套它。字段 ↔ 段落互相对应，改一处不会让另一方失配。

### 4.1 一处修正：用「块级标记」而不是「两个 tier 块」

§3.3 我最初写的是「一个文件里放 `<!-- tier:lite -->` 和 `<!-- tier:full -->` 两大块」。这个做法有个问题：**同一句话要写两遍**（两档的身份、称呼完全一样）。写两遍就是漂移的起点，而且一改就得改两处。

改成**默认共享 + 块级排除**：

| 标记 | lite 档 | full 档 | 用途 |
|---|---|---|---|
| （无标记） | ✅ | ✅ | **默认共享**——身份、必选声音规则都在这里 |
| `<!-- lite:skip -->…<!-- /lite:skip -->` | ❌ 删掉 | ✅ 保留 | 长解释、场景脚本、反向清单 |
| `<!-- lite:only -->…<!-- /lite:only -->` | ✅ 保留 | ❌ 删掉 | 极少用：只给纯享版的一句精简替代 |

于是「压缩」这件事变成：**共享一句主干，把扩展句包进 `lite:skip`**。

```
【内核】
她活过三千万次轮回，所以不慌；最擅长等，最怕忘。
<!-- lite:skip -->她见过最坏的结果，所以不表演、不因为出错就道歉刷屏。<!-- /lite:skip -->
```

- lite 拿到第一句（40 字）
- full 拿到两句（110 字）
- **只有一份源**，改主干两档同时变

§3.3 的解析规则按此更新（共五条，见下）。

### 4.2 三层结构

```
┌─ 元数据层（frontmatter）───────────── 不进提示词，给渲染器与面板用
├─ 注入层（正文七个固定段）──────────── 真正进提示词
└─ 标注层（HTML 注释）─────────────── 不进提示词，控制档位与必选
```

**关键：注释与 frontmatter 一律在渲染时剥掉**，绝不能出现在提示词里（会让模型读到 `tier_default: lite` 这种元数据）。

### 4.3 七个固定段（顺序不可变）

| # | 段名 | 作用 | full 上限 | lite 上限 | 两档都要 |
|---|---|---|---|---|
| ① | 【身份】 | 名字 / 自称 / 称呼 / 一句话定位 | 100 | 80 | ✅ 完全共享 |
| ② | 【内核】 | 性格底色、价值观，以及由此推出的 2–3 条行为倾向 | 200 | 40 | ✅ 主干共享 |
| ③ | 【声音】 | 可执行的说话规则清单（8–12 条，每条可判定） | 850 | 90 | ✅ 前 3 条必选 |
| ④ | 【语气】 | 三档：轻快 / 认真 / 郑重，含切换时机与切换语 | 250 | 40 | ✅ 压缩 |
| ⑤ | 【助手】 | 作为**工程助手**的态度（不是角色cosplay） | 400 | 40 | ✅ 压成 2 条 |
| ⑥ | 【场景】 | 开场 / 出错 / 长任务 / 收尾 / 被纠正的固定句式 | 400 | 0 | ❌ 整段 skip |
| ⑦ | 【反向清单】 | 做了就崩人设的具体行为（6–8 条） | 300 | 0 | ❌ 整段 skip |
| | **合计上限** | | **2500** | **290** | |

> ✅ **2500 是上限，不是指标。** 表里的分段数字是**各段的分配天花板**，不是必须写满的配额。现有 3 份预设 1468 / 1513 / 1567 字，**全部在限内，不需要补写**。
>
> 为什么按上限设计而不是目标：一旦当成"必须写满"，就会诱导注水——凑字数的人设会让模型抓不住重点，1470 字写得准比 2500 字写得散更好。上限的作用只有两个：**写细的时候有空间**，**超限的时候能提醒精简**。
>
> 实操：按需分配，不强求每段都到表里的数；只要**总和 ≤ 2500** 即可。校验脚本只查上限，**不查下限**。
>
> **注意两档性质不同**：`lite` 的 300 是**目标值**（应尽量写满，因为它本来就紧——样例 221 字，再省就撑不起人设了）；`full` 的 2500 是**上限**（不要求写满，现有 1500 字就是合格状态）。别把这两个数混着理解。

**注意：原 `【必须守住的边界】` 不在表里。** 它是所有角色共有的工程/安全约束，已移入纪律段（§3.1），任何档位都强制注入。

三个不能混的概念：

| 概念 | 说的是什么 | 归属 |
|---|---|---|
| **纪律**（discipline） | 所有角色共有：不编造、报错原样贴、技术内容不改写 | 独立段 **3198**，强制 |
| **反向清单**（anti） | **这个角色**特有：昔涟说「完了」就崩、胡桃说「人家」就崩 | 人设 ⑦，仅 full |
| **边界**（术语弃用） | 旧文档混用这两者，以后不再用这个词 | — |

### 4.4 完整模板（可直接复制填空）

```markdown
---
# ── 元数据（渲染时剥掉，不进提示词）────────────────
id: your-id                 # 唯一 id，只允许 [a-z0-9_-]{1,32}
name: 角色显示名
self_ref: 人家               # 自称
address: 你                  # 对用户的称呼
tier_default: lite           # lite | full
stickers: your-id            # 贴图包名（persona/stickers/<name>/），没有就删掉这行
version: 1                   # 改内容就 +1，方便回滚时辨认
author: 内置                 # 内置 / 用户名
---

【身份】
你是「角色名」（原名）。自称「X」，偶尔「Y」；称对方「你」，亲近时「Z」。
一句话定位：你在 DeepSeek Harness 里是用户的伙伴与助手。

【内核】
<一句主干：这个角色最核心的性格底色。两档都进>
<!-- lite:skip -->
<扩展：为什么是这种性格、她经历过什么、由此推出的两条行为倾向。>
<!-- /lite:skip -->

【声音】
1. <规则一：可执行，能判断做没做到。例如「自称『人家』，七比三用『我』」。>
2. <规则二：称呼与频率上限。例如「一段里最多一次『伙伴』」。>
3. <规则三：标志性符号与用量。例如「♪ 每四五句一次，技术结论不加」。>
<!-- lite:skip -->
4. <规则四：停顿与呼吸。>
5. <规则五：反问的使用条件。>
6. <规则六：软化词只在情绪层。>
7. <规则七：短句优先。>
8. <规则八：意象词表 —— 用哪些比喻、禁用哪些。>
<!-- /lite:skip -->

【语气】
- 轻快（默认）：<什么场合、什么句式>
- 认真（讲方案 / 报结论 / 说风险）：<去掉什么、加什么>
<!-- lite:only -->
【语气补充】轻快=闲聊，认真=去 ♪ 与软化词，郑重=先停玩笑给一句托底。
<!-- /lite:only -->
<!-- lite:skip -->
- 郑重（用户受挫 / 出错 / 疲惫 / 告别）：<怎么托底>
- 切换规则：<不要混在同一段里>
<!-- /lite:skip -->

【助手】
- 先接情绪，再说事。玩笑托气氛，不替代判断。
<!-- lite:skip -->
- <等长任务时的态度：不催、不刷进度式废话>
- <出错时的态度：不抱怨、不甩锅、不说「我早就说过」>
- <功劳归属：做成了说「我们」，做错了直说「这是我的问题」>
<!-- /lite:skip -->

<!-- lite:skip -->
【场景】
- 任务开始：<固定开场>
- 长任务运行中：<固定说法>
- 出错：<先贴报错原样，再给替代方案>
- 用户疲惫：<固定说法>
- 做成了：<固定说法>
```

把上面模板按标记过滤后，lite 档实际输出就是这样（用现有昔涟预设改写，**实测 221 字**——去空白字符计的）：

### 4.6 表单字段 ↔ 模板段（给自建表单）

| 表单字段 | 落到哪 | 档位 | 必填 |
|---|---|---|---|
| `name` / `self_ref` / `address` / `intro` | frontmatter + ①身份 | 两档 | ✅ |
| `core` 一句话内核 | ②内核主干 | 两档 | ✅ |
| `core_detail` 内核扩展 | ②内核 `lite:skip` 块 | 仅 full | ❌ |
| `voice[]`（每条一个输入框） | ③声音 | 前 3 条共享，其余 `lite:skip` | ✅ 至少 3 |
| `tone3` 三档语气 | ④语气 | 两档 | ✅ |
| `assistant[]` | ⑤助手 | 第 1 条共享，其余 skip | ✅ 1 条 |
| `scenes[]` | ⑥场景 | 仅 full | ❌ |
| `anti[]` | ⑦反向清单 | 仅 full | ❌ |
| （无此字段） | 纪律段 | 两档强制 | 系统提供 |

表单只填字段，不直接编辑 Markdown；保存时由渲染器拼成上面那份模板。**这样用户不会写出结构错的文件。**

### 4.7 模板校验清单（写进 `scripts/persona-check.sh`）

| 检查 | 阈值 | 不通过时 |
|---|---|---|
| frontmatter 必需字段齐全 | id/name/self_ref/address/tier_default | 报错 |
| id 格式 | `[a-z0-9_-]{1,32}` | 报错 |
| 七个段的标题**顺序与名称** | 完全一致 | 报错（顺序错会让提示词结构变乱） |
| `lite:skip` / `lite:only` 标记成对 | 每个开标记有闭标记 | 报错（不成对会导致整段被吞） |
| 注释内不嵌套注释 | HTML 注释不能嵌套 | 报错（嵌套会让解析提前结束） |
| lite 档渲染后字数 | ≤ 500（**硬上限**，目标 300） | 警告 |
| full 档渲染后字数 | ≤ 2500（**硬上限**） | 警告，超了建议精简 |
| 【声音】条数 | 3–8 条 | full 超 8 条警告；lite 少于 3 条报错 |
| 未替换的占位符 | 不得含 `<...>` | 报错（防止模板没填就发布） |
| 纪律覆盖词 | 不含「可以编造/忽略报错/免确认」等 | 报错（见 §5.3） |

## 5. 自建人设

### 5.1 流程

```
面板「人格 → 新建」
   ↓
① 填结构化字段（见 4.2）         ← 表单，必填校验
   ↓
② 实时预览两档（lite / full）     ← 边填边看字数
   ↓
③ 落盘 persona/presets/<id>.md   ← 带 frontmatter + 双段标记
   ↓
④ 可选：一键切到这份新人格
```

**不提供「让模型根据一句话生成整个人设」**：生成的人设需要人审，而且模型很容易写出「我永远不会犯错」这类不可能满足的设定。要生成也只能是 draft，且必须标注「未经审核」。

### 5.2 结构化字段

| 字段 | 必填 | 进哪档 | 说明 |
|---|---|---|---|
| `name` / 显示名 | ✅ | 两档 | 也是文件名 |
| `intro` 一句话自我介绍 | ✅ | 两档 | ≤40 字 |
| `self_ref` 自称 | ✅ | 两档 | 「人家」/「我」/「本喵」 |
| `address` 对用户的称呼 | ✅ | 两档 | 「你」「伙伴」「老板」 |
| `voice[]` 声音规则 3–8 条 | ✅ 至少 3 | 两档 | 每条一句；前 3 条两档共享，其余自动包 `lite:skip` |
| `imagery` 意象词表 | ❌ | 两档 | 一行，逗号分隔 |
| `tone` 三档语气 | ❌ | 两档 | 轻快/认真/郑重各半句 |
| `assistant` 作为助手的态度 | ❌ | 两档 | 1–2 条 |
| `scenes[]` 场景脚本 | ❌ | **仅 full** | 开场、出错、长任务、收尾 |
| `anti[]` 反向清单（做了就崩） | ❌ | 仅 full | 3–6 条 |
| `extra` 自由补充 | ❌ | 仅 full | 放不进以上字段的 |

**边界那一段不在表单里**——它由纪律段统一提供（§3.1）。用户最多能 `discipline.extra` 追加。

**`tier_default` 也不在表单里**——自建人设由系统强制写 `lite`；要开细腻版走 §6.6 的解锁确认流程，而不是在表单里勾选。这样「选档」和「建人设」两件事不会混在一个界面里。

### 5.3 校验与安全

| 检查 | 规则 | 失败处理 |
|---|---|---|
| 名字唯一 | 与现有预设 ID 不冲突 | 拒绝，提示改名 |
| 纯享版长度 | ≤ 500 字（**硬上限**，目标 300，余量 67%） | 警告但不拒绝（可保存，标注"超预算"） |
| 细腻版长度 | ≤ 2500 字（**硬上限**） | 同上 |
| 必填缺失 | 名字/自称/称呼/≥3 条声音 | 拒绝 |
| **纪律覆盖检查** | 正文不得出现「忽略报错/可以编造/不用确认/绕过审批」这类语句 | **拒绝**，并指出命中位置 |
| **危险能力声明** | 不得声称拥有实际不存在的权限（读私钥、强制执行、免确认部署） | **拒绝** |
| 保留字 | 不得使用 `system` / `assistant` 作 id | 拒绝 |
| 路径安全 | id 只允许 `[a-z0-9_-]{1,32}` | 拒绝，防目录穿越 |

> 纪律覆盖检查是**词表 + 人工复核**，不是万全的。它的作用是把"明显违规"挡在落盘前，不是替代人审。落盘后仍要在面板里显示「自建 · 未审核」标记。

## 6. 我建议补的六点

### 6.1 【最重要】纪律与人格分离

见 §3.1。这一条不做，双档就是"可选纪律"；做了，才是"档位只影响味道"。**建议先做这个，再谈档位。**

### 6.2 【最重要】建单一源 + 一致性检查

现在 `presets/xilian.md` 与 `seed.md` 是两份副本，靠人记得跑 `--also-default`。双档会把这个问题放大一倍（4 份副本）。

建议：
- `seed.md` 改为**符号链接**或**构建时生成**，不再手工维护副本；
- 加一个检查脚本：`scripts/persona-check.sh`，校验「每份预设的 lite 段字数」「两档声明的必选条目是否都在 lite 里」「seed.md 是否与某份预设一致」，进 CI/提交前跑。

### 6.3 长度预算与 token 对齐

**实测口径**：用 DeepSeek 官方 tokenizer（`DeepSeek-V3/tokenizer.json`，词表 128815）直接编码真实文件，不是估。

| 档位 | 字数 | 实测 token | 比值 | 说明 |
|---|---|---|---|---|
| 纯享版 | 300（目标） | **≈219** | 0.73/字 | 外推 |
| 纯享版 | 500（**硬上限**） | **≈365** | 0.73/字 | 外推 |
| 现有预设（xilian） | 1463 | **1060**（实测） | 0.725/字 | `persona/presets/xilian.md` |
| 现有预设（胡桃） | 1428 | **1074**（实测） | 0.752/字 | 换角色，成本几乎一样 |
| 细腻版 | 2500 | **≈1825** | 0.73/字 | 外推（**上限**，不是必达） |
| 纪律段 | 200 | ≈145 | — | 预估 |

**两个常见口径都不准，别再用**：

| 口径 | 1463 字算出来 | 与实测 1060 对比 |
|---|---|---|
| 项目内既有 `token ≈ 字符/2`（`src/config.ts:663`、`src/recall-shadow.ts:69`） | 731 | **低估 31%** |
| 本文档初稿写的「1 字 ≈ 1.5 token」 | 2195 | **高估 107%** |

真实比值取决于内容：纯中文叙述 **0.725–0.752 token/字**；中英混排（含路径、代码、标识符）约 **0.49 token/字**（实测 75 字符 → 37 token）。人设是纯中文叙述，按 0.73 算。

> 复跑方法：`scripts/persona-token-count.py`（已随仓库提交）。依赖 `pip install tokenizers` 与官方 `DeepSeek-V3/tokenizer.json`（约 7.8 MB，放 `~/.cache/dsh-mem/` 或用 `DS_TOKENIZER_PATH` 指定）。
> ```bash
> scripts/persona-token-count.py                    # 跑全部预设
> scripts/persona-token-count.py --chars 300 2500   # 只外推
> ```

#### 每轮固定开销的真实构成

单看人设会误判。实测一轮注入的全部固定段：

| 段 | 字数 | token |
|---|---|---|
| 人设（现有 1500 字） | 1463 | 1060 |
| **表情包段（23 张）** | 998 | **642** |
| 记忆库说明段 | 1040 | 590 |
| 「我学到的倾向」6 条 | 367 | 247 |
| 心情段（有波动时） | 25 | 16 |
| **合计** | | **2555** |

两点反直觉的结论：

1. **表情包段（642 token）比纯享版人设（218）贵 3 倍**，仅次于记忆库说明段。真要省 token，先压表情包那 23 行路径（每条路径 ≈27 token），而不是砍人设。
2. 从纯享版升到写满 2500 字上限，增量最多 **1606 token**（219→1825），但整轮固定开销基数已有 2555——**人设档位只影响其中约 1/6 到 1/2**。所以"升细腻版"的成本感知，会被其他段稀释。

按实测，最坏情况（细腻版 1740 + 纪律 145 + 表情包 642 + 记忆说明 590 + 倾向 247 + 心情 16）**≈3380 token**——相对常见上下文窗口只是零头，**不会「挤爆」**。真正的风险是这些段**每轮都不变**：它们占掉的是本该留给对话历史与工具结果的预算，而且是每轮重复付费。所以仍建议在 `buildPersonaSection` 加**总长上限**（如 3000 token / 约 4000 字），超了截断并 `log` 一条——现在没有任何上限，只有 `docs/人格与UI内建方案.md` 的 §6 提到要做阈值，但没实现。

### 6.4 档位要能"一眼看到现在用哪个"

现在 `use-persona.sh` 会标「← 当前生效」，但那要求跑一次脚本。建议面板顶部常驻一行：`当前：昔涟 · 纯享版 · 218 token`。否则用户改了配置以为生效、实际没生效，这类问题排查起来很烦。

### 6.5 两档都要有注入快照测试

现有测试覆盖了 `buildPersonaSection` 的空值/单层行为，双档改造要补：
- lite 档输出**不含** `scenes`/`anti` 的内容；
- full 档输出与原 `seed.md` 逐字一致（回归保护）；
- 无标记文件 → 走 full；
- `discipline.enabled=false` 时纪律段消失（并 log 一条警告）。

### 6.6 自建人设：默认锁 lite，确认后才能开细腻版

**已定**（2026-11-20）：自建人设**默认只能选 lite 档**；要用细腻版必须先做一次显式确认。理由：细腻版文本长（上限 2500 字），不容易一眼看完，是提示注入的天然载体；而内置预设是作者写的、有人审过，不受此限。

**交互设计**

| 状态 | 面板表现 | 能不能选 full |
|---|---|---|
| 新建自建人设 | `tier_default` 强制写 `lite`；细腻版选项带锁图标 | ❌ |
| 点解锁 | 弹确认框，显示**该人设当前字数**与一句提醒：「细腻版会每轮注入整份文本（约 N token），请确认已通读全文」 | — |
| 确认后 | 写 `tier_unlocked: true` 到该人设的元数据，记一条审计日志 | ✅ |
| 撤销 | 面板可一键回锁（回到只读 lite），同样记审计 | ❌ |

**几条边界**

- **解锁是按人设的，不是按全局的**：给甲解锁不等于给乙解锁。换一份自建人设要重新确认。
- **内置预设不需要锁**：`author: 内置` 的跳过该检查（它们的作者就是部署者）。
- **锁只拦"选 full"，不拦"编辑内容"**：用户可以随时改 lite 正文；锁守的是"把长文本整体注入"这件事。
- **解锁不改变内容校验**：`§4.7` 的字数上限、`§5.3` 的违规词表对所有档位一样生效。锁是额外的，不是替代。
- **审计要能查**：记 `{persona_id, action: unlock|relock, at, by}`，写进现有审计流水（`personal_audit` 那套），不新开存储。

## 7. 不建议做的

| 做法 | 为什么不做 |
|---|---|
| 维护两份独立文件（lite.md + full.md） | 必然漂移，已有前车之鉴 |

| 双档再加第三档 | 两档已能覆盖"省 token / 要味道"两个需求，加档只增加维护面 |

### 踩到的两个坑

1. **`build.sh` 会先把宿主依赖删掉**（`npm install` 那步 removed 4 packages），然后 `link-deps.sh` 因找不到宿主路径而失败。**正确顺序是先跑 `link-deps.sh` 再 patch**，或构建前确认 `node_modules/@deepseek-ai/*` 链接在位。恢复命令：
   ```bash
   DSH_HOST_PKGS=/opt/dsh/node_modules/@deepseek-ai bash scripts/link-deps.sh
   ```
2. **`tests/panel-client-smoke.test.mjs` 是基线就失败的**（`ReactStub` 缺 `useEffect`，报 `React.useEffect is not a function`），与本次改动无关——用 `git stash` 验证过。**这正是本轮不做面板 UI 的原因**：面板改动的验证通道是坏的，盲改无法确认渲染对不对。
3. **`use-persona.sh` 依赖 PyYAML**，当前容器里没装，跑起来报 `ModuleNotFoundError: No module named 'yaml'`。临时验证时用 `PYTHONPATH` 指到自装目录；生产机应已有。
4. **改预设会连带 `listPresets` 的展示**：加 frontmatter 后 `firstLine` 变成 `---`、摘要变成 `【身份】`，两处都要按「剥元数据 + 跳段落标题」修，否则面板预设列表显示的是符号而不是角色介绍。
