# 开源 AI 记忆项目调研（面向 dsh-memory-es）

> 调研时间：2026-10-29 · 目的：找出能直接迁移到本插件的机制，而不是「再抄一个记忆库」。
> 每条机制都标注了来源（论文/README），未核实的传言不进本文。

## 0. 一句话结论

主流开源记忆系统在**存储与检索**上和我们已经很接近（向量 + BM25 + 融合），真正的差距在**写入之后的维护**：
「旧结论怎么失效」「权重怎么随时间与使用变化」「一条命中怎么扩散到相关条目」。

这三件事，正好是当前 `dsh-memory-es` 的三处空白：

| 能力 | 我们的现状 | 主流做法 |
|---|---|---|
| 冲突消解 | `content_sha256` 精确去重 + 相似度阈值 + 极性词对规则 + 人工 pending | LLM 判定 ADD/UPDATE/DELETE/NOOP；事实标有效区间、失效不物理删 |
| 权重 | `PERSONAL_WEIGHT=1.2` 硬编码；BM25 字段权重硬编码；检索不回写 | 访问次数 + 交互量 + 时间衰减构成的「热度」；艾宾浩斯遗忘曲线 |
| 召回扩展 | BM25 + kNN 两路 RRF，到顶 | 图相邻（PPR / BFS）、社区摘要、层次摘要树 |

## 1. Mem0：写入时的四操作模型

**来源**：arXiv 2504.19413（Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory）

流水线分两段：**提取（extraction）** 与 **更新（update）**。更新阶段把新提取的事实与相似的历史记忆一起交给模型，由模型通过 tool call 选择一种操作：

- `ADD` —— 新事实，生成唯一 id 入库
- `UPDATE` —— 与旧条目语义重合但信息更丰富，就地改写
- `DELETE` —— 找到被新事实**矛盾**的旧条目并删除
- `NOOP` —— 已有等价信息，什么都不做

论文附录的 Algorithm 1 就是这个循环。工程上的价值不在「用 LLM」，而在**把写入当成分类问题而不是插入**。

**对本项目的意义**：我们的 `consolidate/dedupe.ts` 只回答「新条 / 重复 / 待人工」三态，从不改写旧条；`conflict.ts` 只认极性词对（「必须 vs 禁止」），换说法的矛盾一律漏。Mem0 的 DELETE 分支正是补这一块的形状，但**它删除、我们不能删**（团队库要审计），应改成 `superseded_by` 指针。

**注意**：Mem0 是 Python + 向量库，整体替换不现实；它的 LLM 抽取对着 CPU Ollama 跑成本过高。只取「四操作」这个语义。

## 2. Zep / Graphiti：双时态 + 失效不删 + 三路召回

**来源**：arXiv 2501.13956（Zep: A Temporal Knowledge Graph Architecture for Agent Memory）

两个机制值得单独拎出来：

### 2.1 双时态（bi-temporal）

每条事实带四个时间戳，分属两条时间线：

- `t_valid` / `t_invalid` —— 事实在**现实世界**里成立与失效的时刻
- `t_created` / `t_expired` —— 事实在**系统里**被写入与作废的时刻

被推翻的关系不删除，只置 `invalid_at`。这样「去年这个结论是对的」与「现在它错了」可以同时被表达和检索。

**对本项目的意义**：这正是「已被推翻的旧结论还留在 ES 里被检索出来」这个痛点的正解。我们现在只有 `status=superseded/rejected` 这种**状态位**，没有**时间区间**——所以答不了「当时确实是这样」这类时间问题，也没法做「按时间点回溯」。

### 2.2 三路检索 + 重排

`cosine 语义` + `Okapi BM25 全文` + `BFS 图广度优先`（沿事实-实体边走），三路候选交给 reranker。reranker 支持 RRF、MMR（多样性）以及**episode-mentions 重排**——按某实体/事实在对话里被提及的次数加权，即「经常被引用的信息更有用」。

**对本项目的意义**：我们只用了 RRF 的前两路。第三路（图/关系扩散）缺失，而 episode-mentions 那种「提及频次」权重其实就是**访问反馈**的静态替身——用 ES 的 `rank_feature` 或一个计数列就能近似，不需要图库。

## 3. A-MEM：链接与记忆演化

**来源**：arXiv 2502.12110（A-MEM: Agentic Memory for LLM Agents，NeurIPS 2025）

按 Zettelkasten 卡片盒方法组织记忆：

1. **Note construction**：每条记忆生成结构化属性——上下文描述（context）、关键词（keywords）、标签（tags）
2. **Link generation**：新条目与历史记忆比对，相似则建立链接，形成网络
3. **Memory evolution**：新条目的写入会**反向更新**旧条目的 context 与属性——记忆网络随新增不断自我精炼

**对本项目的意义**：
- `summary` / `semantic_keywords` 字段我们已有（BM25 里就是 `summary^1.5`、`semantic_keywords^1.5`），说明这条路我们走对了；缺的是**链接**。
- 「演化」这一步有争议：让新记忆改写旧记忆的表述，等于把历史证据改写掉，审计上很危险。建议只取「链接」，不取「反向改写」。

## 4. MemoryOS：分层存储 + 热度淘汰

**来源**：arXiv 2506.06326（Memory OS of AI Agent，腾讯 AI Lab + 北邮）

借鉴操作系统内存管理，三层存储 + 热度公式。**这是本次调研里公式最完整、最容易照搬的一个**：

```
Heat = α·N_visit + β·L_interaction + γ·R_recency
R_recency = exp(-Δt / μ)
```

- `N_visit`：该段落被检索命中的次数
- `L_interaction`：该段落包含的对话轮数（信息量/参与度）
- `R_recency`：距上次命中的时间衰减，`Δt` 以秒计，论文实现取 `μ = 1e7`（约 116 天）
- 段落容量超限时淘汰 `Heat` 最低者；`Heat` 超过阈值（论文取 5）晋升到长期个人记忆
- **检索命中后立即回写 `N_visit` 与 `R_recency`** —— 检索行为反馈到权重

**对本项目的意义**：我们完全没有这一层。`PERSONAL_WEIGHT` 是常数，`updated_at` 只用于显示不参与打分。而「被反复检索到的记忆应当更容易被检索到」是记忆系统里最有效的正反馈，且实现成本极低。

**注意 μ=1e7 是论文的实现选择**，不是普适常数；我们的记忆更新频率比对话低得多，时间常数应当重新标定（比如 30~60 天）。

## 5. MemoryBank：艾宾浩斯遗忘曲线

**来源**：arXiv 2305.10250（MemoryBank: Enhancing Large Language Models with Long-Term Memory）

按艾宾浩斯遗忘曲线更新记忆强度：**随时间遗忘、按重要性（significance）与复述强化**。回忆（retrieval）本身即强化。

**对本项目的意义**：与 MemoryOS 的 `R_recency` 是同一个思想的两个版本。MemoryBank 的额外价值是「**遗忘不等于删除**」——强度低到阈值以下时降级而不是消失，这与我们 `status=superseded` 的做法天然契合。

## 6. MemGPT / Letta：把上下文当内存来调页

**来源**：arXiv 2310.08560（MemGPT: Towards LLMs as Operating Systems）

虚拟上下文管理：分层内存（主上下文 / 外部上下文），模型通过工具调用**自己决定**在层间搬什么、何时中断。这是「agent 自管理记忆」的源头。

**对本项目的意义**：我们是宿主侧插件，模型通过 `memory_save`/`memory_search` 显式读写，本质上已经是 MemGPT 的轻量版。**不建议照搬**——自管理分页需要模型有稳定的工具调用纪律，且每次搬页都是 token。

## 7. 三类「召回扩展」

| 项目 | 机制 | 一句话 |
|---|---|---|
| HippoRAG（arXiv 2405.14831） | 知识图 + Personalized PageRank | 用图的随机游走模拟海马体索引，multi-hop 命中率显著提升，且比迭代检索便宜 10~30 倍 |
| GraphRAG（arXiv 2404.16130） | 实体图 + 社区摘要 + map-reduce | 解决「针对整个语料的全局问题」，社区摘要先行生成局部答案再汇总 |
| RAPTOR（arXiv 2401.18059） | 递归聚类 + 摘要建树 | 自底向上建多层抽象，检索时跨层命中，长文档的多步推理提升明显 |

**对本项目的意义**：
- HippoRAG 的 PPR 在 ES 里做不了（没有图引擎），但**二跳扩展**可用 `links` 字段在应用层实现；成本远低于引图库。
- RAPTOR 对 `doc_search` 是**直接可用**的：现在 chunk 只做等权累加聚合，跨章节的长问题命中率低；给每篇文档加 1~2 层摘要节点（用本地 LLM 或规则摘要），让摘要也参与 RRF，是标准的 RAPTOR-lite。
- GraphRAG 的社区摘要对「团队知识库的总览性问题」有价值，但需要实体抽取 + 层次聚类，工程量最大，优先级最低。

## 8. LangMem：热路径 vs 后台

**来源**：langchain-ai/langmem README

- **热路径工具**：agent 在对话中主动 `record` / `search`
- **后台整理器**：自动 extract / consolidate / update 知识

**对本项目的意义**：「热路径写、后台整理」这个分工我们已经有了（`memory_save` + `consolidate/*`）。差别在于它是**自动抽取**，我们是**模型显式保存**——对本机（CPU 推理、token 敏感）而言，显式保存反而更划算、更可控，不改。

## 9. 落地建议（按性价比排序）

### P0-1：给记忆加时间有效性，冲突改「失效」而非「删除」

- 新增字段：`valid_from` / `valid_until`（date）、`superseded_by`（keyword）
- 检索默认过滤 `valid_until is null`（配合现有 `status=active`）
- `consolidate/conflict.ts` 的命中从「进 pending」改为「**个人库直接 supersede、团队库仍进 pending**」——团队库的错误结论代价太高
- 参考：Zep 的边失效 + Mem0 的 DELETE 语义
- 风险：mapping 是 `dynamic: strict`，改模板要做索引重建或 reindex；个人库可重建，团队库需谨慎
- 验证：造 3 组「旧结论→新结论」样本，确认旧条不再出现在 `memory_search` 结果里，但按 id 可查

### P0-2：检索反馈回写 + 权重可配置

- 新增字段：`hit_count`（integer）、`last_hit_at`（date）
- `memory_search` 命中后异步 `_update` 计数（不要同步阻塞检索；失败不影响返回）
- `mergeScopes` 之后乘一个热度因子，**不要混进 RRF 分**（尺度差一个数量级，见 `fragment.ts` 注释）
- `PERSONAL_WEIGHT` 从常量改为 config，与 `retrieval` 同组
- 参考：MemoryOS 的 `Heat`、Zep 的 episode-mentions
- 验证：同一 query 连续检索 5 次，目标条目的排序应单调上升（或至少不掉），且不能压过明显更相关的新条目

### P0-3：`importance` 落地为「温和乘子」

- `memory_save` 接受 `importance: critical|normal|low`，默认 `normal`
- 映射为 1.1 / 1.0 / 0.9 乘在融合分上——**只做微调，不做主导**，否则会退化成「按标签排序」
- 参考：MemoryBank 的 significance
- 注意：不要进 BM25 字段权重（会让关键词命中和重要性混淆）

### P1-1：加一条「同 topic_key 兄弟」召回路

- 比图扩散便宜得多：RRF 第三路 = 命中条目的 `topic_key` 下的其他条目
- 直接改善「换个说法就问不到同一主题下另一条」的情况
- 参考：Zep 的 BFS 意图、A-MEM 的链接，但用 ES 的 `terms` 查询实现

### P1-2：`doc_search` 的 RAPTOR-lite

- 每篇文档额外索引 1 层摘要节点（`doc_id` 相同、`chunk_index=-1`、`is_summary=true`）
- 检索时摘要节点与普通 chunk 一起进 RRF，聚合时摘要命中的权重略高
- 参考：RAPTOR
- 风险：摘要质量决定上限；建议先用规则抽取（标题 + 首段 + 小节标题拼接）做基线

### P2：评测基准

- 用 LOCOMO / LongMemEval 的问题形态自建一个 50 条的中文小集（单跳 / 多跳 / 时间 / 开放域四类）
- 每次改权重只跑这一个集，避免「凭感觉调参」
- 参考：Mem0 / Zep / MemoryOS 的评测口径

## 10. 明确不建议照搬的

| 做法 | 理由 |
|---|---|
| 引 Neo4j / 图数据库 | 我们的隔离靠「一人一索引 + 索引级 ACL」，ES basic license 没有 DLS/FLS；换图库等于重建整个权限模型 |
| LLM 自动抽取记忆 | 本机是 CPU Ollama，每条记忆一次 LLM 调用不划算；且显式保存的语义质量更高 |
| 物理删除旧结论 | 团队知识库要审计，「为什么当时这么定」本身是知识 |
| 让新记忆反向改写旧记忆的表述（A-MEM 的 evolution） | 等于改写历史证据，无法回溯 |
| agent 自管理记忆分页（MemGPT） | 每次搬页都是 token；我们的工具接口已经够用 |

## 附录：用 Neo4j 按「个人 / 团队」分图可行吗

结论：**技术上能做，但「两张图」这个粒度有三种不同实现，成本与隔离强度差一个数量级；社区版（免费）拿不到干净隔离。**

### 四条硬限制（均来自官方文档原文）

1. **Community 版只能有一个 standard database**
   > "Installations of Community Edition can have exactly **one** standard database. Installations of Enterprise Edition can have any number of standard databases."
   —— [Database administration](https://neo4j.com/docs/operations-manual/current/database-administration/)

   所以「一人一库」在免费版不存在，只能靠多实例或多 label。

2. **RBAC（CREATE ROLE / GRANT / DENY）只在企业版系**
   「Manage roles」「Limitations」等页面的适用版本标注均为 *AuraDB Business Critical / AuraDB Virtual Dedicated Cloud / Enterprise Edition*。Community 版只有认证，没有细粒度授权——任何持连接凭据的用户都能读全库。

3. **授权粒度是 label / 关系类型 / 属性，没有按属性值的行级过滤**
   语法形如 `DENY TRAVERSE ON GRAPH * NODES Person TO users`，不支持 `WHERE n.owner_uid = $user` 这种行级条件。想按用户隔离只能「一人一个 label」，label 数量随人数线性膨胀，索引与查询规划都会变差。

4. **全文 / 向量索引与权限交叉时会保守丢结果**（这条最容易被忽略）
   > "If a result **might violate** the security rules, Neo4j treats it as if it **does violate** the security rules and excludes it from the results returned by the index. This means it either returns zero results (or a partial result)."
   —— [Limitations](https://neo4j.com/docs/operations-manual/current/authentication-authorization/limitations/)

   对记忆检索是灾难性的：宁可漏不可错没错，但「漏到 0 条」等于检索失效，而且丢多少不可预测。

### 四种方案对照

| 方案 | 个人/团队隔离 | 一人一张图 | 版本 | 主要代价 |
|---|---|---|---|---|
| 两个 Community 实例（personal + team） | 实例级，干净 | 不能（个人图内多用户混住） | 免费 | 两套备份/凭据；个人图内仍靠应用层过滤 |
| Enterprise 多库 + 每库 GRANT | 库级，干净 | 能 | 付费 | 许可证；向量索引权限坑；迁移成本 |
| 单库用 `:Personal`/`:Team` + owner 属性 | **假隔离**（应用层） | 名义上能 | 免费 | 任何持凭据者可读全部，与当前「一人一账号」模型冲突 |
| 一人一个 Neo4j 容器 | 天然彻底 | 能 | 免费 | 每人约 0.5~1 GB 内存 × N；N 套备份；三份数据源同步 |

### 建议

**只做一张团队图，个人记忆不进图。**

- 团队知识的权限模型本来就只有「读 / 写」两态（`mem_team_read` / `mem_team_write`），不需要行级隔离，图库的能力边界刚好够用；
- 个人记忆继续留在 ES：一人一索引 + 索引级 ACL 已经把隔离做完了，换到 Neo4j 只会退步；
- 若目标只是「图扩散的召回效果」，有两条更轻的路：ES 里存 `links` 数组 + 应用层二跳；或离线用 networkx 算 PPR 后把 `ppr_score` 写回 ES 作 `rank_feature`（不需要在线图库）；
- 若目标是「可交互地探索知识关系」，把 Neo4j 当**只读镜像**：从 ES 单向同步，不承担权威数据与权限，这是性价比最高的一种用法。

另外提醒：现在已有 ES + mnemon SQLite 两份数据源，加图就是第三份，双写一致性会成为新的一类故障（整理任务要同时维护两处）。
