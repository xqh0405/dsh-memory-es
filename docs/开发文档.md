## 0. 结论先行

1. **没有现成插件能覆盖这个闭环**：ES 后端 + 双层隔离 + LLM 整理入库 + 混合检索，四件事同时具备的 DSH 插件当前不存在，需要自建。
2. 可复用的只有两处**局部经验**：`dsh-client-ui-elasticsearch` 的 ES 连接配置与工具注册形态、`dsh-memory-bridge` 的“LLM 提取 + 规则双通道 + 可追溯”思路。两者的定位都不是记忆管理，不能当骨架直接改。
3. **ES 免费版没有 DLS**（实测 403 `non-compliant for field and document level security`）→ 个人库改用「一人一索引 `personal_memory_<user_id>` + 索引级 ACL」（§4，D5）。写路径仍由插件强制注入 `user_id`，且**工具参数里不出现 `user_id`**。
4. 第二条容易做错的：团队库是**单向写入**。AI 日常对话只能写个人库，团队库唯一的写入方是整理服务。这条一旦松掉，检索质量会随库膨胀单向下降，且没有回退手段。
5. **当前进度（2026-10-25）**：ES 8.19.23 已部署并验证（`scripts/verify-isolation.sh` 11/11 PASS），`bge-m3` 已装；插件代码**尚未开始**，按 §16 从 S1 起。

## 1. 目标与边界

### 1.1 目标

| # | 目标 | 可验证的判据 |
|---|---|---|
| G1 | 双层记忆库 | `personal_memory` / `team_knowledge` 两个索引；个人库文档跨用户互不可见（集群层，不靠应用过滤） |
| G2 | AI 读写用各自凭证 | 用户 A 的凭证读不到 B 的文档；插件不持有超级用户权限做日常读写 |
| G3 | 定期整理入库 | 定时任务能把个人记忆蒸馏成团队知识，`source_user` / `source_memory_id` 可回溯到原始记忆 |
| G4 | 语义增强 | 专有名词与错误码能精确命中；换了说法、口语化提问也能命中 |

### 1.2 非目标

- 不做通用搜索引擎 / 日志平台（那是 `dsh-client-ui-elasticsearch` 的定位，不要混）。
- 不做多租户 SaaS、不做公网多团队托管；本期面向单团队自托管。
- 不替代 DSH 现有的热记忆层（`MEMORY.md` / `USER.md` 注入）：ES 是**按需召回的冷层**，每回合全量注入的成本模型不同，不要试图用 ES 取代热层。
- 不做自动的“记忆衰退删除”：`expires_at` 本期只做标记与检索降权，不做物理删除。

### 1.3 硬约束

1. **单一写入入口**：团队库只允许整理服务账号写入。
2. **成本约束**：整理任务不在固定周期全量扫描，按增量/活跃度触发。
3. **可追溯**：任何团队知识必须能回答“它来自谁的哪条记忆”。
4. **安全优先**：ES 必须开 `xpack.security`。官方 quickstart 里 `xpack.security.enabled=false` 的跑法只用于本机试用，不进入本方案。

## 2. 总体架构

### 2.1 组件

```
┌──────────────────────────────────────────────┐
│ DSH (web profile)                            │
│  ┌────────────────────────┐                  │
│  │ dsh-memory-es 插件     │                  │
│  │  memory_save           │──┐               │
│  │  memory_search         │  │ 每用户凭证    │
│  │  memory_update_status  │  │ (API key)     │
│  │  memory_promote(可选)  │  │               │
│  └────────────────────────┘  │               │
└──────────────────────────────┼───────────────┘
                               │ HTTPS
                  ┌────────────▼──────────────────────┐
                  │ Elasticsearch（Docker，security 开）│
                  │  personal_memory_<uid> (索引级 ACL) │
                  │  team_knowledge        (全员读)     │
                  └────────────▲──────────────────────┘
                               │ 整理服务账号（读全部个人索引 + 只写团队库）
                  ┌────────────┴─────────────┐
                  │ consolidate 整理任务      │
                  │ （独立进程，非插件内）     │
                  │  LLM 蒸馏 → 去重 → 写入   │
                  └──────────────────────────┘
                               │ 可选
                  ┌────────────┴─────────────┐
                  │ Markdown 镜像层（人读/入 Git）│
                  └──────────────────────────┘
```

### 2.2 三条数据流

**写路径（对话中）**

```
模型 → memory_save(content, memory_type, domain, privacy)
     → 插件补全 user_id / memory_id / 时间戳 / status=active
     → （可选）LLM 生成 semantic_keywords + embedding
     → ES index personal_memory_<uid>（refresh=wait_for；索引名由 user_id 派生）
     → 返回 memory_id
```

**读路径（对话中）**

```
模型 → memory_search(query, [memory_type], [domain], [scope=both|personal|team])
     → 个人库：BM25 + kNN 双路（索引级 ACL 限定范围，插件不重复过滤）
     → 团队库：先元数据过滤（domain/memory_type/时间窗）再混合检索
     → 融合排序（RRF）→ 截断 → 返回精简字段
```

**整理路径（定时，独立进程）**

```
扫描：活跃用户的 promote_state=none 且 privacy=normal 的近期记忆
     → LLM 蒸馏：判断「仅个人有用」/「有团队普适价值」
     → 团队候选：改写去个人上下文 + domain 标签 + 来源字段
     → 去重（精确 hash → 语义近邻）+ 冲突检测（矛盾则进人工队列）
     → 敏感信息扫描（命中即阻断）
     → 写入 team_knowledge（source_user / source_memory_id）
     → 回写个人库 promote_state=promoted|rejected|blocked
```

### 2.3 交付物清单

| 交付物 | 形态 | 归属里程碑 |
|---|---|---|
| ES 集群（Docker，安全开启） | compose + 初始化脚本 | M0 |
| 索引 mapping + 索引模板 | JSON / curl 脚本 | M0 |
| 角色与用户/API key（个人只读 / 团队读 / `mem_writer` / 整理服务 / `apikey_owner`） | 初始化脚本 + `verify-isolation.sh` | M1 |
| `dsh-memory-es` 插件（4 工具 + 配置 + 系统提示片段） | npm 包 / file: 安装 | M2–M3 |
| 整理任务（consolidate） | 独立 Node/Python 进程 + 调度 | M4 |
| 治理能力（隐私标记、去重、冲突、审计） | 插件 + 整理任务 | M5 |
| Markdown 镜像层（可选） | 脚本 | M6 |

## 3. 索引与映射

### 3.1 `personal_memory_<user_id>`（索引模板）

一人一索引；所有个人索引由同一个 composable index template 继承 mapping：

```json
PUT _index_template/personal_memory_template
{
  "index_patterns": ["personal_memory_*"],
  "priority": 100,
  "template": {
    "settings": {
      "number_of_shards": 1,
      "number_of_replicas": 0,
      "refresh_interval": "5s"
    },
    "mappings": {
    "dynamic": "strict",
    "properties": {
      "memory_id":        { "type": "keyword" },
      "user_id":          { "type": "keyword" },

      "content":          { "type": "text",
                            "analyzer": "ik_max_word",
                            "search_analyzer": "ik_smart" },
      "semantic_keywords":{ "type": "text",
                            "analyzer": "ik_max_word",
                            "search_analyzer": "ik_smart" },
      "embedding":        { "type": "dense_vector",
                            "dims": 1024,
                            "index": true,
                            "similarity": "cosine" },

      "memory_type":      { "type": "keyword" },
      "domain":           { "type": "keyword" },
      "privacy":          { "type": "keyword" },
      "promote_state":    { "type": "keyword" },
      "status":           { "type": "keyword" },
      "supersedes":       { "type": "keyword" },
      "superseded_by":    { "type": "keyword" },
      "content_sha256":   { "type": "keyword" },

      "created_at":       { "type": "date" },
      "updated_at":       { "type": "date" },
      "expires_at":       { "type": "date" }
    }
    }
  }
}
```

说明：

- **索引按人切分**（D5）：`personal_memory_<user_id>`，由上面的模板统一 mapping；新用户只需 `PUT personal_memory_<uid>`（空 body `{}`）即继承全部字段。这是索引级 ACL 能真正隔离的前提（§4）。
- `number_of_replicas: 0`：单节点部署；上多节点时改 1，否则集群长期 yellow。
- `dims: 1024` 已定（D1：`bge-m3`，依据见 §14）。必须与 embedding 模型严格一致，改模型 = 重建索引（ES 不允许原地改维度）。**这个值 M0 就要定死**；若 M0 实测退模型，索引必须删掉重建，不要试图改 `dims`。
- `dynamic: strict` 是故意的：字段名写错会直接写入失败，而不是静默生成一个没人查的新字段。代价是新增字段要先改 mapping。
- `content` 走 `ik_max_word`（索引细粒度，提高召回）、`ik_smart`（检索粗粒度，提高精度）是常见组合；如果实测发现口语化 query 召回不足，优先调 `semantic_keywords`，不要动分词器。

### 3.2 `team_knowledge`

```json
PUT team_knowledge
{
  "settings": { "number_of_shards": 1, "number_of_replicas": 1 },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "doc_id":          { "type": "keyword" },
      "content":         { "type": "text", "analyzer": "ik_max_word", "search_analyzer": "ik_smart" },
      "semantic_keywords":{ "type": "text", "analyzer": "ik_max_word", "search_analyzer": "ik_smart" },
      "embedding":       { "type": "dense_vector", "dims": 1024, "index": true, "similarity": "cosine" },

      "memory_type":     { "type": "keyword" },
      "domain":          { "type": "keyword" },
      "topic_key":       { "type": "keyword" },
      "content_sha256":  { "type": "keyword" },

      "source_user":     { "type": "keyword" },
      "source_memory_id":{ "type": "keyword" },
      "source_created_at":{ "type": "date" },
      "promoted_at":     { "type": "date" },

      "status":          { "type": "keyword" },
      "review_state":    { "type": "keyword" },
      "supersedes":      { "type": "keyword" },
      "superseded_by":   { "type": "keyword" },
      "updated_at":      { "type": "date" }
    }
  }
}
```

### 3.3 字段语义

| 字段 | 取值 | 谁写 | 备注 |
|---|---|---|---|
| `memory_type` | `preference` / `fact` / `task_progress` / `decision` / `context` | 插件（可由 LLM 判定，缺省 `fact`） | 检索时先过滤，能显著缩小候选集 |
| `domain` | 业务域短标签（如 `lottery-cloud`、`backup-server`） | 插件自动（按工作目录/配置）+ 整理任务改写 | 团队库里是主要的收窄维度 |
| `privacy` | `normal` / `private` | 用户显式标记 | `private` 不参与整理 |
| `promote_state` | `none` / `candidate` / `promoted` / `rejected` / `blocked` | 整理任务 | `blocked` = 敏感信息命中 |
| `status` | `active` / `superseded` / `expired` | 插件 / 整理任务 | 检索一律 `status=active` |
| `review_state` | `auto` / `pending` / `approved` | 整理任务 | 冲突或低置信度进 `pending`，人工裁决 |
| `topic_key` | 主题指纹（domain + 归一化主题短语的 hash） | 整理任务 | 去重与冲突检测的粗键 |
| `content_sha256` | 归一化后正文哈希 | 插件 / 整理任务 | 精确去重，避免同文多写 |

### 3.4 版本化写入约定

**模式 A（默认，可追溯）**

- 新版本 = 新 `memory_id` 的新文档；
- 新文档 `supersedes = 旧 memory_id`；
- 旧文档 `status = superseded`、`superseded_by = 新 memory_id`；
- 检索只取 `status=active`，历史仍在库里可审计。

**模式 B（省空间，无历史）**

- 同 `_id` 覆盖 `index`，`version` 自增。

本期取 **模式 A**：审计与撤回都依赖历史留存。代价是每次更新多两次写（新文档 + 旧文档置 `superseded`），两次都由 **writer 服务账号**执行——个人用户的 key 是只读的（D2，见 §4.1 / §4.4）。

## 4. 权限与安全

> **2026-10-25 部署实测后的修订（重要）**：ES 免费版（basic license）**不支持 DLS**，实测建带 `query` 的角色直接返回
> `403 current license is non-compliant for [field and document level security]`。
> 所以个人库隔离改为 **一人一索引 `personal_memory_<user_id>` + 索引级 ACL**（免费版支持）。
> 本节按新方案写；原 DLS 方案降级为"买了 license 之后可选"，见 §4.6。

### 4.1 角色矩阵

| 角色 | 索引范围 | 读 | 写 |
|---|---|---|---|
| `mem_personal_<uid>`（个人） | `personal_memory_<uid>` | ✅ | **无（只读）** |
| `mem_team_read` | `team_knowledge` | ✅ | 无 |
| `mem_writer`（插件持有） | `personal_memory_*` | ✅ | ✅ `index`（含 update/upsert）+ `create_index` |
| `mem_consolidator`（整理服务） | `personal_memory_*` + `team_knowledge` | ✅ | 仅 `team_knowledge` |
| `mem_apikey_owner`（每个身份都绑） | — | — | cluster: `manage_own_api_key` |
| 运维只读 | 全部 | ✅ | 无 |

> 注（D2 + D5）：个人 key **只读**，所有写与状态变更由 `mem_writer` 执行。因此写入边界的可信度依赖插件进程与凭证保管，而不是依赖集群——§4.4 的 F1/F2/F3 是必需项，不是可选项。

### 4.2 角色定义（实际部署版本）

个人角色（一人一个角色、一个索引）：

```json
PUT _security/role/mem_personal_xqh
{
  "indices": [
    { "names": ["personal_memory_xqh"], "privileges": ["read", "view_index_metadata"] }
  ]
}
```

写入服务（插件持有，唯一写入口）：

```json
PUT _security/role/mem_writer
{
  "indices": [
    {
      "names": ["personal_memory_*"],
      "privileges": ["index", "read", "create_index", "view_index_metadata"]
    }
  ]
}
```

团队读 / 整理服务 / API key 自助：

```json
PUT _security/role/mem_team_read
{ "indices": [ { "names": ["team_knowledge"], "privileges": ["read", "view_index_metadata"] } ] }
```

```json
PUT _security/role/mem_consolidator
{
  "indices": [
    { "names": ["personal_memory_*"], "privileges": ["read", "view_index_metadata"] },
    { "names": ["team_knowledge"], "privileges": ["index", "read", "view_index_metadata"] }
  ]
}
```

```json
PUT _security/role/mem_apikey_owner
{ "cluster": ["manage_own_api_key"], "indices": [] }
```

要点（全部是部署时踩出来的，别再踩）：

- **`update` 不是合法的 index privilege**：ES 只认 `index` / `write` / `create_doc` / `create_index` / `read` 等固定名，写 `update` 会 400 `unknown index privilege [update]`。`index` 已经覆盖 update/upsert。
- **用户不会自动拥有 API key 创建权限**：不绑 `manage_own_api_key` 时 `POST /_security/api_key` 返回 403。
- 不给 `delete`：记忆不物理删除。
- `mem_writer` 对 `personal_memory_*` 有 `read` 是刻意的（去重、审计要跨用户读），所以**它的凭证泄露 = 全库泄露**，只能放宿主 env。
- 角色里不要出现 `manage` / `all`。

### 4.3 用户与凭证发放

```
建个人索引 → 建个人角色 → 建用户（绑个人角色 + mem_team_read + mem_apikey_owner）
→ 用该用户凭证创建 API key（继承角色）→ 写进 profile 的 identity.readApiKey
```

- 插件只持 `https://127.0.0.1:9200` + 两个 key（只读 + writer），**不持 elastic 超级用户密码**。
- key 由用户自己创建（`manage_own_api_key`），可单独吊销，不必动密码。
- TLS：自签 CA，证书必须带 SAN（`--name es01 --dns localhost --ip 127.0.0.1`），否则 curl 会因 hostname 不匹配拒绝；这套 CA 不与 MCP 的 `NODE_EXTRA_CA_CERTS` 混用。

### 4.4 写入口与三道防线

真正的风险不是"DLS 不管写"，而是"任何有写权限的身份都可能把 `user_id` 写错"。防线：

| # | 防线 | 落点 | 失败行为 |
|---|---|---|---|
| F1 | 工具参数里**没有 `user_id`** | `memory_save` schema（§6.3） | 模型无从指定，越权没有入口 |
| F2 | `user_id` 由插件注入（源 `identity.userId`），索引名也由它派生 | `memory/save.ts` | 配置缺失 → **拒绝写入**，不写匿名 |
| F3 | 写入后断言 `doc.user_id === identity.userId` 并留痕 | 写入路径 + 审计日志 | 不一致 → 拒绝 + 告警 |

F3 防的是**自己改错代码**，不防攻击者（能改配置的人本来就能写任何索引）。别把它当安全边界宣传。

### 4.5 检索范围

- 个人库：只查 `personal_memory_<identity.userId>`；索引级 ACL 保证读不到别人的。
- 团队库：查 `team_knowledge`，全员可读。
- 插件侧**不需要**再拼 `user_id` 过滤条件——这是索引级 ACL 相对 DLS 的额外好处：查询更简单、也不会因为忘记加条件而越权。

### 4.6 DLS 方案（仅购买 license 后可选）

未来若升到 Platinum/Enterprise，可回到"单索引 + DLS"：个人角色加 `"query": "{\"term\":{\"user_id\":\"<uid>\"}}"`，索引合并回 `personal_memory`。届时需要 reindex 并重发 key。**当前不做**，basic license 直接 403。

### 4.7 传输与凭证卫生

- ES 只绑 `127.0.0.1:9200`。
- key 不进仓库、不进 `cordis.patch.yml` 明文；`deploy/es/.env` 权限 600 且已 gitignore。
- 日志脱敏：打印 ES 请求时剔除 `Authorization`。

## 5. Docker 部署与运维

### 5.1 compose 骨架（单节点起步）

```yaml
# 仅示意结构，密码/证书不要提交到仓库
services:
  es01:
    image: docker.elastic.co/elasticsearch/elasticsearch:<版本号>
    container_name: dsh-es01
    environment:
      - node.name=es01
      - discovery.type=single-node        # 单节点起步；多节点时改 cluster.initial_master_nodes
      - xpack.security.enabled=true       # 必须为 true
      - xpack.security.transport.ssl.enabled=true
      - xpack.security.http.ssl.enabled=true
      - xpack.security.http.ssl.keystore.path=certs/http.p12
      - xpack.security.transport.ssl.keystore.path=certs/transport.p12
      - ELASTIC_PASSWORD=${ELASTIC_PASSWORD}
      - ES_JAVA_OPTS=-Xms2g -Xmx2g
    ulimits:
      memlock: { soft: -1, hard: -1 }
      nofile:  { soft: 65536, hard: 65536 }
    mem_limit: 6g                      # heap 2g + 堆外约 1g + page cache，见 §5.4
    volumes:
      - ./data:/usr/share/elasticsearch/data
      - ./certs:/usr/share/elasticsearch/config/certs
      - ./plugins/analysis-ik:/usr/share/elasticsearch/plugins/analysis-ik
    ports:
      - "127.0.0.1:9200:9200"             # 只绑回环，需要外部访问时再放开内网地址
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS -u elastic:$$ELASTIC_PASSWORD https://localhost:9200/_cluster/health || exit 1"]
      interval: 10s
      retries: 20
```

部署注意：

- **`<版本号>` 在部署当天确认**：`docker pull` 时用具体 tag，不要用 `latest`。IK 插件版本必须与该 tag 完全一致，否则节点起不来（启动日志报 plugin version 不匹配）。
- 单节点时 `number_of_replicas` 必须为 0，否则集群长期 yellow（副本无处分配）。本文 §3.1 写的 `1` 是多节点值，**单节点部署要改 0**。
- JVM 堆不超过宿主机内存一半，且不超过 ~31g（压缩指针边界）。
- 数据目录与证书目录都要落宿主卷，容器重建不丢。

### 5.4 生命周期、容量与内存（2026-10-25 实测）

- 本期不用 ILM 自动删除（记忆是资产）；`expires_at` 只做检索降权与状态标记。
- **实测数据**（ES 8.19.23、heap 2g、`dense_vector` 1024 维、单节点）：

| 数据量 | 索引体量 | 写入后 heap | 稳态 heap | kNN（k=10, candidates=100） |
|---|---|---|---|---|
| 0（空库） | ~40 KB | 176 MB (8%) | 176 MB | — |
| 1 万条 | 213 MB | 194 MB (9%) | — | — |
| 3 万条 | 0.6–1.1 GB | 1335 MB (65%) | 770 MB (37%)，约 2 分钟后回落 | p50 26 ms / p95 40 ms / max 90 ms |

- **结论：2 GB 堆对目标场景够用，余量很大。** 真实写入是单条（每天几十条），不会出现压测里"65 秒灌 3 万条"的峰值。
- **边界**：一次性批量导入 > 2 万条时，写入峰值会接近 2 GB。迁移/回灌必须分批（≤1000 条/批、批间留间隔），或临时调大 `ES_JAVA_OPTS`。
- **容器 RSS ≈ heap + 堆外 ≈ 2.6–3.1 GB**（Lucene mmap + page cache）。已设 `mem_limit: 6g`（heap 2g + 堆外约 1g + page cache 约 3g）：不设限时 cgroup 会把 page cache 一路记到宿主上限。实测重启后 `2.6 GiB / 6 GiB`（43%），宿主 15 GiB 上还有 ollama（加载 bge-m3 约 1.2 GiB）与 dsh。
- ⚠️ **不要用 `_source.excludes: ["embedding"]` 省存储**：向量 JSON 化后占单条约 70%（~15 KB/条），看起来很有吸引力；但 `_update` 会从 `_source` 重建整篇文档，被 exclude 的 `embedding` 会**丢失**——等于把这条记忆从 kNN 检索里废掉（不报错，只是永远搜不到）。要省空间只能换架构（向量独立索引）或给 `dense_vector` 加 `int8_hnsw` 量化，别动 `_source`。
- ⚠️ `bootstrap.memory_lock=true` 在容器里**默认不生效**（`mlockall` 未加锁，缺 `IPC_LOCK` capability）；日志不报错、单节点也不跑 bootstrap check。实测 swap 仅 0.5 MB，影响可忽略；要真锁上需加 `cap_add: ["IPC_LOCK"]`。

### 5.5 备份：snapshot + 文件级二层（2026-10-25 实测）

**为什么不能直接备份 `data/`**：运行中复制 Lucene 段会拿到不一致状态（merge/flush 时段文件在变），恢复时可能损坏或丢数据，而且当场看不出来。另外 `data/` 之外还有 `certs/` 和 `.env` 必须一起保管。

**第一层：ES snapshot（一致性由 ES 保证、增量）**

```bash
./scripts/init-snapshot.sh    # 注册 fs_repo + SLM 策略 + 立即打一个快照
./scripts/verify-backup.sh    # 写探针 → 快照 → 恢复 → 校验 → 清理（备份链验收）
```

- 仓库 `fs_repo` 落在 `deploy/es/snapshots/fs_repo`（`path.repo=/usr/share/elasticsearch/snapshots`）。
- 策略 `dsh_memory_daily`：**UTC 19:30 = 北京 03:30**，保留 14 天、最少 3 个、最多 14 个。
  - ⚠️ ES 的 SLM cron **按 UTC 解释**：写 `0 30 3 * * ?` 会在北京 11:30 跑，不是凌晨。
- 快照范围 `personal_memory_*` + `team_knowledge`，`include_global_state: true`（带上索引模板）。
- 实测：3 shard 全 SUCCESS；恢复演练 4/4（文档数一致、探针可读、mapping 16 字段）。

**第二层：文件级备份（backup-server 或 ssh 都可以）**

只需要拷三个路径：

| 路径 | 内容 | 为什么必须 |
|---|---|---|
| `deploy/es/snapshots/` | snapshot 产出 | 数据本体 |
| `deploy/es/certs/` | 自签 CA + 节点证书 | 丢了客户端信任失效，要重新分发 |
| `deploy/es/.env` | elastic 密码 + 三个 API key 明文 | ES 只在创建时返回一次，丢了只能重发 |

**不要拷 `deploy/es/data/`**：有 snapshot 就不需要；非要拷必须先停容器。

时间安排：ES 快照 03:30 完成 → 文件备份排在 **04:10 之后**，避免抓到写了一半的快照文件。

**恢复流程（灾难恢复）**

1. `scripts/es-up.sh` 起空集群（同一份 compose；certs 从备份恢复或重签）
2. 挂载 `snapshots` 目录，重新注册 `PUT _snapshot/fs_repo`
3. `POST _snapshot/fs_repo/<snap>/_restore`（`include_global_state: true` 会带回模板；目标集群已有冲突状态时改 `false` 并重跑 `init-indices.sh`）
4. 跑 `init-security.sh` 重建角色/用户/API key —— `.security` 是系统索引，**不进快照**。脚本会先**验活** `.env` 里的 key：有效才跳过，失效就重建并写回。**新 key 与旧 key 不同**，插件与脚本里的旧值必须同步更新（或改用 Basic Auth，见 §5.6）
5. 跑 `verify-isolation.sh` 确认权限仍正确

**已知边界**：`include_global_state: true` 的快照恢复到非空集群可能冲突（持久化设置/模板被覆盖），所以 `verify-backup.sh` 用的是 `false` + rename。

- 与 Markdown 镜像层（附录 C）互为兜底：ES 全挂时还能靠 md 重建语义字段之外的内容。

### 5.6 凭据的恢复语义（2026-10-25 实测）

灾备恢复后 `.security` 索引是空的，由此有三个必须知道的结论（都做过实测）：

| 事实 | 实测结果 | 后果 |
|---|---|---|
| API key 的有效性只由 `.security` 内的记录决定 | 建 key → 200；吊销 → **401** | 恢复后旧 key 必然失效，且**无法复现**（secret 由服务端随机生成） |
| 删除用户**不会**连带吊销该用户的 key | 删用户后 key 仍 **200** | key 携带创建时的权限快照；别把"删用户"当吊销手段。正确吊销：`DELETE /_security/api_key` + body `{"ids":[...]}`（`?name=` 形式在 8.19 返回 400） |
| 用户名 + 密码**可以复用** | 同名同密码重建后 Basic Auth 立即 **200** | 密码存在 `.env` 里，恢复时原样重建即可 |

**所以两条路可选**：

- **用 API key**：恢复后必须重建（`init-security.sh` 已能验活并重建），然后同步更新插件配置和任何脚本里的旧值。旧 key 在新集群里不存在，不会留孤儿。
- **用 Basic Auth（用户名+密码）**：恢复后重建用户、密码不变，客户端**零改动**。在「单机 + TLS + 只绑 127.0.0.1」的场景里，这个取舍通常更划算——API key 的优势（单独吊销、细粒度）在这里用不上，却换来一次灾备配置同步。
- 插件可以两者都支持：`identity.readApiKey` 与 `identity.username/password` 二选一。

随时可复查当前有效 key：

```bash
curl -sS --cacert deploy/es/certs/ca.crt -u "elastic:$PASS" \
  'https://127.0.0.1:9200/_security/api_key?active_only=true'
```

## 6. 插件设计（DSH 侧）

### 6.1 类型选型

- 主体是 **Tool Plugin**：注册 4 个工具 + 一个 `systemPrompt` 片段（教模型何时存、何时查）。
- 不选 Event Interceptor / Agent Loop：记忆读写是显式动作，不需要挂到工具执行链上。
- 若后续要做“每回合自动召回注入”，再考虑 `systemPrompt` 动态段或拦截器，但那会把每回合 token 成本抬高，**本期不做**。

### 6.2 配置项

| 配置键 | 说明 |
|---|---|
| `es.url` | `https://host:9200` |
| `es.caCertPath` | 自定义 CA 证书路径（自签集群必填） |
| `es.requestTimeoutMs` | 默认 8000；检索超时要降级而不是挂住 |
| `index.personalPrefix` / `index.team` | 个人索引前缀（默认 `personal_memory_`，实际索引 = 前缀 + `identity.userId`）/ 团队索引 `team_knowledge` |
| `identity.userId` | 当前用户 id（F2 注入源）；缺省**拒绝写入**，不写匿名（D3：一机一身份） |
| `identity.writerCredentials` | `mem_writer` 凭证（F1/F2 的执行者）；只从 env 读，不落配置明文 |
| `identity.readApiKey` | 读用的个人 API key（只读角色） |
| `embedding.provider` / `model` / `dims` | 默认 `ollama` / `bge-m3` / `1024`（D1）；`dims` 必须与索引 mapping 一致 |
| `retrieval.rrfK` | RRF 常数，默认 60 |
| `retrieval.topK` | 每路候选数，默认 20 |
| `retrieval.resultLimit` | 返回给模型的最大条数，默认 8 |
| `consolidation.*` | 整理任务的阈值（在独立进程里读同一份配置或独立配置文件） |

### 6.3 工具契约

#### `memory_save`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `content` | string | 是 | 要记住的正文（建议一句一事实，避免整段对话） |
| `memory_type` | enum | 否 | 默认 `fact`；取值见 §3.3 |
| `domain` | string | 否 | 缺省按当前工作目录/配置推导 |
| `privacy` | enum | 否 | `normal`（默认）/ `private` |
| `ttl_days` | number | 否 | 可选过期，写 `expires_at` |

行为：补全 `memory_id`（uuid）、`user_id`（注入）、`created_at`/`updated_at`、`status=active`、`content_sha256`；生成 `semantic_keywords` 与 `embedding`；`refresh=wait_for` 后返回。

返回：`{ memory_id, deduped: bool, note?: string }`。命中 `content_sha256` 已存在 → 不重复写，返回 `deduped=true`。

#### `memory_search`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `query` | string | 是 | 自然语言或关键词 |
| `scope` | enum | 否 | `both`（默认）/ `personal` / `team` |
| `memory_type` | string[] | 否 | 过滤 |
| `domain` | string[] | 否 | 过滤 |
| `time_range` | string | 否 | 如 `now-180d`，只影响 `updated_at` 过滤 |
| `limit` | number | 否 | 默认 8，上限 20 |

返回：**精简结构**，每条只给 `memory_id`、`content`（截断到 500 字符）、`memory_type`、`domain`、`updated_at`、`source::personal|team`、`score`。**不要返回 `embedding`、`_source` 全量**，否则一次检索就吃掉大量 token。

空结果要明确返回 `{ hits: [], note: "no_match" }`，不要静默返回空对象让模型误判为“没有记忆”。

#### `memory_update_status`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `memory_id` | string | 是 | 目标记忆 |
| `action` | enum | 是 | `supersede` / `expire` / `mark_private` |
| `reason` | string | 否 | 审计用 |
| `replacement_memory_id` | string | 否 | `supersede` 时指向新版本 |

行为：对旧文档置 `status=superseded` / `expired`，写 `superseded_by`。**不物理删除**。

#### `memory_promote`（可选）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `memory_id` | string | 是 | 标记为团队候选 |
| `reason` | string | 否 | 说明为什么值得团队复用 |

行为：只置 `promote_state=candidate`，**不直接写团队库**。真正的晋升由整理任务完成（§9）。这一条是防噪声的闸门，不要为了“方便”改成直写。

### 6.4 系统提示片段（要点）

- **何时存**：用户明确要求记住、做了非显然的决策、踩到可复现的坑、约定/口径变化。**不要存**：临时进度、会话摘要、能从代码里读到的内容。
- **何时查**：动手前查“这个项目以前怎么定的”；查不到再问人，不要凭印象。
- **一次一条**：`memory_save` 的 `content` 是“一句可独立成立的事实”，不是一段对话。
- **不要反复检索**：同一问题最多查一次，拿到结果就往前走。

### 6.5 错误处理与降级

| 情况 | 行为 |
|---|---|
| ES 不可达 / 超时 | 工具**明确失败**并返回原因；不允许静默“当作已保存” |
| 认证失败（key 过期） | 提示轮换凭证，不重试 |
| 索引不存在 | 报配置错误并给出应执行的初始化命令 |
| embedding 服务不可用 | 降级为纯 BM25 写入（`embedding` 留空），工具返回 `degraded=true`；整理任务跳过该批 |
| F3 校验失败（`actor_user_id ≠ document.user_id`） | 视为越权尝试，拒绝 + 审计日志 + 告警 |

## 7. 入库提炼管道

### 7.1 两条腿并行，不要互相替代

| 通道 | 手段 | 负责什么 |
|---|---|---|
| 精确通道 | IK 分词 + BM25 | 专有名词、产品代号、错误码、文件路径、接口名 |
| 语义通道 | `semantic_keywords` + `embedding` + kNN | “换了说法也能找到”“口语提问”“同义词” |

**常见错误**：用 LLM 生成的关键词替代分词。后果是错误码被“润色”掉，精确检索反而失效。

### 7.2 LLM 增强字段的生成

`semantic_keywords` 的生成提示应当要求“**用户可能怎么问**”，而不是“同义词列表”：

```
给定一条记忆正文，生成 3–6 条用户可能用来检索它的问句或短语。
要求：
- 保留原文中的专有名词、错误码、接口名（不得改写）
- 覆盖不同提问角度（是什么 / 怎么修 / 在哪配 / 坑在哪）
- 每条 ≤ 25 字
- 只输出 JSON 数组
```

`embedding`：对 `content + semantic_keywords` 拼接后编码（不要只编码 content，会浪费关键词带来的召回面）。

### 7.3 ingest pipeline 还是应用侧生成？

**推荐应用侧生成**，理由：

1. ES 的 inference processor 需要部署模型或指向外部 inference endpoint，多一层运维；
2. 插件已经要调 LLM 做蒸馏，生成关键词/向量的复用成本更低；
3. 失败可重试、可观测（pipeline 里出错排查成本高）。

pipeline 只保留一件事：**写入前校验**（字段完整性、`content_sha256` 计算、越权拒绝）。

### 7.4 幂等

- 以 `content_sha256`（正文归一化后：去空白、统一全半角）为幂等键；
- 同一用户同一 hash 已存在 → 跳过写入，返回既有 `memory_id`；
- 整理任务重跑不应产生重复团队文档：以 `topic_key` + `content_sha256` 双键判重。

## 8. 检索策略

### 8.1 混合检索的两条实现路线

**路线 A：集群侧（需要较新版本）**

ES 的 retriever API / 原生 RRF 可以把双路下推到集群。版本门槛与语法在不同 8.x 小版本间有变化，**部署时先 `GET /` 确认版本，再查对应版本文档**，不要照抄某篇博客的语法。

**路线 B：应用侧融合（默认，版本无关）**

两路各取 topN，应用侧用 RRF 合并：

```
score(d) = Σ_route  1 / (k + rank_route(d))     k = 60
```

伪代码：

```
bm25 = search(index, { query: multi_match(fields: ["content^2","semantic_keywords^1.5"]),
                      filter: [status=active, ...meta], size: topK })
knn  = search(index, { knn: { field: "embedding", query_vector: vec,
                              k: topK, num_candidates: topK*5,
                              filter: [status=active, ...meta] }, size: topK })
merged = rrf([bm25, knn], k=60)
```

注意：`knn` 在 ES 8.x 里是**顶层参数**，不能塞进 `query.bool.should`。宁可两次请求，也不要用“看似能跑但排序语义不明”的混合写法。

### 8.2 先过滤再检索

团队库必须先按 `domain` / `memory_type` / `updated_at` 收窄，再做语义匹配：

- 降延迟（kNN 的 `num_candidates` 只在过滤后的集合里展开）；
- 降噪声（跨域的同义表述会互相污染）；
- 降成本（候选少了，LLM 重排才负担得起）。

过滤条件缺失时的兜底：只加 `status=active` + `updated_at >= now-365d`，并在返回里标注 `filtered=false`，让模型知道结果面比较宽。

### 8.3 个人 + 团队合并

1. 两库分别检索，各自内部 RRF；
2. 合并时**不要让团队库天然压过个人库**：给个人库乘一个 >1 的权重（如 1.2），因为个人记忆通常更贴近当前上下文；
3. 按 `content_sha256` 去重（同一条被晋升后两库都有）；
4. 截断到 `limit`，并在每条上标 `source`。

### 8.4 阈值：不要用绝对相似度切

2026-10-25 用 `bge-m3` 做了 4 条记忆 × 5 个中文 query 的定性测试（完整数据见附录 B），结论是**绝对相似度不可用作硬阈值**：

| 查询 | top1 | top2 | margin |
|---|---|---|---|
| 比赛腰斩/中断了该怎么结算 | A 0.5710 | C 0.4315 | 0.1395 |
| 发布流水线选错分支怎么办 | B 0.6511 | D 0.4994 | 0.1517 |
| 下载模型一直提示连接被拒绝 | C 0.6039 | D 0.5229 | 0.0810 |
| 某个用户能不能伪造别人的记忆 | D 0.4742 | A 0.4070 | 0.0672 |
| （噪声）无对应文档 | C 0.4800 | D 0.4755 | **0.0045** |

- 正确命中的绝对分低到 **0.4742**，而无关查询也能到 **0.4800** → 任何固定阈值都会同时误杀正确命中、放进噪声。
- **能用的信号是 margin（top1 − top2）**：命中 0.067~0.152，噪声 0.0045。
- 因此：kNN 结果**不做绝对分过滤**；用 margin（初值 0.05）判“是否值得返回”，并**返回 top-2 让模型自己判断**；排序用 RRF（等级融合，天然不依赖绝对分）。
- 这是 4 条样本的定性结论，M3 用 30 条扩样本复测后再把初值写死。

## 9. 定期整理任务（consolidation）

### 9.1 触发策略

不做固定全量扫描。三种触发条件取其一（配置可调）：

1. 某用户 `promote_state=none` 且 `created_at` 在窗口内的记忆数 ≥ N（默认 20）；
2. 距该用户上次整理 ≥ 7 天且有新增；
3. 手动触发（一期先提供 CLI，`--dry-run` 为默认）。

### 9.2 蒸馏契约

输入：一批个人记忆的精简字段（`memory_id`、`content`、`memory_type`、`domain`、`created_at`）。**不要喂整段对话**。

输出：严格 JSON（失败则整批不写，避免半成品入库）：

```json
{
  "items": [
    {
      "source_memory_ids": ["..."],
      "verdict": "team_worthy | personal_only",
      "reason": "为什么",
      "rewritten_content": "去掉个人上下文的表述",
      "domain": "lottery-cloud",
      "memory_type": "fact",
      "confidence": 0.0
    }
  ]
}
```

### 9.3 改写规则

- 去掉“我/我们的环境/上次你说”这类个人上下文；
- 保留可复现的关键信息：版本号、路径、错误码、判据；
- 补 `domain` 标签；
- 必带 `source_user` + `source_memory_id` + `source_created_at`。

### 9.4 去重与冲突

```
第一道：content_sha256 精确命中 → 跳过
第二道：kNN top-5，最高相似度 ≥ 0.90 → 判重复，走“合并/更新”而非新增
第三道：同 topic_key 但语义相似度中低（0.6~0.9）→ 可能是同一主题的不同结论
        → review_state=pending，进人工队列，不进检索结果
```

冲突（同一 `topic_key` 出现相反结论，如“必须 A”vs“禁止 A”）**一律 pending**。这类判断交给人工，是 §1.3 的可追溯约束的一部分。

### 9.5 敏感信息扫描

入库前扫：私钥块、云厂商 AK/SK、`sk-`/`ghp_` 类 token、身份证号、手机号、内网密码。命中：

- `promote_state=blocked`，记 `blocked_reason`；
- 不写团队库；
- 不打印原文到日志（只打命中类型与位置）。

### 9.6 成本与幂等

- 批大小上限（默认 20 条/批），失败重试上限 3 次；
- 每批处理前后记录游标（用户 id + 时间窗），重跑幂等；
- LLM 调用失败**不回滚已写入的团队文档**，但要把该批标记为 `partial` 供人工核对。

## 10. 隐私与审计

- 用户可对单条记忆标 `privacy=private`：不进整理候选，不参与团队检索。
- 团队库每条都带 `source_user` / `source_memory_id` / `promoted_at`，支持“这条知识哪来的/谁撤”。

- 保留期：团队库不自动清理；个人库 `expires_at` 过期后只降权，不删。

## 14. 决策记录（ADR）

### D1 · embedding 模型 = `bge-m3`（1024 维）

- **决策**：语义通道用 `bge-m3`，`dims = 1024`；不用本机已有的 `nomic-embed-text`。
- **依据**：
  - 本机实测 `nomic-embed-text` 输出 **768 维**（模型族 `nomic-bert`），偏英文——而 G4 的核心正是“换了说法也能找到”，中文改写式查询恰是它的弱项。
  - `bge-m3` 是多语模型、1024 维、中文表现优于同尺寸英文模型，Ollama 官方库直接可取。
  - 容量代价可忽略：1024 维比 768 维每条多约 1 KB（§5.4 已按 1024 重算）。
- **代价**：本机 CPU 推理，单条编码比 nomic 慢；写入每条约 1 次编码、检索 1 次/query，可接受。
- **复核结果（2026-10-25 已验）**：维度 **1024** 实测通过；CPU 单条编码 **约 0.20 s**（3 次 0.197~0.209 s，含 HTTP 开销）；4 条中文“换说法”query 定性测试 **4/4 top1 命中**（margin 判别结论见 §8.4）。M3 仍需扩到 30 条复测。
- **退路**：若拉取或推理不可用，退 `nomic-embed-text`（768）——那时 `dims` 必须重建索引，且 G4 的验收阈值要下调。

### D2 · 写入隔离 = 个人只读 + `mem_writer` 单一写入口

> ⚠️ **本条关于"单索引"的部分已被 D5 取代**（改为一人一索引）。写入侧的结论不变：个人 key 只读、写只走 `mem_writer`。

- **决策**：个人 API key 只读；所有写与状态变更由 `mem_writer` 服务身份执行。
- **依据**：
  - 若个人 key 带写权限，“注入 user_id”就是唯一防线，太薄。
  - 个人只读后，写边界集中在一处，审计简单。
- **代价**：写边界的可信度依赖插件进程与凭证保管；`mem_writer` 有跨用户读权限，泄露即全库泄露。
- **补偿**：F3 不变量断言（§4.4）+ writer 凭证只走宿主 env + 定期轮换。

### D3 · 身份来源 = 一机一身份

- **决策**：`identity.userId` 由 profile 配置指定，一台机器 / 一个 profile 代表一个用户。
- **依据**：DSH 是本机单用户 harness；“每会话不同身份”需要额外的身份传递通道，本期没有需求支撑。
- **扩展路径**：真出现多身份共用一台机器时，把 `identity.userId` 改成按会话头解析；索引与角色都不用动（`user_id` 是文档字段）。

### D4 · 版本化写入取模式 A（新文档 + 旧文档 superseded）

- **决策**：见 §3.4。
- **依据**：审计与撤回依赖历史留存；置 `superseded` 的 `_update` 由 writer 执行。
- **代价**：每次更新两次写；库里保留历史版本，检索必须带 `status=active`。

### D5 · 个人库隔离 = 一人一索引（因 basic license 无 DLS）

- **背景**：D2 原先假设"DLS 可用、单索引 + 文档级过滤"。2026-10-25 实际部署 ES 8.19.23（basic license）后，建带 `query` 的角色直接 403：

  ```
  current license is non-compliant for [field and document level security]
  ```

  DLS / FLS（字段级安全）都是 Platinum/Enterprise 功能，免费版没有。

- **决策**：改为 **一人一索引 `personal_memory_<user_id>` + 索引级 ACL**（免费版支持），mapping 由 `personal_memory_template` 统一。
- **依据**：
  - 索引级权限在 basic license 下可用：`scripts/verify-isolation.sh` 实测 **11/11 通过**（读隔离、写边界、IK 精确命中、kNN 换说法召回）。
  - 隔离更硬：读写都由集群 ACL 限制，不依赖应用层拼 `user_id` 条件。
  - 不依赖会过期的 trial license（trial 30 天到期后 DLS 角色失效，记忆会突然读不到）。
- **代价**：索引数随用户增长；mapping 升级要按索引重建（模板 + `_reindex`）；检索扇出 = 个人 1 + 团队 1，可忽略。
- **否决的替代方案**：① 开 30 天 trial —— 到期失效，不可接受；② 纯应用层 `user_id` 过滤 —— 安全边界全在插件代码，漏一个条件就串号。
- **运维**：新增用户 = 跑 `init-indices.sh` + `init-security.sh`（按 `.env` 的 `MEM_USER_ID` 生成索引、角色与 key）。

### 15.3 关键流程

#### 15.3.1 启动与失败边界

```ts
export function apply(ctx: Context, raw: unknown) {
  const cfg = Config(raw)                  // 缺 identity.userId → 这里就抛
  const client = createEsClient(cfg.es)
  const embed  = createEmbedder(cfg.embedding)

  ctx.effect(() => ctx.tools.register(saveTool(cfg, client, embed)),   'dsh-memory-es.save')
  ctx.effect(() => ctx.tools.register(searchTool(cfg, client, embed)), 'dsh-memory-es.search')
  ctx.effect(() => ctx.tools.register(statusTool(cfg, client)),        'dsh-memory-es.status')
  ctx.effect(() => ctx.tools.register(promoteTool(cfg, client)),       'dsh-memory-es.promote')
  ctx.effect(() => ctx.systemPrompt.section({
    name: 'dsh-memory-es', order: 80, text: MEMORY_PROMPT,
  }), 'dsh-memory-es.prompt')
}
```

**失败边界**：配置非法时让**这个插件**加载失败，而不是让整个 dsh 起来不了。Cordis 会隔离单个插件的 apply 异常——M2 要实测确认这一点（判据：故意删掉 `identity.userId`，dsh 仍能启动、但无 memory_* 工具）。

#### 15.3.2 `memory_save`

```ts
execute({ content, memory_type = 'fact', domain, privacy = 'normal', ttl_days }) {
  if (!content?.trim()) throw new Error('memory_save: content 不能为空')

  // F2：唯一注入点。用户不可指定 user_id（参数里根本没有这个键）
  const userId = cfg.identity.userId
  if (!userId) throw new Error('memory_save: 缺少 identity.userId，拒绝写入')

  const norm = normalizeContent(content)
  const sha  = sha256Hex(norm)

  // 幂等：同用户同 hash 直接返回既有 id
  const idx = cfg.index.personalPrefix + userId
  const dup = await client.search(idx, {
    query: { bool: { filter: [
      { term: { user_id: userId } }, { term: { content_sha256: sha } }, { term: { status: 'active' } },
    ]}}, size: 1,
  })
  if (dup.hits.length > 0) return { memory_id: dup.hits[0].memory_id, deduped: true, text: '已存在相同内容，未重复写入' }

  const emb = await embed(norm).catch(() => null)        // 降级：向量失败仍写（只走 BM25）
  const kw  = await llmKeywords(norm, cfg).catch(() => [])

  const doc = {
    memory_id: randomUUID(), user_id: userId, content,
    semantic_keywords: kw.join('\n'), embedding: emb,
    memory_type, domain: domain ?? cfg.defaultDomain,
    privacy, promote_state: 'none', status: 'active',
    content_sha256: sha,
    created_at: nowIso(), updated_at: nowIso(),
    expires_at: ttl_days ? addDaysIso(ttl_days) : undefined,
  }
  await client.index(cfg.index.personalPrefix + cfg.identity.userId, doc, { refresh: 'wait_for' })  // writer 凭证

  // F3：不变量断言（防自己写错，不防攻击者——见 §4.4 说明）
  if (doc.user_id !== cfg.identity.userId) throw new Error('memory_save: user_id 注入不一致，已拒绝')

  log({ tool: 'save', user: userId, ms, degraded: !emb })
  return { memory_id: doc.memory_id, deduped: false, degraded: !emb,
           text: emb ? '已保存' : '已保存（向量服务不可用，仅关键词可检索）' }
}
```

> F3 的定位要说清楚：`user_id` 是我们自己注入的，正常永远相等。它的价值是**抓住重构时把注入点改错**，不是防越权（越权防线是 F1 参数里没有该字段 + F2 只从配置取）。

#### 15.3.3 `memory_search`

```ts
execute({ query, scope = 'both', memory_type, domain, time_range, limit = 8 }) {
  const qv = await embed(query).catch(() => null)        // 失败 → 只走 BM25

  const filter = dslFilters({ memory_type, domain, time_range })
  const routes: Hit[][] = []

  const personalIdx = cfg.index.personalPrefix + cfg.identity.userId
  if (scope !== 'team') {
    routes.push(await client.search(personalIdx, bm25(query, filter)))
    if (qv) routes.push(await client.search(personalIdx, knn(qv, filter)))
  }
  if (scope !== 'personal') {
    routes.push(await client.search(team, bm25(query, filter)))
    if (qv) routes.push(await client.search(team, knn(qv, filter)))
  }

  let fused = rrfFuse(routes, cfg.retrieval.rrfK)         // 等级融合，不依赖绝对分
  fused = boostPersonal(fused, 1.2)                       // 个人库贴近当前上下文
  if (margin(fused) < cfg.retrieval.marginFloor) {
    return { hits: [], note: 'low_confidence', text: '没有足够相关的记忆' }
  }
  const hits = fused.slice(0, Math.min(limit, 20)).map(h => projectHit(h, 500))
  return { hits, text: renderText(hits) }
}
```

要点：两路是**独立请求**（`knn` 在 ES 8.x 是顶层参数，不能塞进 `query.bool.should`），融合在应用侧完成。

#### 15.3.4 `memory_update_status`

```ts
execute({ memory_id, action, reason, replacement_memory_id }) {
  const idx = cfg.index.personalPrefix + cfg.identity.userId
  const cur = await client.get(idx, memory_id)   // 404 明确报错
  const patch =
    action === 'supersede'    ? { status: 'superseded', superseded_by: replacement_memory_id }
  : action === 'expire'       ? { status: 'expired' }
  : action === 'mark_private' ? { privacy: 'private' }
  : (() => { throw new Error('memory_update_status: 未知 action') })()

  await client.update(idx, memory_id, { doc: { ...patch, updated_at: nowIso() } })  // partial doc，writer 凭证
  audit({ tool: 'status', memory_id, action, reason, actor: cfg.identity.userId })
  return { memory_id, status: patch.status ?? cur.status, text: '已更新状态' }
}
```

### 15.4 纯函数契约（`fragment.ts`）

```ts
export function normalizeContent(s: string): string   // 去首尾/折叠空白、全角标点转半角；幂等
export function sha256Hex(s: string): string           // node:crypto
export function rrfFuse(routes: Hit[][], k: number): Fused[]
export function margin(fused: Fused[]): number         // top1-top2；<2 条返回 0（不判空）
export function projectHit(hit: Fused, maxChars: number): Projected
export function renderText(hits: Projected[]): string  // 给模型的短文本
```

这些函数不 import dsh 与 ES，**纯函数可单测**——RRF 的单调性、margin 的边界（0 条 / 1 条 / 并列）都在这里钉死。

### 15.5 ES 请求封装与错误映射

| 情况 | 处理 | 给模型的提示 |
|---|---|---|
| 401 | 不重试 | 凭证失效，检查 `identity.readApiKey / writerApiKey` |
| 403 | 不重试 | 权限不足。两种典型：拿个人 key 去写；在 basic license 下建带 `query` 的角色（`non-compliant for field and document level security`） |
| 404 | 不重试 | 索引/文档不存在；索引缺失时提示先跑 `scripts/init-indices.sh` |
| 409 | 重试 1 次 | 并发写冲突 |
| 429 | 退避 200 ms 重试 1 次 | 被限流 |
| 5xx / 超时 | 不重试，明确失败 | ES 不可用，本次记忆操作未生效 |

TLS：`https.request({ ca: fs.readFileSync(cfg.es.caCertPath) })`，**不关 `rejectUnauthorized`**。

### B.1 环境现状（2026-10-25 实测）

- Ollama **0.40.3**，监听 `127.0.0.1:11434`，模型目录 `~/.ollama/models`。
- 两个模型：

  | 模型 | 磁盘 | 维度 | family |
  |---|---|---|---|
  | `nomic-embed-text` | 274 MB | 768 | nomic-bert |
  | **`bge-m3`** | **1158 MB** | **1024** | bert |

- **daemon 已改为无代理启动**：旧启动命令写死 `HTTPS_PROXY=127.0.0.1:7897`，Clash 未运行时 `ollama pull` 必报 `proxyconnect ... connection refused`（而 shell 直连 registry 是 HTTP 200）。现行启动命令：

  ```bash
  setsid nohup env -u HTTPS_PROXY -u HTTP_PROXY -u ALL_PROXY \
    OLLAMA_MODELS=/home/user/.ollama/models \
    /home/user/.local/ollama/bin/ollama serve >> /home/user/.ollama/ollama.log 2>&1 &
  ```

- ⚠️ ollama **不在** `crontab -l` 里，机器/进程重启后不会自愈，要手动拉起上面这条。
- ⚠️ 停它**不要**用 `pkill -f 'ollama serve'`：该模式会匹配到执行脚本自己的 `bash -c` 命令行（脚本文本里含这个串）→ 把自己 SIGTERM 掉、后续步骤静默不执行。用 `pkill -x ollama`。

### B.2 embedding 定性实测（供 M3 参考）

- 维度：`bge-m3` = **1024**，`nomic-embed-text` = 768。
- CPU 编码延迟：**约 0.20 s/条**（3 次 0.197 / 0.198 / 0.209 s，含 HTTP 开销，短中文句）。写入每条约 1 次、检索 1 次/query，成本可接受。
- 换说法召回（4 条记忆 × 5 个 query）：**4/4 top1 命中**；但绝对相似度与噪声重叠，阈值只能用 margin（结论见 §8.4）。

### B.3 Elasticsearch 部署实测（2026-10-25）

| 项 | 结果 |
|---|---|
| 镜像 | `docker.elastic.co/elasticsearch/elasticsearch:8.19.23` |
| license | **basic**（免费） |
| IK 插件 | `analysis-ik 8.19.23`；`_analyze` 正确切出 `win_price` / `win_price_practical` |
| 集群 | 单节点 green，replicas=0 |
| 索引 | `personal_memory_xqh`（继承模板：16 字段、dims 1024、ik_max_word）与 `team_knowledge` |
| 隔离验证 | `scripts/verify-isolation.sh` **11/11 PASS** |
| JVM | `-Xms2g -Xmx2g`（宿主 15 GiB / 可用 12 GiB） |
| 入口 | `127.0.0.1:9200`，自签 CA（SAN: `127.0.0.1`、`localhost`） |

**踩到的五个坑**（全是硬错误，不是偏好）：

1. **DLS 不可用**：建带 `query` 的角色 → `403 current license is non-compliant for [field and document level security]`。basic license 没有 DLS，方案改 per-user 索引（D5）。
2. **证书缺 SAN**：certutil 默认 CN=instance 且无 SAN → `certificate subject name 'instance' does not match target host name '127.0.0.1'`。必须 `--name --dns --ip`。
3. **p12 密码没传给 ES**：`keystore password was incorrect`。compose 必须显式传 `*.ssl.keystore.password` 与 `truststore.password`。
4. **`update` 不是合法 privilege**：400 `unknown index privilege [update]`，用 `index`（已含 update/upsert）。
5. **用户默认不能建 API key**：403，需绑 `manage_own_api_key`。

### B.4 其余

- 本机 DSH 为 web profile，插件安装走 `dsh plugin --profile web add file:<路径>`；插件改动需重启或同步产物后才生效。
- 已有 Docker 环境；ES 暴露端口建议仅绑回环，经 DSH 插件从本机访问。

## 附录 C：Markdown 层为何保留（可选项）

纯 ES 单轨的代价是“人不可读、Git 不可审计、迁移绑定集群”。保留 md 镜像层的最低成本做法：

- 团队库按 `domain` 定期导出为 `knowledge/<domain>.md`，每条带 `source_user` / `promoted_at` / `doc_id`；
- md 只做**只读视图 + 备份**，不反向写 ES（避免双写漂移）；
- 若确实需要人工编辑，走“改 md → 脚本 diff → 生成 ES 更新补丁 → 人工确认”的流程，而不是让 md 和 ES 互相同步。
