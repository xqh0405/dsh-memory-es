## 阶段 0 · 地基（不改任何线上行为）

没有基线就没有「优化」，只有「凭感觉改」。这一阶段全部是零行为变更。

### 0.1 检索评测集

- 新增 `tests/eval/queries.jsonl`，每行：`{ "id", "query", "expect": ["<memory_id>"], "kind": "single|paraphrase|exact|noise" }`
- 起步 30 条，四类各若干：

  - `paraphrase`：换说法（验证向量路）
  - `exact`：接口名/错误码/路径（验证 BM25 路）

- 新增 `scripts/eval-search.ts`：直接调 `searchMemories`，输出 recall@5 / MRR@5 / 空结果率 / `low_confidence` 率，写 `tests/eval/baseline.json`
- **验收**：`npm run eval` 能跑通，基线归档

> 这一步需要人抽检口径：我先从 MEMORY.md 反向生成 30 条候选，你抽检 10 条确认「期望命中」标得对。

#### 0.1 结果（2026-10-29 已完成）

评测集 30 条（single 8 / paraphrase 8 / exact 8 / noise 6），全部连真实个人库（268 条）。

**口径 A：不判空（`--margin-floor 0`，衡量排序质量）**

| kind | n | hit@1 | hit@5 | MRR |
|---|---|---|---|---|
| single | 8 | 100% | 100% | 1.000 |
| paraphrase | 8 | 88% | 88% | 0.875 |
| exact | 8 | 75% | 100% | 0.844 |
| noise | 6 | — | — | 误报 6/6（不判空必然如此） |

**口径 B：生产默认（`--margin-floor 0.05`）**

| kind | n | hit@1 | hit@5 | low_conf |
|---|---|---|---|---|
| 全部 | 30 | **0%** | **0%** | **30/30** |

**结论：排序能力本身是好的（hit@5 96%、MRR≈0.91），但置信判空把 73% 的查询直接杀死，包括 8/8 的 single（top1 就是正确答案仍然返回空）。**

根因数据：

| 指标 | single | paraphrase | exact | noise |
|---|---|---|---|---|
| kNN top1 | 0.804~0.888 | 0.799~0.835 | 0.753~0.851 | 0.768~0.797 |
| margin（top1−top2） | 0.015~0.095 | 0.002~0.073 | 0.001~0.066 | 0.002~0.021 |
| BM25 top1 | 30.8~53.9 | 20.5~37.0 | 13.9~46.2 | 10.3~25.8 |

margin 中位数 **0.0208**，22/30 低于 0.05。

**这不是 bug，是参数标定失效**：`0.05` 来自文档 §8.4「三条记忆」时的实测（换说法 margin=0.0516）。候选池从 3 条涨到 268 条后，top2 必然逼近 top1，margin 整体下移——**门槛必须随库规模重新标定**。

## 阶段 0.5 · 置信判定重构（插队，优先级最高）

> 原计划的阶段 1（兄弟路）顺延到这一步之后。理由：它修的是「明明有答案却返回空」，影响面 100%；兄弟路只影响少数换说法场景。

四类数据说明**没有单一阈值能同时做好**：真命中与噪声的 kNN top1 在 0.75~0.80 区间重叠，BM25 也有重叠（paraphrase 最低 20.5 < noise 最高 25.8）。任何静态阈值都会误杀或误放。

**待定方案（需拍板，三选一）：**

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. 下调门槛 | `marginFloor` 0.05 → 0.005~0.01 | 改动最小，一行配置 | 阈值仍随库规模漂移；噪声误报增加 |
| B. 分层判据 | top1 < 0.65 直接空；0.65~0.80 要求 margin≥0.02 或 BM25≥25；≥0.80 直接返回 | 用绝对分兜底，噪声与真命中分得开一些 | 中间区仍有边缘误杀；三个常量都要标定 |
| C. 分位数自适应 | 定期用 N 条随机 query 采样 top1 分布，取下分位（如 P15）作门槛 | 随库规模自动调整，不用手调 | 多一个离线任务；冷启动需要样本 |

**倾向 B**：`margin` 只做中间区的辅助，绝对相似度做主线；它能在不引入新任务的前提下，把这批数据从「全杀」救回「只杀明显无关的」。但 B 的三个常量要在真实数据上跑一遍验证，不能拍脑袋。

#### 0.5 试算结果（2026-10-29，`npm run eval:thresholds`）

网格扫描 3000+ 组（tLow × tHigh × mMin × bMin），帕累托前沿只剩两个点：

| 参数 | 真命中返回 | 误杀 | noise 误放 |
|---|---|---|---|
| tLow=0.75 tHigh=0.78 mMin=0.015 bMin=13 | 24/24 | 0 | 2（q25、q30） |
| tLow=0.75 tHigh=0.80 mMin=0.025 bMin=30 | 23/24 | 1（q20） | 0 |

**关键发现：存在「不可分对」。** q20（真命中，`lot.bd_write_sync`）在三个维度上**全部劣于** q25（ZooKeeper 噪声）：

| | top1 | margin | bm25 top1 |
|---|---|---|---|
| q20（该留） | 0.7663 | 0.0014 | 13.9 |
| q25（该走） | 0.7971 | 0.0208 | 13.6 |

→ 由这三项构成的任何阈值都判不出「q20 留、q25 走」：想误杀 0 必然误放，想误放 0 必然误杀 q20。这不是调参问题。

**两个必须写下来的警告：**

1. **样本不足，参数贴边**：noise 只有 6 条，两个前沿点都贴着数据边界（bMin=13 vs q25 的 13.6；bMin=30 vs q30 的 25.8）。这是过拟合的典型形状，**不能据此定生产常数**；noise 扩到 20 条以上要重跑。
2. **q20 的根因不是阈值**：它是 exact 类（含下划线标识符），BM25 只有 13.9——标识符被 IK 切碎、又被口语部分（「已经做到哪一步」）稀释。阈值救不了，需要**标识符精确匹配子字段**（keyword + standard 分析器）单独提权。记为后续优化项。

#### 新增方案 D：低置信「返回 + 标注」，而不是「返回空」

建议与 B 叠加，而不是二选一。

理由：记忆检索的失败模式是「模型以为没记过，于是凭印象编」；返回几条不相关的记忆，模型看内容就知道不相关，代价小得多。现状 `low_confidence → hits: []` 把信息全部丢掉了。

- 粗粒度：`note=low_confidence` 但照常返回 hits，`text` 里加一句「相关性较低，谨慎使用」（约 10 行）
- 细粒度：`Projected` 加 `confidence`，逐条标注（改动大，暂不做）

B 的分层阈值仍有价值——用来挡「top1 < 0.65 的明显无关」，而不是用来决定「返回几条」。

**落地顺序**：① 改 note 语义（返回 + 标注）→ ② B 取宽松档 `tLow=0.60 / tHigh=0.80 / mMin=0.01 / bMin=20` → ③ noise 样本扩到 20 条后重跑试算再收紧。

**验收**：口径 B 下 single/paraphrase 的 hit@5 ≥ 90%，且不再出现「全空」；noise 允许少量误放（有标注兜底）。

#### 0.5 实现结果（2026-10-29 已完成）

改造前 vs 改造后（30 条评测集，真实个人库 268 条）：

| 指标 | 改造前（`marginFloor=0.05`） | 改造后（分层 + 返回标注） |
|---|---|---|
| single hit@5 | 0% | **100%** |
| paraphrase hit@5 | 0% | **88%** |
| exact hit@5 | 0% | **100%** |
| 真命中能拿到结果 | 0 / 24 | **24 / 24** |
| noise 被标注低置信 | —（全部空返回） | **6 / 6** |
| noise 漏标（当正常结果给出） | — | **0** |
| 真命中被误标 | 24 / 24 | **1 / 24**（q20） |

**最终参数**：`floorTop1=0.60`、`autoPassTop1=0.80`、`minMargin=0.025`、`minBm25=30`。

实现要点：

- `judgeConfidence` / `DEFAULT_CONFIDENCE` 在 `search.ts` 里导出；**config 的 schema 默认值直接引用它**，杜绝「代码默认」与「配置默认」两处漂移
- 低置信不再 `hits: []`：照常返回，`text` 前置一句「相关性偏低，谨慎采信；无关时当作没有检索到」
- **margin 不再跨库混算**：`scope=both` 时置信信号只取个人库（原实现把两库 kNN 分数混在一起排序，库不同、候选池不同，margin 无意义）
- **只有一条候选时不判窄**：没有第二名就没有「区分度」可言，否则库里只存一条相关记忆时永远被判低置信
- **降级（无向量）不判低置信**：没有依据就不判
- 埋点 `low_confidence` 记实际返回条数（原为 0），空结果率与低置信率才分得开

已知遗留：q20（`lot.bd_write_sync`）被误标，根因是标识符被 IK 切碎、BM25 仅 13.9，**不是阈值能解决的**——归到阶段 1 的「标识符精确匹配子字段」。

**参数贴边警告仍然有效**：noise 只有 6 条，`minBm25=30` 贴着 q30 的 25.8。noise 扩到 20 条以上必须重跑 `npm run eval:thresholds`。

## 阶段 1 · 第三路召回（不动 mapping，纯检索层）

调研里「同 topic_key 兄弟条目」是性价比最高的一条，因为它用 ES 的 `terms` 查询就能实现，不碰图、不碰模型。

- `src/memory/search.ts`：BM25 结果取前 5 条的 `topic_key`（跳过空值与 `general`）→ 发一次 `terms` 查询取同 topic 的其他条目（上限 20 条）
- 三路进 `rrfFuse`：`[bm25, knn, siblings]`，与现有两路同权重
- 开关 `ranking.siblingRoute`，默认 `false`
- **验收**：开关两跑评测对比，`recall@5` 不下降、`noise` 类不误报；关掉后结果与阶段 0 基线一致

#### 阶段 1 实现结果（2026-10-29 已完成——标识符子字段）

先做了「标识符精确匹配」，把 q20 的遗留一起解决；`topic_key` 兄弟路留到下一步。

**字段**：`content_exact`（`text` + `standard` 分析器，与正文同源）。为什么用 standard：UAX#29 在字母之间不因 `.`/`_` 断词，`lot.bd_write_sync` 保留为单个 token；中文仍逐字可搜，phrase 一样能用。实测 `match_phrase content_exact:"lot.bd_write_sync"` 命中 1 条。

**查询侧**：`extractIdentifiers()` 从 query 里挑标识符（最多 5 个），在 `bm25Body` 里生成 `should: [match_phrase content_exact^5]`。`should` 不命中也不影响召回（`must` 里已有主查询）。

**效果**：

| 指标 | 阶段 0.5 之后 | 阶段 1 之后 |
|---|---|---|
| q20 的 BM25 首条分 | 13.9 | **38.0**（越过 `minBm25=30`） |
| exact 类被标低置信 | 1 | **0** |
| noise 误放 | 0 | **0** |
| 排序名次 | — | 与基线逐条一致（RRF 只用名次） |

**踩到的坑（值得记住）**：第一版规则把「全大写缩写」也算标识符，于是 `Kubernetes Ingress 的 TLS 证书怎么续期` 提取出了 `TLS`——而库里真有宝塔 SSL 证书的记忆，`match_phrase` 命中后 boost 5，把这条噪声查询的 BM25 从 25.8 顶到 **65.6**，直接越过门槛放行。

修法不是维护黑名单（会漂移），而是**要求缩写必须含数字**（`E101`/`PM2` 算，`TLS`/`CLI`/`API`/`TTL` 不算）。修完 q30 的 BM25 回落到 27.1，噪声重新被正确标注。

**迁移（顺序不能反）**：

```bash
# 1) 先加字段并回填（旧代码不写该字段，无害）
ES_URL=... ES_CA=... ES_USER=... ES_PASS=... scripts/migrate-identifier-field.sh xqh
# 2) 再更新插件代码
```

为什么不能反：`dynamic: strict` 下，索引没有 `content_exact` 时，新代码写文档会直接 400。

已验证幂等：复跑 `total=0 updated=0`。个人索引与 `team_knowledge` 都已加字段。`scripts/init-indices.sh` 的模板也同步了，新用户的索引会自动继承。

**部署注意**：线上跑的是旧 `lib`，要让改动生效需要重新构建 + 重启 dsh-web；且**先迁移、后重启**。

## 阶段 2 · 排序信号（mapping 增量，风险最低的一次加字段）

### 2.1 加字段

新增 `scripts/migrate-ranking.sh`（照 `migrate-s9.sh` 的模式：改模板 + 对已存在索引 `PUT _mapping`）：

| 字段 | 类型 | 用途 |
|---|---|---|
| `importance` | keyword | critical / normal / low |
| `hit_count` | integer | 被检索命中次数 |
| `last_hit_at` | date | 最近一次命中时间 |

⚠️ **`scripts/init-indices.sh` 必须同步改**，否则新用户的索引模板不带这些字段（`dynamic: strict` 下写入直接 400）。

### 2.2 写入 importance

- `src/memory/save.ts`：schema 加 `importance`（枚举校验，默认 `normal`）
- 提示段加一句：`critical` 只给「不看就会做错」的规则，别滥用
- **验收**：单测覆盖非法值与默认值；旧调用方不传也能写

### 2.3 热度回写

- 检索命中后 `void recordHits(ids)`：**不 await**、失败只记日志、不影响返回
- 用 `_bulk` 或 `update_by_query`？**用 `_bulk`（一批 ≤50 条）**，避免 `update_by_query` 扫全索引
- **验收**：`search` 的 p95 不因回写变慢（回写走 fire-and-forget，压测对比）；连跑 5 次同一 query，`hit_count` 单调上升

### 2.4 乘子接入

在 `src/fragment.ts` 的 `mergeScopes` **之后**统一乘，绝不混进 RRF 分（尺度差一个数量级）：

```
factor = 1
       + importanceWeight × (imp_value - 1)       // critical=1.1, normal=1, low=0.9
       + hitBoost × log1p(hit_count) / 10
       + recencyWeight × exp(-Δdays / halfLife)
```

- 三项系数全部来自 `ranking` 配置，默认 0 → 行为不变
- **验收**：系数为 0 时与基线逐位一致；单项开启时只影响目标维度

#### 阶段 2 实现结果（2026-10-29 已完成）

**字段**（`scripts/migrate-ranking-fields.sh`，个人索引 + `team_knowledge` 都已加）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `importance` | keyword | critical / normal / low |
| `hit_count` | integer | 被检索命中的次数 |
| `last_hit_at` | date | 最近一次命中时间 |

**不需要回填**：代码把缺失值当 `normal` / `0` / `null`，老文档天然参与排序。

**乘子公式**（`fragment.ts` 的 `applyRanking`，作用在 `mergeScopes` 之后）：

```
factor = 1
       + importanceWeight × (imp − 1)          // critical 1.1 / normal 1.0 / low 0.9
       + hitWeight × log1p(hit_count) / 10
       + recencyWeight × exp(−ageDays / halfLife)
```

默认值：`importanceWeight=1`、`hitWeight=0.2`、`recencyWeight=0.1`、`recencyHalfLifeDays=30`。三项都可归零关闭（全零时函数直接返回原数组）。

**为什么 importance 只给 ±10%**：它是**微调**，不是主导。否则排序会退化成「按标签排」，真正相关的那条被一个 critical 标签压下去。

**命中回写**：

- 用 `_update` + painless 脚本 `hit_count += 1`（**不是读-改-写**，并发检索会丢更新）；
- fire-and-forget，失败只打日志，绝不影响检索返回；
- 不配 `hitRecorder` 就不回写（测试与脚本默认无写流量）；
- 回写用文档的 ES `_id`（`merged[].id`），不是 `memory_id`——两者不是一回事。

**验证**：

| 项 | 结果 |
|---|---|
| 评测排序名次 | 与基线**逐条一致**（默认值不劣化） |
| 生产口径 | single 100% / paraphrase 88% / exact 75%(hit@5 100%) / noise 误报 0、低置信 6 |
| 单测 | 255 pass / 0 fail，含「critical 在编排层反超 1.5% 分差」的接线验证 |

**已知边界**：`hitWeight` 与 `recencyWeight` 都依赖真实使用量，现在 `hit_count` 全为 0、`last_hit_at` 全空，所以这两项目前**没有任何实际影响**——上线后随检索逐步累积。这也是为什么评测显示「名次一致」：不是没生效，而是信号还没产生。

## 阶段 3 · 时间有效性（字段已有，缺写入与过滤）

### 3.1 检索过滤

`src/es/dsl.ts` 的 `buildFilters` 加两条：

```
must_not: { exists: { field: "superseded_by" } }
```

- 注意：ES 里「字段没值」可能是「不存在」也可能是 `null`，**必须用 `must_not exists`**，不能写 `term: superseded_by: null`
- `expires_at` 同理：`must_not: { range: { expires_at: { lt: now } } }`（写法需实测确认，别想当然）

### 3.2 个人库自动 supersede

- `consolidate/` 的冲突分支：个人库命中冲突 → 写 `status=superseded` + `superseded_by=<新 id>` + `superseded_at`；**团队库仍走 pending**（错误结论的代价太高）
- 不物理删除（调研结论）
- **验收**：造 3 组「旧结论 → 新结论」，旧条不出现在 `memory_search`，按 id 仍可查；撤回动作进 `memory_audit`

### 3.3 时间点回溯（可选，加分项）

#### 阶段 3 实现结果（2026-10-29）

**3.1 检索过滤：已完成**

`buildFilters` 末尾加两条兜底过滤（`freshOnlyFilters`，测试与实现共用同一份定义）：

- `must_not exists superseded_by` —— 被取代的条目不再返回；
- `must_not range expires_at < now` —— 过期条目不返回（字段不存在时 range 不匹配，天然保留）。

**为什么用 `must_not exists` 而不是 `term: null`**：字段缺失与字段为 `null` 在 ES 里是两回事，前者才是「没有值」的稳妥判据。

**端到端验证**（临时探针文档，验证后已删）：同一条 query，带过滤命中 7 条、去掉过滤 8 条——差的正是那条标了 `superseded_by` 的文档，证明是「被过滤」而不是「不存在」。

**3.2 自动 supersede：否决（数据否决的，不是设计否决）**

`scripts/supersede-scan.ts` 对 267 条真实数据跑 dry-run，出 **39 对候选，全部是误判**。

典型例子：

- 「DSH skill 子系统」vs「~/.dsh/skills 已从 8 个扩到 24 个」→ 因为一边有「要」另一边有「不要」就判成相反结论；
- 「jbp 安全组规则」vs「lottery-cloud 生产拓扑」→ 同上。

**根因**：`detectContradiction` 只做极性词对匹配，**没有「是否在讲同一件事」的约束**。整理任务里没炸，是因为调用前有 `decision.verdict === 'merge_candidate'`（高相似 + 同 `topic_key`）这道前置门；而 `topic_key` 在库里几乎全空（16/267），单独跑冲突扫描时这道门不存在。

**如果按原计划打开自动 supersede，会误杀 39 条记忆。**

处置：

- 脚本改成**必须逐条点名**才写：`--apply --older <memory_id>`，批量写入在代码层被拒绝；
- 保留 `superseded_at` 字段（日期），为将来的人工/半自动路径留位置；
- 自动部分与阶段 1b 是同一个阻塞点：**先有可复用的主题粒度，才谈得上「同一主题的相反结论」**。

**3.3 时间点回溯：未做**（`as_of` 依赖语义化的失效判定，先搁置）

## 阶段 4 · 从 LivingMemory 提取的两项（2026-10-29 已完成）

对照仓库：`lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory`（397 stars，AGPL-3.0）。
它的记忆原子模型给了两个可直接迁移的机制。

### 4.1 按 memory_type 的半衰期

原来所有记忆统一 30 天半衰期——对 `task_progress` 太慢、对 `fact`/`decision` 太快。

`fragment.ts` 新增 `MEMORY_TYPE_HALF_LIFE_DAYS`：

| 类型 | 半衰期 | 理由 |
|---|---|---|
| `decision` | 365 天 | 用户定下的口径，一年内基本不变 |
| `fact` | 365 天 | 工程事实，确认过就长期成立 |
| `context` | 180 天 | 项目/环境背景，半年内仍有效 |
| `preference` | 90 天 | 会变，但不像进度按周过期 |
| `task_progress` | 14 天 | 两周内还有意义 |
| （未列出的类型） | `recencyHalfLifeDays` 兜底 | 默认 30 |

**为什么不照抄它的数字**：LivingMemory 的 TTL 描述的是「从对话自动抽取的原子」的寿命（factual 180 天、planned 2 天、preference 60 天），而我们的记忆是**模型显式保存、人确认过的稳定事实**，语义更重。照抄会把正当的知识提前衰减掉。

### 4.2 访问强化延长寿命

它把 TTL 乘 `(1 + min(0.5, count × 0.1))`。我们照此实现，但作用在**半衰期**上：

```
halfLife = 类型半衰期 × (1 + min(reinforcementCap, hit_count × reinforcementPerHit))
```

默认 `reinforcementPerHit=0.1`、`reinforcementCap=0.5`（最多延长 50%，避免老条目「越用越不朽」）。

与已有的 `hitWeight × log1p(hit_count)/10` 是**两个维度**：那个是「排得更靠前」，这个是「老得更慢」。

### 验证

| 项 | 结果 |
|---|---|
| 单测 | **258 pass / 0 fail**，新增 3 例（类型差异、强化延寿、封顶） |
| 评测排序名次 | 与基线**逐条一致** |

名次没变不是没生效——`recencyWeight` 只有 0.1，而库里 269 条中 250 条是 `context`（半衰期同为 180 天），类型差异在现有数据上几乎不产生区分度；`hit_count` 又全是 0。真正会改变排序的是**上线后访问量积累**。若要把时间因素放大，调 `ranking.recencyWeight` 即可（但会削弱「旧而相关」的条目，不建议超过 0.2）。

### 4.3 agreement_bonus 的 A/B 结论：**不启用**（2026-10-29 实测）

`rrfFuse` 增加可选的两路一致加成：`fusedScore × (1 + bonus × (1 − rankGap/span))`，只对「两路都命中」的条目生效。用评测集扫了四档：

| bonus | paraphrase hit@1 | paraphrase MRR | exact MRR |
|---|---|---|---|
| **0（默认）** | **88%** | **0.875** | **0.844** |
| 0.1 | 75% | 0.813 | 0.844 |
| 0.2 | 75% | 0.813 | 0.838 |
| 0.4 | 75% | 0.813 | 0.838 |

**没有提升，反而让 paraphrase 的 hit@1 掉了 13 个百分点。**

原因：换说法的查询里，正确答案往往**只被向量路命中**（字面不同），而「字面匹配但意思不对」的条目才被两路同时命中。agreement bonus 恰好把后者顶上来、把正确答案挤下去。

这条实验反过来印证了阶段 2 的选择：**用乘子而不是加权和**是对的——相关性必须是硬门槛，否则「两路都命中」这种间接信号会盖过真正的相关度。

代码保留（`ranking.agreementBonus`，默认 0），因为它对「两路都命中且都靠前」的场景仍有理论意义，只是在本数据集上被证伪；默认关即无影响。

### 4.4 生命周期：做到归档为止，**不做物理删除**（用户 2026-10-29 定调）

`memory_update_status` 补齐两个动作：

| action | 行为 |
|---|---|
| `archive` | `status=archived`，移出检索，仍可按 id 查回 |
| `restore` | 置回 `active`，**并清 `superseded_by`**（否则检索的 `must_not exists` 仍会挡住它） |

**不提供 `purge`**，理由三条：

1. 审计要能回答「当时为什么这么定」——旧结论本身就是知识；
2. 插件在结构上没有删除能力：`EsClient` 根本没有 `delete` 方法（2026-10-29 核实）；
3. 唯一会物理删除的是运维脚本（`prune-audit.sh` 清审计日志、`init-*.sh` 清探针文档），与记忆正文无关。

所以「遗忘」在本插件里**永远是可见性变化，不是销毁**。

## 阶段 5 · 联结与激活（设计说明）

> 勾选清单在 [README「待开发」](../README.md#待开发勾选进度)。这里只记**为什么这么做**与**边界条件**。

**为什么排在情绪与自我迭代之前**：它是唯一能用现有评测集直接量化的一层（`tests/eval/queries.jsonl` 的 single / paraphrase 两类会直接反映扩散激活是帮忙还是添乱）。情绪和自我迭代的收益没有现成判据，必须先有稳定的排序基线。

**为什么 `activation` 不合并进 `hit_count`**：两者语义不同。

| 字段 | 语义 | 更新时机 | 是否有上界 |
|---|---|---|---|
| `hit_count` | 被命中过多少次（计数） | 每次命中 +1 | 无，靠 `log1p` 压缩 |
| `activation` | 当前有多"热"（强度） | 命中提升、时间衰减 | 有封顶 |

混成一个字段会让「一周前被命中 100 次的条目」和「昨天被命中 1 次」无法区分——而这正是活跃度要表达的东西。

**为什么 `α` 默认 0**：扩散激活在单跳上容易把错误邻居带进来。默认关 = 合并前后逐条一致，出问题能一键退回，符合本仓库「新能力默认关」的既有原则。

**边界条件（必须挡）**：

1. **边数膨胀**：每条记忆最多保留 `relatedTopK`（建议 5）条边，按权重截断；否则 268 条库会生成 O(n²) 条边。
2. **自环与重复边**：写入前按 `id` 去重，禁止自指。
3. **只对 `active` 建边**：`archived` / `superseded` / 过期的条目不应成为邻居，否则扩散激活会把已失效的结论重新拉回。
4. **命中回写只写 `active`**：`must_not` 挡掉的条目不能因「被算过分」而升温。

**回滚**：`α=0` 且不写 `related` 即回到阶段 4 的行为；`activation` 作为纯新增字段，旧代码读不到也不受影响。

#### 5.1 实现结果（2026-10-30）

| 项 | 结果 |
|---|---|
| mapping | `personal_memory_xqh` 与 `team_knowledge` 两处 `PUT _mapping` 成功（`related: object/enabled:false`、`activation: float`） |
| 既有文档 | 279 条，读回时两个字段缺失——**不回填**，代码按 `related=[]` / `activation=0` 处理 |
| typecheck | 通过 |
| 单测 | 264 pass / 0 fail / 7 skipped |
| 评测 | 30 条**逐条名次与基线完全一致**（gate=off） |

**踩到的坑**：`embedding.url` 指向 `127.0.0.1:11434`，本机 ollama 没在跑时 30 条会全部走降级（只走 BM25），paraphrase 的 hit@1 从 88% 掉到 50%。**那不是回归，是环境问题**——看到"⚠️ 走了降级"就先起 ollama 再跑，别拿降级数字和基线比。

#### 5.2 实现结果（2026-10-30）

**实现**：`src/memory/edges.ts`（纯函数 `pickNeighbors` / `mergeEdges` / `readEdges`）+ `save.ts` 的 `linkNeighbors`（best-effort）+ `config.edges` 四项（`enabled` / `topK=5` / `minScore=0.55` / `maxScore=0.85`）。

**一个前提修正**：原计划写的「复用去重那批 kNN 候选」在代码里不存在——`memory_save` 的去重是 `content_sha256` 精确查（`dedupeBody`），没有相似度候选池。所以建边改成**写入后单独发一次 kNN**（多 2 个 RTT）。这是本阶段唯一的额外成本。

| 项 | 结果 |
|---|---|
| 新增单测 | 18 例（纯函数 16 + 端到端 5，含失败不影响保存） |
| 全量测试 | 282 pass / 0 fail / 7 skipped |
| 真实库验收 | 3 条触发 15 条边，**无自环**、权重全在 `[0.55, 0.85)` |
| 幂等 | 重复保存同内容 → `deduped=true`，`related` 逐字节不变 |
| 回归 | 30 条评测**逐条名次与基线一致** |

**观察**：三条测试记忆之间**没有**互相建边，边都指向历史记忆。原因是它们内容太像（相似度落进判重带或被更相似的历史条目挤掉 topK）。这说明「相关但不重复」需要真实的内容差异，不是设计缺陷——但 5.3 上扩散激活前值得用真实数据看一眼边的分布，别拿测试数据下结论。

**精度边界修复（同日发现）**：`pickNeighbors` 原来用**原始分数**判区间、用 `round4` 后的值存权重 → `0.84996` 通过过滤却被存成 `0.85`，在判重带边界上冒充越界（实测 3 条）。改为「先舍入再判区间」，存进去的值才是判定依据；补了回归测试。

**历史回填（5.3 的前置）**：5.2 的建边只挂在 `memory_save`，历史记忆一条边都没有——实测 active 279 条里有边的 **0** 条。用 `.dsh-smoke/backfill-edges.ts --apply` 回填：写入 270、无合格邻居跳过 8、失败 0。

| 指标 | 值 |
|---|---|
| active 有边 | 270 / 279（96.8%） |
| 边总数 | 1333（平均出度 4.71，最大 5） |
| 自环 / 悬空边 | 0 / 0 |

#### 5.3 实现结果（2026-10-30）

**实现**：`fragment.ts` 的 `spreadActivation`（纯函数）+ `RankingConfig.activationAlpha`（默认 0）+ `search.ts` 在 `mergeScopes` 之后、`applyRanking` 之前接入。`edges.ts` 从 `memory/` 移到 `src/` 顶层——它是纯函数契约，和 `fragment.ts` 同层。

**一个刻意的限制**：邻居只认**本次结果集里的**，不做二次召回。做二次召回会让候选池变大，同时抬高 hit 和噪声，掩盖真实收益；不做反而能干净地回答「借邻居的分到底有没有用」。

**扫描结果**（30 条查询，同一份评测集）：

| α | hit@1 | hit@5 | MRR | 误报 | 与 α=0 相比 |
|---|---|---|---|---|---|
| 0 | 21 | 23 | 0.906 | 6 | — |
| 0.02 | 20 | 23 | 0.885 | 6 | 1 条变差 |
| 0.05 | 19 | 23 | 0.865 | 6 | 2 条变差 |
| 0.1 | 16 | 23 | 0.788 | 6 | 5 条变差 |
| 0.15 | 16 | 23 | 0.788 | 6 | 5 条变差 |
| 0.2 | 15 | 23 | 0.751 | 6 | 7 条变差 |
| 0.3 | 14 | 23 | 0.731 | 6 | 8 条变差 |

**没有任何一条查询变好，全部变差**；hit@5 不变（借分只改前列顺序，不改变"进不进 top5"）。

**原因**：RRF 分数本身很紧（实测 top1 与 top2 的 margin 中位数约 0.02），而扩散是**加法**——任何在 0.02 量级上的扰动都会直接换位。而且被借分的那条往往不是最相关的：它的邻居也在候选里，只能说明"同一簇都相关"，不说明它更贴题。

这与 [4.3 agreement_bonus](#43-agreement_bonus-的-ab-结论不启用2026-10-29-实测) 是同一类结论：**间接信号（两路一致 / 邻居也在）不能盖过直接相关性**。所以按同样的处置：**实现保留、默认 0、不启用**。

**回滚/开关**：`ranking.activationAlpha`，0 即完全关闭（逐条原样返回）。

## 阶段 6 · 情绪维度（设计说明）

**为什么状态独立成索引**：一次心情是一个**短期**状态（半衰期按小时计），而记忆是长期事实。把状态写进 `personal_memory_<uid>` 会让它出现在检索结果里，且每次情绪变化都会污染记忆库的统计口径。

**为什么 `β` 默认 0**：情绪一致召回（mood-congruent recall）有一个已知反效果——**放大偏差**。心情差时更容易想起负面记忆，形成自我强化的回路。所以：

- 默认关，先只看不排序；
- 开启后 `β` 上限建议不超过 `0.15`，且**只做正向提权，不做负向压制**；
- 每次开 β 都要跑一遍评测，确认 `noise` 类误报率没有上升。

**为什么情绪不能由模型自述驱动**：模型会为了迎合用户而永远"开心"。状态只能由事件改（工具失败/超时、用户明确夸奖或批评），模型自述一律丢弃并记审计。

**回滚**：`valence` 为空即不参与排序；关掉状态索引读取即回到阶段 5 行为。

## 阶段 7 · 自我迭代（设计说明）

**为什么必须人在环**：人格级改写是唯一不可逆的改动。LLM 自我改写有三类已知失败：漂移（逐渐偏离初始设定）、迎合（向用户偏好坍缩）、崩塌（规则互相冲突后失去一致口吻）。所以提炼产物一律先进 pending 队列，**不直接进检索**。

**为什么复用现有审核台**：S9 的 `review.ts` 已经有 pending 闸、审计、`superseded_by` 链。造第二套审批流程会产生两份互相不知道的状态——这正是本仓库反复避免的那种漂移。

**锚点保护**：`identity` 条目里挑出一组标 `anchor: true`（名字、称呼、底线、语言偏好这类不该被"优化"的东西）。提炼任务命中锚点时拒绝写候选，并记一条审计说明为什么拒。

**与 `memory_promote` 的分工**：`promote` 是「这条个人记忆值得进团队库」；自我迭代是「这条候选 traits 值得成为我的自述」。两者共用队列机制，但审核口径与目标索引不同，不要合并成一个动作。

**回滚**：identity 走 `superseded_by` 链，回滚 = 把旧版本 `restore` 回 `active` 并清链（与 4.4 的实现一致）。

## 不做清单（增补）

除 [原清单](#不做清单复述避免跑偏) 外，阶段 5~7 追加四条：

1. **不上图数据库**：`related` 用 ES 的 `nested` 或 `keyword` 数组就够，几万条以内不需要 Neo4j。附录已论证分图方案的四条硬限制。
2. **不做自动替代（auto-supersede）**：阶段 3.2 已实测否决，自我迭代同样不例外。
3. **不做情绪驱动的负向压制**：只提权，不降权，避免自我强化回路。
4. **不让人格文本进记忆库**：人格归上层插件，记忆库只存"发生过什么"。两份真相是这类系统最常见的坏味道。

#### 6.1 / 6.3 实现结果（2026-10-30）

**6.1 记忆效价**：`memory_save` 增加两个可选参数 `valence`（-1~1）/ `arousal`（0~1）。

- **不给就不写字段**，而不是写 0：`缺失` 表示"这条没标情绪"，`0` 表示"中性"，两者在 6.3 里行为不同（前者不参与、后者会参与）。
- 越界直接拒绝，不静默截断：`valence=1.5` 抛错，而不是夹到 1。静默截断会让调用方以为标成功了。
- 参数表用 `number` 而不是枚举：情绪是连续量，枚举会诱使人乱挑一档。

**6.3 情绪一致召回**：`score × (1 + β × 相似度)`，相似度 `1 - |v - m| / 2`（两个标量都在 [-1,1]）。

- **只提权、不降权**：心情差时把正向记忆压下去会形成自我强化回路（越想越丧），所以反向只回到"不加成"。
- **未标 valence 的条目不参与**：否则"没标注"会变成对老条目的隐性打压。
- `β` 默认 0，扫 0 / 0.05 / 0.1 / 0.2 / 0.3 全部**零差异**。

**为什么零差异**：实测两个库的 `valence` 覆盖都是 **0 条**（`_count` + `exists` 查询）。乘子没有输入，所以任何 β 都不会动排序——这不是实现问题，是**没有数据**。

| 项 | 结果 |
|---|---|
| 新增单测 | fraction 5 例（相似度、只提权、未标不参与、β=0 不变）+ save 2 例（可选、越界拒绝） |
| 全量测试 | 330 pass / 0 fail / 7 skipped |
| β 扫描 | 5 档全部 0/30 条差异 |

**结论**：代码就位、默认关闭。等真有记忆被标注（上层插件在用户情绪明显时标一条）之后再回来标定 β。

| `rollback` | 只有 `superseded` 能回滚；**先撤后继再恢复自己**，避免中间态出现两个 active |

**回滚不删任何东西**：新版置 `archived`（"被撤回的版本"），正文不动。理由很直接——谁都不想
某天要问"上一版到底写了什么"，而它已经被删了。

**链是双向的**：`status.ts` 的 supersede 本来就两边都写；如果只有一边，从新版出发就走不回旧版了。
测试里专门用"从中间一版出发"验证两个方向都能走通。

| 项 | 结果 |
|---|---|
| 新增单测 | 9 例（双向链、offset、无历史、找不到、脏数据成环、回滚顺序、拒回滚 active、不删正文） |
| 全量测试 | 371 pass / 0 fail / 7 skipped |


#### 7.5 实现结果（2026-10-30）

**实现**：`anchor` 布尔字段 + `memory_review action=anchor`。

**为什么是"退出素材池"而不是"拒绝覆盖"**：提炼任务只**新增候选**，从不改写既有条目，
所以"覆盖"这件事本身不会发生。真正的麻烦是「又归纳出一条意思差不多的」，让审核队列里
堆积重复项。把锚点从素材里排掉，正好从源头解决——这也顺带避免了自我强化（拿"你已经被确认的样子"再归纳一遍）。

| 规则 | 行为 |
|---|---|
| 谁能设锚点 | 只有 `status=active` 的 identity（pending 还没生效、archived 是撤回过的，锚定它们没有意义） |

| 项 | 结果 |

### 8.8 两个代价很低的坑（都已修，记录下来免得再踩）

1. **不能用 `ctx.get('layout')` 守住整组注册。**
   `layout` 服务由 `ui-layout` 在自己的 `apply` 里 `reflect.provide`，与本插件没有依赖关系，
   谁先跑不定。实测这里拿到 `undefined`，`if (layout)` 整块跳过 → 侧栏永远没有入口，
   而设置页看起来一切正常（最难查的那种）。**正确做法**：靠 `ctx.slots.inject('main', …)` 等槽位
   （槽位存在就说明布局装好了），`close` 里再惰性 `ctx.get('layout')`。
2. **`scripts/sync-local-plugin.sh --check` 原来只比 `lib/index.js` 与 `panel/index.js`。**
   只改 `panel/client.js` 时它照样报「全部一致」，于是「重启了还是旧界面」会被误判成缓存问题。
   已改成 `diff -rq` 逐文件比对（panel 侧排除同步时才补进去的 `cli/`）。
3. **主区底不能用 `--dsw-alias-bg-base`（皮肤会把它变成「不是实色」）。**
   orca-link 亮色主题把它设成 `#faf7f13d`（24% alpha），暗色主题设成 `initial`
   （自定义属性取 `initial` 等于未定义 → `background: var(--dsw-alias-bg-base)` 整条声明失效）。
   两种情况下主区都透出皮肤插画，正文压在漫画上（2026-11-01 在 test 实例截图复现「Memory」
   标题被「你这吃白饭的蓝色大肥鱼」盖住）。**做法**：注入一条 `[data-memory-workspace]`
   的样式，用 DSH 静态中性色按明暗主题铺实底（亮 `--dsw-static-neutral-bluish-00`、
   暗 `-950`），并在 `S.workspace` 里**不要**再写 background（inline 会盖掉注入的 CSS）。

| 求数 | `GET /graph?scope=team|personal`（接口本来就支持 `scope`，此前前端一直传 `both`） |
| 切换副作用 | 清 `focusId` / `hover` / 画布缩放平移：聚焦点属于上一个库，不清会得到一个空子图 |
| 图例 | 从「实心=个人 带描边=团队」的双图例改成单范围说明（两库不再同图混画） |
| 画布尺寸 | 外层 `height: calc(100dvh - 180px)`、`minHeight: 420`；画布容器 `flex: 1; minHeight: 0`，宽度跟随容器 |

实现上值得记的两点：

1. **加载态也要保留切换控件**：原来三态（loading/error/empty）直接 `return <p>`，一旦切 scope 进入
   加载态，控件就会消失再出现（闪一下）。改成「工具栏 + 提示」的同一结构，控件常驻。
2. 后端 `buildGraph` 的节点上限是**跨索引**取的；`scope=both` 时两个库的节点抢 top-300。
   分开取之后团队/个人各自独立封顶，数字也更接近各自库的总量（本机：团队 268、个人 300）。

#### 8.14.1 第二轮：图没跟着变大 + 拖拽费劲（v0.5.15）

用户看完第一版反馈两件事：画布大了，但**图还是挤在左边一小块**；拖拽很难。

| 症状 | 根因 | 修法 |
|---|---|---|
| 图只占画布一部分，右侧大片空 | `layoutGraph` 末尾用**单一 `scale` 等比缩放**，取两轴较小者 → 宽屏上由高度定倍数，X 永远用不满 | 拆成 `scaleX / scaleY` 两轴各自适配（仍保留 1.6 上限防小图拉散），图形横向铺满 |
| 拖到一半就断，越用力越拖不动 | 事件挂在容器 `div` 上：鼠标划出画布 → `onMouseLeave` 清 `dragRef`，拖拽立即终止 | 位移改挂 `window` 的 `mousemove/mouseup`；`onMouseLeave` 只清高亮，`blur` 也清（切换窗口会丢 mouseup） |
| 拖动发涩、帧率不稳 | 每个 `mousemove` 都 `setState` 重绘 268 点 + 601 边，事件比刷新快时堆叠 | 位移按 `requestAnimationFrame` 合并成一帧一次；拖动中跳过过点检测（`hitTestAt`） |
| 按住拖动时浏览器抢鼠标 | 未 `preventDefault`，会触发文本选择 / 原生拖拽 | `onMouseDown` 加 `preventDefault` |

复核口径：图形在 930×580 画布上占 ~835×460（两侧各留 pad 48），X 不再是等比缩放时的 ~640。

### 8.15 星图 3D 银河化（2026-11-02，v0.6.0）

用户定案：**自由 3D 相机可做**——"星图只是显示，不影响实际逻辑，可以做好看点；切走就停，这么大也够了"。
视觉参考 [dsh-Memory-Galaxy](https://github.com/leesingx/dsh-Memory-Galaxy)（MIT，Copyright (c) 2026 Derpyu520 & 大肥鱼），
**只借视觉语言，代码全部自己实现**：它也是纯 Canvas 2D、零依赖，所以不引入任何包。

| 层 | 实现 |
|---|---|
| 布局 | `layoutGalaxy`：世界坐标 3D，**最大连通分量放盘心**，其余按黄金角散到外圈；团内仍是 BFS 环，y 轴给厚度（中心厚、外缘薄）。布局与画布尺寸解耦 |
| 相机 | `yaw / pitch / dist`，手写「绕 Y → 绕 X → 透视」；拖动旋转、滚轮推拉、`复位` 回默认。焦点模式相机拉近到 880 |
| 投影 | `projectTo`：`focal 1600`、`persp = focal/(focal+z+dist*0.35)`、`unit = min(w,h)/900` 自适应画布 |
| 背景 | 离屏 canvas 缓存（径向渐变 + 暖金核辉光 + 220 颗确定性散星），**只在尺寸变化时重画** |
| 旋臂 | 每帧投影 3 臂 × 2 层（蓝宽 / 粉窄），`lighter` 混合；这是唯一每帧都要重算的重元素，但只有 384 段 |
| 节点 | 本体走 `source-over` 保领域色（`lighter` 叠几层会冲成白，领域就认不出来了）；光晕是径向渐变，只给 hub / hover / 焦点 |
| 聚焦 | 中心节点在原点，1/2 跳各一层**球壳**（黄金角球面分布）；2D 同心环在 3D 下转起来像两个亮圈 |
| 拾取 | 用绘制时缓存的屏幕坐标（`sceneRef`），半径 `max(16, r+11)`——屏幕上节点只有几像素，像素级命中太难点 |

**三条性能纪律**（这是"切走就停"的落点）：

1. **页签不可见就停循环**：`IntersectionObserver` 判可见性，不可见时 `tick` 直接 return 不再调度；
   重新可见时由观察器把循环拉起来（第一版漏了这一步，切回来会停在静止帧）。
2. **自转是一帧一次的全量重绘**，关掉自转后只在数据 / 尺寸 / 悬停 / 聚焦变化时画一帧。
3. **拖动位移按 `rAF` 合并**，且拖动中不做过点检测；相机状态放在 `ref` 里（不触发 React 重渲染）。

验收（本机 1280×800）：团队 268 节点 / 601 边，自转流畅；点节点进入两跳聚焦（47 节点 / 86 边），
点空白或「返回全图」退出；`导出 .canvas` 用当前相机投影后的屏幕坐标，所见即所得。

#### 8.15.1 第二轮：画布没铺满 + 中心太密（v0.6.1）

用户看完第一版反馈两点：星图只占画布左上角一块、右下大片空；中心挤成一坨。

| 症状 | 根因 | 修法 |
|---|---|---|
| 画布只占左上角，右下是纯色 | `draw` 用 React `size` state 定画布像素，而 `ResizeObserver` 回调可能晚于实际布局 → 画布停在上一档尺寸 | `draw` 每帧从 `wrapRef.getBoundingClientRect()` 现读宽高（存 `viewportRef` 给投影用），画布尺寸随之修正 |
| 中心太密、外围发散不均 | 布局用 BFS 层的**同半径圆周**：主团 268 个点、BFS 只有 2~3 层 → 200 个点压在同一个圆周上 | 改成**面积均匀的螺旋**（Vogel）：`radius = sqrt((k+0.5)/n) * reach`、`angle = k * 黄金角`，按 BFS 顺序编号 → 密度按面积走，相邻邻居仍相邻 |

#### 8.15.2 第三轮：节点沿旋臂铺开（v0.6.2）

用户要求"记忆点再铺开一点，照着曲线周围铺"。把布局从"面积均匀的圆盘"换成**沿旋臂分布**：

| 项 | 做法 |
|---|---|
| 共享曲线 | 新增 `galaxyArmAngle(arm, r) = arm/3*2π − 2.6*ln(r/420+1)`，**布局与背景旋臂雾共用**，节点才会真的贴在臂上 |
| 分臂 | domain 按大小降序轮转分配到三条臂；**单个 domain 超过全盘 22% 时按 id 哈希打散**——否则最大 domain（200+ 条）独占一条臂，另外两条几乎是空的 |
| 臂内位置 | `t = (k+0.5)/n`，半径 `R0 + t^0.85*(R1-R0)`，hub 在内段、叶子甩到外段 |
| 厚度 | 径向散布 `(0.09+0.24t)*盘宽`、角度抖动 `±(0.1+0.2t)`，外圈更蓬松 |
| 亮核 | 度数最高的 5% 单列，压进盘心 `r < 0.9*R0`，给整张图一个核 |
| 晕 | 主盘之外的碎点放到盘外一圈 |

**边的处理**（这轮真正的观感分水岭）：601 条边一开始从盘心辐射到臂上，糊成一片光幕。

1. 全局只画**屏幕长度 ≤170px 的短边**，跨臂长边不画；
2. 短边也按长度衰减（`near = 1 - span/220`）；
3. 鼠标悬停某节点时，才把它的**全部边**（含长边）以高亮画出来——结构信息不丢。

结果：全局是三条臂 + 星点，悬停才看关系。

#### 8.15.3 第四轮：星点铺满盘面，别排成珠链（v0.6.3）

上一版把节点严格排进臂里，结果成了一条**珠子链**——用户要的是参考图那种"星点铺满盘面、
臂上只是略密"。

| 症状 | 根因 | 修法 |
|---|---|---|
| 节点排成一条线 | `t` 直接决定半径、角度只加 ±0.1 抖动，等于沿曲线等距排队 | 角度改为**自由角**（黄金角 + id 哈希），再用 `pull = hash^2.6 * 0.92` 的概率朝所属臂拉：多数节点散开、少数贴臂 |
| 半径一圈圈等距 | `t` 线性映射 | `sqrt(t)` 面积均匀 + `±17%` 哈希抖动 |
| 同一领域一样亮、像一排灯 | alpha 只由新鲜度决定 | 再乘 `0.78~1.18` 的 id 哈希，星点有明暗层次 |
| 星点偏大、盘偏小 | — | 半径基数 2.9→2.3，`GALAXY_CAM.dist` 1180→1040 |

一句话：**臂由雾带承担视觉，星点按统计概率聚集**——这才是真实星系的样子，也是参考图的观感。

雾带亮度（2026-11-02 用户反馈「太显眼」）：`lighter` 叠加两层会累加，alpha 从 `0.05/0.03` 降到 `0.02/0.011`，宽度 58/22 → 66/28（更宽更柔）。

#### 8.15.4 第五轮：星尘与星等层次（v0.6.5）

用户对比参考图后说「没他的星点那么协调」。根因不是数量，是**层次**：

| 问题 | 修法 |
|---|---|
| 268 个点大小几乎一样，像撒豆子 | 半径改 `(1.6 + degree^0.75 * 1.3) * sizeJitter(0.72~1.32) * depth`，幂次把度数差距放大 |
| 盘面空、没有底噪 | 加 **2600 颗星尘**（确定性哈希生成，不参与拾取、不连任何记忆），沿臂概率聚集，`fillRect` 画 0.4~2px 微点 |
| 全是蓝的，单调 | 10% 节点用淡金色（`hash > 0.9`），像星空里的异类恒星 |
| 2000+ 个点逐点算三角函数会掉帧 | 投影的 `cos/sin` 一帧算一次，`project()` 用闭包里的缓存，只做乘加 |

参考图那种"协调"其实是**密度分层**：海量暗微点 + 中星 + 少量亮星。我们只有 268 条记忆，
靠节点本身铺不出这层，所以补一层纯装饰的星尘——它不承载任何数据，也不可点击。

#### 8.15.5 第六轮：抄参考图的星点配色与光晕（v0.6.6）

用户要求「抄一下他的星点，让画面更丰富」：

| 项 | 改动 |
|---|---|
| 调色板 | 换成参考图那套亮色：`#96beff / #82e6c8 / #ffd28c / #c0a5ff / #ffa0d2 / #ffcd78 / #7fd8e0 / #ffb08a`（原先是暗色图表色） |
| 星点 | 半径再缩一档（`1.5 + degree^0.7*1.05`），**每颗星外圈加一层 0.2 alpha 同色柔光**（原先只有 hub 有） |
| 星尘 | 2600 → 3200，颜色从两色扩到四色（白蓝/青/暖金/淡紫） |
| 亮度 | 基数 `0.28 → 0.34`，整盘更亮 |

#### 8.15.6 第七轮：星点画法（v0.6.7）

第六轮的星点看起来像**气泡**：柔光是半径 2.35 倍、alpha 0.2 的实心圆，边缘硬，
每颗星都套着一个能看见的环。参考图里星星是「亮核 + 范围很大、几乎看不见边界的光」。

| 项 | 改动 |
|---|---|
| 柔光 | 半径 `2.35x → 3.2x`，alpha `0.2 → 0.08`：大到看不出边界，才不会成环 |
| 星点 | 半径基数按 `1.35 + degree^0.7*0.95`，多数是小点，只有 hub 明显 |
| 亮度 | alpha 基数 `0.34 → 0.42`、深度因子提高，小点不发灰 |
| 星尘 | 3200 → 3800，径向范围 `0.55~1.17` 扩到 `0.55~1.40` 倍盘半径，盘外也有星 |

经验：**小半径 + 高 alpha 的柔光一定是环**；要软，就让半径远大于核心、alpha 低到看不见边缘。

#### 8.15.7 第八轮：光晕改用预渲染贴图（v0.6.8）

第七轮之后每个星点外面变成了一圈**灰蓝色的圆盘**：柔光还是实心圆，`arc` 出来的边缘是硬的，
alpha 再低，在纯暗背景上也能看出边界；密集处叠起来更像蜂窝。

| 项 | 改动 |
|---|---|
| 光晕 | 改成**预渲染的 64×64 径向渐变贴图**（每种颜色一张，`Map` 缓存），绘制时 `drawImage` 缩放 |
| 形状 | 贴图从中心 1.0 渐到边缘 0，叠多少层都看不出轮廓 |
| 统一 | 去掉原来每帧新建的 `createRadialGradient`（hub 专用那套），所有星共用一个 sprite，hub 只是尺寸更大 |

顺带解决性能：原来每帧给 hub 建渐变对象，现在整个生命周期只建 8 张（调色板色数）。

#### 8.15.8 第九轮：初始视角改倾斜（v0.6.9）

用户要求「进星图的时候初始可以斜着旋转，好看一点」。原来 `pitch = -1.05`（约 -60°）几乎是俯视，
盘呈正圆、没有体积；改成 `pitch = -0.78`（约 -45°）、`dist 1040 → 940`：

- 盘被压成椭圆，能看出版面的厚度与旋臂走向；
- 自转仍是绕 Y 轴，倾斜视角下就是「斜着转」，比俯视更像星系。

`复位` 按钮回到的也是这组值。

2026-11-02 二次调整：用户指定「再扁一点」，`pitch -0.78 → -0.46`、`dist 940 → 840`。
盘的高宽比 `|sin(pitch)|` 由 0.70 降到 0.44，更接近参考图的侧倾感（v0.6.10）。

**一次事故（值得记）**：用脚本按「函数起止锚点」整段替换时，把夹在 `layoutGalaxy` 与 `layoutFocusGalaxy`
之间的 `subgraphOf` 一起删了——语法检查通过（少一个函数不算语法错误），页面一进星图就
`ReferenceError: subgraphOf is not defined`，整个面板槽位崩掉。教训：**大段替换后除了语法检查，
还要 grep 一遍被删区间里出现过的函数/常量名**，并在浏览器控制台确认没有 `ReferenceError`。

### 阶段 9 · 写入准入与隐私（P0，先做）

防的是真实发生过的事：巡检发现两个容器把明文密码蒸馏进了记忆库。

- **准入屏障**（memoripy 模式，规则版先行、LLM 版后置）：
  - 拒绝/隔离（`status=quarantine` 而非丢弃，面板可审查）：疑似 secrets（高熵串、`password=|token=|密钥` 模式）、
    检索结果原样再摄取（内容与最近命中高度雷同且无新增信息）、assistant 对用户的自述复述；
  - `memory_save` 返回值加 `quarantined/reason`，工具描述同步写明「凭据不会入库」；
- **写入来源戳** `origin`：user / agent / tool / import / ingest（巡检入库统一标 ingest）——字段新增，走迁移脚本；
- **保存时近似去重 advisory**：more_like_this 命中 cos≥0.85 时返回 `similar_to` 提示（不阻塞，agentmemory 模式）；
- **蒸馏批处理化（可选，默认关）**：distillRunner 攒批 flush、固定调用次数（memobase 模板），观测到调用量后再开。
- 验收：单测注入含密码/含检索原文的候选，断言 quarantine；`npm run eval` 不回退。

#### 阶段 9 落地记录（2026-11-01，v0.5.0）

| 项 | 落点 | 验收 |
|---|---|---|
| 准入屏障（规则版） | `src/memory/admission.ts`（纯函数）；`save.ts` 在 embedding **之前**判定 | 35 条单测：11 类凭据形态隔离、10 类正常内容放行、返回值不含完整凭据 |
| 隔离而非丢弃 | 写 `status=quarantine` + `quarantine_reason`，`distill_state=skipped` | 8 条集成断言：落库、不进检索、不建边、不花向量、不蒸馏 |
| 写入来源戳 `origin` | `SaveInput.origin`（user/agent/tool/import/ingest），缺省 `agent`；脏值直接拒绝 | 单测断言缺省与 ingest 写入；未知值报错 |
| 近似去重 advisory | 与建边共用一次 kNN，cos ≥ 0.85 回 `similar_to` | 单测：自身排除、只提示不阻塞 |
| 面板审查与恢复 | 浏览页状态筛选加「已隔离」；详情显示 `origin` / 隔离原因；新增 `POST /memories/restore` | 自检行 `浏览: ok`；恢复接口按 ES `_has_privileges` 判权 |
| 字段迁移 | `scripts/migrate-origin-fields.sh`（模板 JSON 现场从 init-indices.sh 提取，不抄第二份） | 125 上 10 个 `personal_memory_*` 全部 ok；模板同步 |

**实现上值得记的三点**：

1. **准入放在 embedding 之前**。隔离条目不进检索，向量只有人工恢复后才有意义；
   先判定省掉一次 Ollama 调用——误触发多的时候这笔钱不小。
2. **「检索原文再摄取」只能靠进程内短期缓存**（`recallCache`，20 条 / 30 分钟）。
   拿全库比会把「同义改写」误杀，那是记忆库最值钱的东西；刚搜完就抄回来才是搬运。
   缓存随重启失效是**正确行为**，不是缺陷。
3. **模板 JSON 从 init-indices.sh 现场提取**，不在迁移脚本里抄第二份。

#### 阶段 12 收尾：效用信号接入（2026-11-02，v0.5.9）

`ranking.utilityWeight`（默认 **0 = 关**）：`score × (1 + utilityWeight × log1p(confirmed_use − corrections))`。

三个设计取舍：

1. **单独一个旋钮，不改 hitWeight**：`hit_count` 量的是「被搜到几次」（流行度，写得越多越占便宜），
   `confirmed_use` 量的是「被判定有用几次」。语义不同，能不能替换必须由评测回答，不能偷偷换算。
2. **负效用一个都不罚**：👎 多于 👍 时按 0 算——被否过不代表该消失，只是不加分。
3. **默认关**：👍/👎 才刚攒（批 B 上线一天），样本量不够就说"效用信号能改善排序"是自欺。

#### 阶段 13 批 C：提案-确认闭环（2026-11-02，v0.5.11）

整理任务本来就有 `--apply` / dry-run 两档，但中间缺一步：**dry-run 的结论只打到 stdout，
人看完就没了**，而 `--apply` 是全量写。现在补上「提案 → 确认 → 只落确认过的」：

```bash
node consolidate/cli.ts --limit 5 --proposals /tmp/p.json   # 只出提案
node consolidate/cli.ts --apply --only-ids id1,id2          # 只落点名的
```

| 落点 | 说明 |
|---|---|
| `RunReport.proposals` | 只收 `duplicate` / `merge_candidate` / `pending` 三类；`new`（正常入库）、`blocked`（敏感拦下）、`personal_only`（只留个人库）都不进提案 |
| `buildProposals()` | 纯函数，4 条单测（筛选/带邻居/不留空字段/空输入） |
| `--proposals <path>` | 提案落成 JSON（含 action/neighborId/topScore/confidence），可直接贴给人看 |
| `--only-ids <ids>` | 只处理点名的条目；与 `--apply` 组合即「确认后才落库」 |
| `--apply`（不带 only-ids） | 仍在，但文档标注「全量，慎用」 |

**真实 dry-run 结果（本机跑 125 的库，limit=5）**：5 条候选**全是** `merge_candidate`
（相似度 0.91 / 0.948 / 0.915 / 0.919 / 0.978），每条都带出了「和谁重复」。
也就是说库里确实积着近似重复的条目——提案清单第一次跑就把它们点名了。

**第一次真实合并（2026-11-02）**：拿提案里相似度最高的一对做了闭环，结论值得记：

- 那 5 条 `merge_candidate` 里只有 **2 条真重复、1 条是团队版落后、2 条是同主题不同侧面**。
  说明 0.90 这个阈值**分不开「重复」与「互补」**——`--apply` 全量写会真的丢信息，这也印证了
  「只做 `--only-ids`」这个决定。
- 真正做的动作不是"合并出新条目"，而是**用个人库的完成态覆盖团队里过时的快照**：
  删掉「规则 YAML 尚未验证 / PROM_DS_UID 待回填」，补上「10 条规则已 provision 且 health=ok、
  全链路实测、数据量闸门、实测基线」。**保留了团队版里那些「为什么/坑」**（nginx 按 SNI 分流、
  匿名 API 401、为什么用 stdio、dsh-mcp-panel 会覆盖 config 行）。
- 更新团队条目时**必须同步重算 `content_sha256` / `topic_key` / `embedding`**：
  内容变了不重算向量，检索会继续按旧正文匹配——这条知识就"搜得到但对不上"。
- 审计新增 `merged` 事件（拿 `promoted` 冒充会让审计读起来像"新晋升了一条"）。
  审计里记了旧/新 sha 与长度，回滚有据。

**`dismissed` 状态（2026-11-02，v0.5.12）**：人工判定「相似但不该合并」时用
`--dismiss <memory_id> --reason "..."`，把条目从待合并候选里摘出来。

- `promote_state` 的取值集中在 `src/memory/promoteState.ts`：`RESCANNABLE`（none/candidate）
  与 `SETTLED`（promoted/blocked/personal_only/dismissed）两组，单测断言**两组不重叠、并集覆盖全部**——
  加状态时最容易漏的就是扫描条件或终态列表，错一处就会被反复处理或永远显示"还没结论"。
- 候选查询的默认值改成引用 `RESCANNABLE_PROMOTE_STATES`，`dismissed` 天然被排除。
- 审计新增 `dismissed` 事件；`--dismiss` 也要求 `--reason`（为什么判不合并要能追溯）。
- 顺带修了一个真 bug：审计 actor 在 `parseArgs` 里就取了 `MEM_USER_ID`，
  那时 `--user` 还没生效 → 记成 `cli:unknown`。改成由 main 用**实际生效的** userId 补。

**为什么不做「面板待审队列」而是先做命令行闭环**：队列要新索引 + 面板页 + 状态机，
而这一步的**核心风险是「无人值守的批量删除/合并」**，用 `--only-ids` 已经把它关上了。
队列化是体验优化，不是安全边界，放到面板子项那批做。

#### 阶段 13 批 B：forget_reason 失效原因留痕（2026-11-02，v0.5.10）

`memory_update_status` 的 `expire` / `supersede` 现在把 `reason` 写进 **`forget_reason`**。

| 行为 | 落库 |
|---|---|
| `supersede` + reason | `forget_reason = reason`（裁剪两端空白） |
| `supersede` 不给 reason | `forget_reason = 'superseded'`（动作名兜底） |
| `expire` ± reason | 同上，兜底 `'expired'` |
| `restore` | `forget_reason = null` —— 否则会出现「已生效却还挂着失效理由」 |
| `archive` | **不写**：它是可 restore 的暂存，不是终态失效 |

**为什么必须留痕**：半年后看到一条 superseded 的记忆，没有这个字段就没人知道它被什么取代、
为什么下架。`reason` 参数本来就在，但**只进了日志**——日志会滚掉，字段不会。

**为什么兜底写动作名而不是空串**：空值等于「不知道」，而「被新版本取代」本身就是原因；
写动作名之后，`forget_reason` 永远可查、可聚合。

**迁移**：`migrate-forget-reason-fields.sh`，125 上 10/10 索引 ok（新字段 keyword/ignore_above 256）。
老条目没有这个字段属正常（`exists` 判据一致）。

#### 阶段 13 批 A：as-of 时间点回看（2026-11-02，v0.5.9）

`memory_search` 加 `as_of`（ISO 8601）：只返回该时间点之前**创建**的记忆，结果里回显 `as_of`。

**语义说清楚（这是近似，不是版本回放）**：ES 里没有版本历史，所以它回答的是
「那时已经存在的条目」，看到的内容是**现在的内容**；已 supersede/expire 的仍按 active 过滤掉。
把它写成「能回放旧版本」就是骗人——要真回放得引入版本索引，那是另一阶段的事。
非法日期直接报错（静默回落到"不过滤"会让时间点回看骗人）。

#### 阶段 13 契约评测落地记录（2026-11-01）

| 项 | 落点 | 验收 |
|---|---|---|
| 契约集 | `tests/eval/contracts.jsonl`：35 条（4 must / 31 should） | must 全过；should 8 失败**已写进基线** |
| 判定纯函数 | `scripts/lib/contracts.ts`（解析 / 逐项判定 / 汇总） | 12 条单测 |
| runner | `scripts/eval-contracts.ts`（`npm run eval:contracts[:gate]`） | 真实 ES 跑通，`--update-baseline` 产出基线 |
| 调参 | `scripts/tune.ts`（只调 rrfK / hitWeight / recencyWeight） | 6 组真实跑完 |

**闸门的两道**（比"看个数字"重要）：

1. `must` 级任何一条失败 → 非零退出。currently 4 条：identity/persona/journal 不进普通检索、
   `__mood__` 不被检索、`explain=true` 时回执与 hits 同长、常见 query 至少有一条命中。
2. `should` 级不仅比**数量**，还比**失败集合**：修好一条又坏一条同样拦。
   （这一点是写闸门时特意加的——只比数量会被"换人"骗过去。）

**当前基线（诚实记录）**：must 0 失败；should 8 失败 = 1 条召回漏（q16 本地备份服务的端口/容器名）
+ 7 条噪声 query 全误报。噪声是已知缺口，先把数字钉住，等阶段 12 的置信/多样化处理。

**tune 的真实结论**：rrfK ∈ {30,60,100} × hitWeight ∈ {0,0.2} 六组结果**完全一致**
（hit@1 79%、hit@5 96%、MRR 0.865、should 8）。说明当前瓶颈不在这三个参数上——
不要为了"调过参"而调参。真正的收益在召回结构（分级读取、多样化、CJK 分词）而非旋钮。

**局限（别把它当万能闸）**：
- 召回契约用 `memory_id` 写死，重建索引/换库会全部失效（迁移不会，reindex 会）；
- 噪声契约依赖库内容，库越大越容易"碰巧命中"，需要定期重估；
- 写入类契约（准入→隔离）不在 runner 里跑（要写 ES），由 `tests/admission*.test.ts` 覆盖。

- 验收：`npm run eval`（契约版）进 CI；删除路径 100% 走提案或人工。
