## 阶段 0 · 地基（不改任何线上行为）

没有基线就没有「优化」，只有「凭感觉改」。这一阶段全部是零行为变更。

### 0.1 检索评测集

- 新增 `tests/eval/queries.jsonl`，每行：`{ "id", "query", "expect": ["<memory_id>"], "kind": "single|paraphrase|exact|noise" }`
- 起步 30 条，四类各若干：
  - `single`：一句记忆的反问（从真实个人库取样）
  - `paraphrase`：换说法（验证向量路）
  - `exact`：接口名/错误码/路径（验证 BM25 路）
  - `noise`：库里确实没有的东西（`expect: []`，验证 `low_confidence` 不误报）
- 新增 `scripts/eval-search.ts`：直接调 `searchMemories`，输出 recall@5 / MRR@5 / 空结果率 / `low_confidence` 率，写 `tests/eval/baseline.json`
- **验收**：`npm run eval` 能跑通，基线归档

> 这一步需要人抽检口径：我先从 MEMORY.md 反向生成 30 条候选，你抽检 10 条确认「期望命中」标得对。

#### 0.1 结果（2026-10-29 已完成）

评测集 30 条（single 8 / paraphrase 8 / exact 8 / noise 6），全部连真实个人库（268 条）。

**口径 A：不判空（`--margin-floor 0`，衡量排序质量）**

| kind | n | hit@1 | hit@5 | MRR |
|---|---|---|---|---|
| single | 8 | 100% | 100% | 1.000 |
| paraphrase | 8 | 88% | 88% | 0.875 |
| exact | 8 | 75% | 100% | 0.844 |
| noise | 6 | — | — | 误报 6/6（不判空必然如此） |

**口径 B：生产默认（`--margin-floor 0.05`）**

| kind | n | hit@1 | hit@5 | low_conf |
|---|---|---|---|---|
| 全部 | 30 | **0%** | **0%** | **30/30** |

**结论：排序能力本身是好的（hit@5 96%、MRR≈0.91），但置信判空把 73% 的查询直接杀死，包括 8/8 的 single（top1 就是正确答案仍然返回空）。**

根因数据：

| 指标 | single | paraphrase | exact | noise |
|---|---|---|---|---|
| kNN top1 | 0.804~0.888 | 0.799~0.835 | 0.753~0.851 | 0.768~0.797 |
| margin（top1−top2） | 0.015~0.095 | 0.002~0.073 | 0.001~0.066 | 0.002~0.021 |
| BM25 top1 | 30.8~53.9 | 20.5~37.0 | 13.9~46.2 | 10.3~25.8 |

margin 中位数 **0.0208**，22/30 低于 0.05。

**这不是 bug，是参数标定失效**：`0.05` 来自文档 §8.4「三条记忆」时的实测（换说法 margin=0.0516）。候选池从 3 条涨到 268 条后，top2 必然逼近 top1，margin 整体下移——**门槛必须随库规模重新标定**。

## 阶段 0.5 · 置信判定重构（插队，优先级最高）

> 原计划的阶段 1（兄弟路）顺延到这一步之后。理由：它修的是「明明有答案却返回空」，影响面 100%；兄弟路只影响少数换说法场景。

四类数据说明**没有单一阈值能同时做好**：真命中与噪声的 kNN top1 在 0.75~0.80 区间重叠，BM25 也有重叠（paraphrase 最低 20.5 < noise 最高 25.8）。任何静态阈值都会误杀或误放。

**待定方案（需拍板，三选一）：**

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. 下调门槛 | `marginFloor` 0.05 → 0.005~0.01 | 改动最小，一行配置 | 阈值仍随库规模漂移；噪声误报增加 |
| B. 分层判据 | top1 < 0.65 直接空；0.65~0.80 要求 margin≥0.02 或 BM25≥25；≥0.80 直接返回 | 用绝对分兜底，噪声与真命中分得开一些 | 中间区仍有边缘误杀；三个常量都要标定 |
| C. 分位数自适应 | 定期用 N 条随机 query 采样 top1 分布，取下分位（如 P15）作门槛 | 随库规模自动调整，不用手调 | 多一个离线任务；冷启动需要样本 |

**倾向 B**：`margin` 只做中间区的辅助，绝对相似度做主线；它能在不引入新任务的前提下，把这批数据从「全杀」救回「只杀明显无关的」。但 B 的三个常量要在真实数据上跑一遍验证，不能拍脑袋。

#### 0.5 试算结果（2026-10-29，`npm run eval:thresholds`）

网格扫描 3000+ 组（tLow × tHigh × mMin × bMin），帕累托前沿只剩两个点：

| 参数 | 真命中返回 | 误杀 | noise 误放 |
|---|---|---|---|
| tLow=0.75 tHigh=0.78 mMin=0.015 bMin=13 | 24/24 | 0 | 2（q25、q30） |
| tLow=0.75 tHigh=0.80 mMin=0.025 bMin=30 | 23/24 | 1（q20） | 0 |

**关键发现：存在「不可分对」。** q20（真命中，`lot.bd_write_sync`）在三个维度上**全部劣于** q25（ZooKeeper 噪声）：

| | top1 | margin | bm25 top1 |
|---|---|---|---|
| q20（该留） | 0.7663 | 0.0014 | 13.9 |
| q25（该走） | 0.7971 | 0.0208 | 13.6 |

→ 由这三项构成的任何阈值都判不出「q20 留、q25 走」：想误杀 0 必然误放，想误放 0 必然误杀 q20。这不是调参问题。

**两个必须写下来的警告：**

1. **样本不足，参数贴边**：noise 只有 6 条，两个前沿点都贴着数据边界（bMin=13 vs q25 的 13.6；bMin=30 vs q30 的 25.8）。这是过拟合的典型形状，**不能据此定生产常数**；noise 扩到 20 条以上要重跑。
2. **q20 的根因不是阈值**：它是 exact 类（含下划线标识符），BM25 只有 13.9——标识符被 IK 切碎、又被口语部分（「已经做到哪一步」）稀释。阈值救不了，需要**标识符精确匹配子字段**（keyword + standard 分析器）单独提权。记为后续优化项。

#### 新增方案 D：低置信「返回 + 标注」，而不是「返回空」

建议与 B 叠加，而不是二选一。

理由：记忆检索的失败模式是「模型以为没记过，于是凭印象编」；返回几条不相关的记忆，模型看内容就知道不相关，代价小得多。现状 `low_confidence → hits: []` 把信息全部丢掉了。

- 粗粒度：`note=low_confidence` 但照常返回 hits，`text` 里加一句「相关性较低，谨慎使用」（约 10 行）
- 细粒度：`Projected` 加 `confidence`，逐条标注（改动大，暂不做）

B 的分层阈值仍有价值——用来挡「top1 < 0.65 的明显无关」，而不是用来决定「返回几条」。

**落地顺序**：① 改 note 语义（返回 + 标注）→ ② B 取宽松档 `tLow=0.60 / tHigh=0.80 / mMin=0.01 / bMin=20` → ③ noise 样本扩到 20 条后重跑试算再收紧。

**验收**：口径 B 下 single/paraphrase 的 hit@5 ≥ 90%，且不再出现「全空」；noise 允许少量误放（有标注兜底）。

#### 0.5 实现结果（2026-10-29 已完成）

改造前 vs 改造后（30 条评测集，真实个人库 268 条）：

| 指标 | 改造前（`marginFloor=0.05`） | 改造后（分层 + 返回标注） |
|---|---|---|
| single hit@5 | 0% | **100%** |
| paraphrase hit@5 | 0% | **88%** |
| exact hit@5 | 0% | **100%** |
| 真命中能拿到结果 | 0 / 24 | **24 / 24** |
| noise 被标注低置信 | —（全部空返回） | **6 / 6** |
| noise 漏标（当正常结果给出） | — | **0** |
| 真命中被误标 | 24 / 24 | **1 / 24**（q20） |

**最终参数**：`floorTop1=0.60`、`autoPassTop1=0.80`、`minMargin=0.025`、`minBm25=30`。

实现要点：

- `judgeConfidence` / `DEFAULT_CONFIDENCE` 在 `search.ts` 里导出；**config 的 schema 默认值直接引用它**，杜绝「代码默认」与「配置默认」两处漂移
- 低置信不再 `hits: []`：照常返回，`text` 前置一句「相关性偏低，谨慎采信；无关时当作没有检索到」
- **margin 不再跨库混算**：`scope=both` 时置信信号只取个人库（原实现把两库 kNN 分数混在一起排序，库不同、候选池不同，margin 无意义）
- **只有一条候选时不判窄**：没有第二名就没有「区分度」可言，否则库里只存一条相关记忆时永远被判低置信
- **降级（无向量）不判低置信**：没有依据就不判
- 埋点 `low_confidence` 记实际返回条数（原为 0），空结果率与低置信率才分得开

已知遗留：q20（`lot.bd_write_sync`）被误标，根因是标识符被 IK 切碎、BM25 仅 13.9，**不是阈值能解决的**——归到阶段 1 的「标识符精确匹配子字段」。

**参数贴边警告仍然有效**：noise 只有 6 条，`minBm25=30` 贴着 q30 的 25.8。noise 扩到 20 条以上必须重跑 `npm run eval:thresholds`。

## 阶段 1 · 第三路召回（不动 mapping，纯检索层）

调研里「同 topic_key 兄弟条目」是性价比最高的一条，因为它用 ES 的 `terms` 查询就能实现，不碰图、不碰模型。

- `src/memory/search.ts`：BM25 结果取前 5 条的 `topic_key`（跳过空值与 `general`）→ 发一次 `terms` 查询取同 topic 的其他条目（上限 20 条）
- 三路进 `rrfFuse`：`[bm25, knn, siblings]`，与现有两路同权重
- 开关 `ranking.siblingRoute`，默认 `false`
- **验收**：开关两跑评测对比，`recall@5` 不下降、`noise` 类不误报；关掉后结果与阶段 0 基线一致

#### 阶段 1 实现结果（2026-10-29 已完成——标识符子字段）

先做了「标识符精确匹配」，把 q20 的遗留一起解决；`topic_key` 兄弟路留到下一步。

**字段**：`content_exact`（`text` + `standard` 分析器，与正文同源）。为什么用 standard：UAX#29 在字母之间不因 `.`/`_` 断词，`lot.bd_write_sync` 保留为单个 token；中文仍逐字可搜，phrase 一样能用。实测 `match_phrase content_exact:"lot.bd_write_sync"` 命中 1 条。

**查询侧**：`extractIdentifiers()` 从 query 里挑标识符（最多 5 个），在 `bm25Body` 里生成 `should: [match_phrase content_exact^5]`。`should` 不命中也不影响召回（`must` 里已有主查询）。

**效果**：

| 指标 | 阶段 0.5 之后 | 阶段 1 之后 |
|---|---|---|
| q20 的 BM25 首条分 | 13.9 | **38.0**（越过 `minBm25=30`） |
| exact 类被标低置信 | 1 | **0** |
| noise 误放 | 0 | **0** |
| 排序名次 | — | 与基线逐条一致（RRF 只用名次） |

**踩到的坑（值得记住）**：第一版规则把「全大写缩写」也算标识符，于是 `Kubernetes Ingress 的 TLS 证书怎么续期` 提取出了 `TLS`——而库里真有宝塔 SSL 证书的记忆，`match_phrase` 命中后 boost 5，把这条噪声查询的 BM25 从 25.8 顶到 **65.6**，直接越过门槛放行。

修法不是维护黑名单（会漂移），而是**要求缩写必须含数字**（`E101`/`PM2` 算，`TLS`/`CLI`/`API`/`TTL` 不算）。修完 q30 的 BM25 回落到 27.1，噪声重新被正确标注。

**迁移（顺序不能反）**：

```bash
# 1) 先加字段并回填（旧代码不写该字段，无害）
ES_URL=... ES_CA=... ES_USER=... ES_PASS=... scripts/migrate-identifier-field.sh xqh
# 2) 再更新插件代码
```

为什么不能反：`dynamic: strict` 下，索引没有 `content_exact` 时，新代码写文档会直接 400。

已验证幂等：复跑 `total=0 updated=0`。个人索引与 `team_knowledge` 都已加字段。`scripts/init-indices.sh` 的模板也同步了，新用户的索引会自动继承。

**部署注意**：线上跑的是旧 `lib`，要让改动生效需要重新构建 + 重启 dsh-web；且**先迁移、后重启**。

## 阶段 2 · 排序信号（mapping 增量，风险最低的一次加字段）

### 2.1 加字段

新增 `scripts/migrate-ranking.sh`（照 `migrate-s9.sh` 的模式：改模板 + 对已存在索引 `PUT _mapping`）：

| 字段 | 类型 | 用途 |
|---|---|---|
| `importance` | keyword | critical / normal / low |
| `hit_count` | integer | 被检索命中次数 |
| `last_hit_at` | date | 最近一次命中时间 |

⚠️ **`scripts/init-indices.sh` 必须同步改**，否则新用户的索引模板不带这些字段（`dynamic: strict` 下写入直接 400）。

### 2.2 写入 importance

- `src/memory/save.ts`：schema 加 `importance`（枚举校验，默认 `normal`）
- 提示段加一句：`critical` 只给「不看就会做错」的规则，别滥用
- **验收**：单测覆盖非法值与默认值；旧调用方不传也能写

### 2.3 热度回写

- 检索命中后 `void recordHits(ids)`：**不 await**、失败只记日志、不影响返回
- 用 `_bulk` 或 `update_by_query`？**用 `_bulk`（一批 ≤50 条）**，避免 `update_by_query` 扫全索引
- **验收**：`search` 的 p95 不因回写变慢（回写走 fire-and-forget，压测对比）；连跑 5 次同一 query，`hit_count` 单调上升

### 2.4 乘子接入

在 `src/fragment.ts` 的 `mergeScopes` **之后**统一乘，绝不混进 RRF 分（尺度差一个数量级）：

```
factor = 1
       + importanceWeight × (imp_value - 1)       // critical=1.1, normal=1, low=0.9
       + hitBoost × log1p(hit_count) / 10
       + recencyWeight × exp(-Δdays / halfLife)
```

- 三项系数全部来自 `ranking` 配置，默认 0 → 行为不变
- **验收**：系数为 0 时与基线逐位一致；单项开启时只影响目标维度

#### 阶段 2 实现结果（2026-10-29 已完成）

**字段**（`scripts/migrate-ranking-fields.sh`，个人索引 + `team_knowledge` 都已加）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `importance` | keyword | critical / normal / low |
| `hit_count` | integer | 被检索命中的次数 |
| `last_hit_at` | date | 最近一次命中时间 |

**不需要回填**：代码把缺失值当 `normal` / `0` / `null`，老文档天然参与排序。

**乘子公式**（`fragment.ts` 的 `applyRanking`，作用在 `mergeScopes` 之后）：

```
factor = 1
       + importanceWeight × (imp − 1)          // critical 1.1 / normal 1.0 / low 0.9
       + hitWeight × log1p(hit_count) / 10
       + recencyWeight × exp(−ageDays / halfLife)
```

默认值：`importanceWeight=1`、`hitWeight=0.2`、`recencyWeight=0.1`、`recencyHalfLifeDays=30`。三项都可归零关闭（全零时函数直接返回原数组）。

**为什么 importance 只给 ±10%**：它是**微调**，不是主导。否则排序会退化成「按标签排」，真正相关的那条被一个 critical 标签压下去。

**命中回写**：

- 用 `_update` + painless 脚本 `hit_count += 1`（**不是读-改-写**，并发检索会丢更新）；
- fire-and-forget，失败只打日志，绝不影响检索返回；
- 不配 `hitRecorder` 就不回写（测试与脚本默认无写流量）；
- 回写用文档的 ES `_id`（`merged[].id`），不是 `memory_id`——两者不是一回事。

**验证**：

| 项 | 结果 |
|---|---|
| 评测排序名次 | 与基线**逐条一致**（默认值不劣化） |
| 生产口径 | single 100% / paraphrase 88% / exact 75%(hit@5 100%) / noise 误报 0、低置信 6 |
| 单测 | 255 pass / 0 fail，含「critical 在编排层反超 1.5% 分差」的接线验证 |

**已知边界**：`hitWeight` 与 `recencyWeight` 都依赖真实使用量，现在 `hit_count` 全为 0、`last_hit_at` 全空，所以这两项目前**没有任何实际影响**——上线后随检索逐步累积。这也是为什么评测显示「名次一致」：不是没生效，而是信号还没产生。

## 阶段 3 · 时间有效性（字段已有，缺写入与过滤）

### 3.1 检索过滤

`src/es/dsl.ts` 的 `buildFilters` 加两条：

```
must_not: { exists: { field: "superseded_by" } }
```

- 注意：ES 里「字段没值」可能是「不存在」也可能是 `null`，**必须用 `must_not exists`**，不能写 `term: superseded_by: null`
- `expires_at` 同理：`must_not: { range: { expires_at: { lt: now } } }`（写法需实测确认，别想当然）

### 3.2 个人库自动 supersede

- `consolidate/` 的冲突分支：个人库命中冲突 → 写 `status=superseded` + `superseded_by=<新 id>` + `superseded_at`；**团队库仍走 pending**（错误结论的代价太高）
- 不物理删除（调研结论）
- **验收**：造 3 组「旧结论 → 新结论」，旧条不出现在 `memory_search`，按 id 仍可查；撤回动作进 `memory_audit`

### 3.3 时间点回溯（可选，加分项）

`memory_search` 加 `as_of` 参数：不看 `superseded_by`，而看 `superseded_at > as_of`。这才让「当时确实是这样」可回答。

#### 阶段 3 实现结果（2026-10-29）

**3.1 检索过滤：已完成**

`buildFilters` 末尾加两条兜底过滤（`freshOnlyFilters`，测试与实现共用同一份定义）：

- `must_not exists superseded_by` —— 被取代的条目不再返回；
- `must_not range expires_at < now` —— 过期条目不返回（字段不存在时 range 不匹配，天然保留）。

**为什么用 `must_not exists` 而不是 `term: null`**：字段缺失与字段为 `null` 在 ES 里是两回事，前者才是「没有值」的稳妥判据。

**端到端验证**（临时探针文档，验证后已删）：同一条 query，带过滤命中 7 条、去掉过滤 8 条——差的正是那条标了 `superseded_by` 的文档，证明是「被过滤」而不是「不存在」。

**3.2 自动 supersede：否决（数据否决的，不是设计否决）**

`scripts/supersede-scan.ts` 对 267 条真实数据跑 dry-run，出 **39 对候选，全部是误判**。

典型例子：

- 「DSH skill 子系统」vs「~/.dsh/skills 已从 8 个扩到 24 个」→ 因为一边有「要」另一边有「不要」就判成相反结论；
- 「jbp 安全组规则」vs「lottery-cloud 生产拓扑」→ 同上。

**根因**：`detectContradiction` 只做极性词对匹配，**没有「是否在讲同一件事」的约束**。整理任务里没炸，是因为调用前有 `decision.verdict === 'merge_candidate'`（高相似 + 同 `topic_key`）这道前置门；而 `topic_key` 在库里几乎全空（16/267），单独跑冲突扫描时这道门不存在。

**如果按原计划打开自动 supersede，会误杀 39 条记忆。**

处置：

- 脚本改成**必须逐条点名**才写：`--apply --older <memory_id>`，批量写入在代码层被拒绝；
- 保留 `superseded_at` 字段（日期），为将来的人工/半自动路径留位置；
- 自动部分与阶段 1b 是同一个阻塞点：**先有可复用的主题粒度，才谈得上「同一主题的相反结论」**。

**3.3 时间点回溯：未做**（`as_of` 依赖语义化的失效判定，先搁置）

## 阶段 4 · 从 LivingMemory 提取的两项（2026-10-29 已完成）

对照仓库：`lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory`（397 stars，AGPL-3.0）。
它的记忆原子模型给了两个可直接迁移的机制。

### 4.1 按 memory_type 的半衰期

原来所有记忆统一 30 天半衰期——对 `task_progress` 太慢、对 `fact`/`decision` 太快。

`fragment.ts` 新增 `MEMORY_TYPE_HALF_LIFE_DAYS`：

| 类型 | 半衰期 | 理由 |
|---|---|---|
| `decision` | 365 天 | 用户定下的口径，一年内基本不变 |
| `fact` | 365 天 | 工程事实，确认过就长期成立 |
| `context` | 180 天 | 项目/环境背景，半年内仍有效 |
| `preference` | 90 天 | 会变，但不像进度按周过期 |
| `task_progress` | 14 天 | 两周内还有意义 |
| （未列出的类型） | `recencyHalfLifeDays` 兜底 | 默认 30 |

**为什么不照抄它的数字**：LivingMemory 的 TTL 描述的是「从对话自动抽取的原子」的寿命（factual 180 天、planned 2 天、preference 60 天），而我们的记忆是**模型显式保存、人确认过的稳定事实**，语义更重。照抄会把正当的知识提前衰减掉。

### 4.2 访问强化延长寿命

它把 TTL 乘 `(1 + min(0.5, count × 0.1))`。我们照此实现，但作用在**半衰期**上：

```
halfLife = 类型半衰期 × (1 + min(reinforcementCap, hit_count × reinforcementPerHit))
```

默认 `reinforcementPerHit=0.1`、`reinforcementCap=0.5`（最多延长 50%，避免老条目「越用越不朽」）。

与已有的 `hitWeight × log1p(hit_count)/10` 是**两个维度**：那个是「排得更靠前」，这个是「老得更慢」。

### 验证

| 项 | 结果 |
|---|---|
| 单测 | **258 pass / 0 fail**，新增 3 例（类型差异、强化延寿、封顶） |
| 评测排序名次 | 与基线**逐条一致** |

名次没变不是没生效——`recencyWeight` 只有 0.1，而库里 269 条中 250 条是 `context`（半衰期同为 180 天），类型差异在现有数据上几乎不产生区分度；`hit_count` 又全是 0。真正会改变排序的是**上线后访问量积累**。若要把时间因素放大，调 `ranking.recencyWeight` 即可（但会削弱「旧而相关」的条目，不建议超过 0.2）。

### 4.3 agreement_bonus 的 A/B 结论：**不启用**（2026-10-29 实测）

`rrfFuse` 增加可选的两路一致加成：`fusedScore × (1 + bonus × (1 − rankGap/span))`，只对「两路都命中」的条目生效。用评测集扫了四档：

| bonus | paraphrase hit@1 | paraphrase MRR | exact MRR |
|---|---|---|---|
| **0（默认）** | **88%** | **0.875** | **0.844** |
| 0.1 | 75% | 0.813 | 0.844 |
| 0.2 | 75% | 0.813 | 0.838 |
| 0.4 | 75% | 0.813 | 0.838 |

**没有提升，反而让 paraphrase 的 hit@1 掉了 13 个百分点。**

原因：换说法的查询里，正确答案往往**只被向量路命中**（字面不同），而「字面匹配但意思不对」的条目才被两路同时命中。agreement bonus 恰好把后者顶上来、把正确答案挤下去。

这条实验反过来印证了阶段 2 的选择：**用乘子而不是加权和**是对的——相关性必须是硬门槛，否则「两路都命中」这种间接信号会盖过真正的相关度。

代码保留（`ranking.agreementBonus`，默认 0），因为它对「两路都命中且都靠前」的场景仍有理论意义，只是在本数据集上被证伪；默认关即无影响。

### 4.4 生命周期：做到归档为止，**不做物理删除**（用户 2026-10-29 定调）

`memory_update_status` 补齐两个动作：

| action | 行为 |
|---|---|
| `archive` | `status=archived`，移出检索，仍可按 id 查回 |
| `restore` | 置回 `active`，**并清 `superseded_by`**（否则检索的 `must_not exists` 仍会挡住它） |

**不提供 `purge`**，理由三条：

1. 审计要能回答「当时为什么这么定」——旧结论本身就是知识；
2. 插件在结构上没有删除能力：`EsClient` 根本没有 `delete` 方法（2026-10-29 核实）；
3. 唯一会物理删除的是运维脚本（`prune-audit.sh` 清审计日志、`init-*.sh` 清探针文档），与记忆正文无关。

所以「遗忘」在本插件里**永远是可见性变化，不是销毁**。

## 阶段 5 · 联结与激活（设计说明）

> 勾选清单在 [README「待开发」](../README.md#待开发勾选进度)。这里只记**为什么这么做**与**边界条件**。

**为什么排在情绪与自我迭代之前**：它是唯一能用现有评测集直接量化的一层（`tests/eval/queries.jsonl` 的 single / paraphrase 两类会直接反映扩散激活是帮忙还是添乱）。情绪和自我迭代的收益没有现成判据，必须先有稳定的排序基线。

**为什么 `activation` 不合并进 `hit_count`**：两者语义不同。

| 字段 | 语义 | 更新时机 | 是否有上界 |
|---|---|---|---|
| `hit_count` | 被命中过多少次（计数） | 每次命中 +1 | 无，靠 `log1p` 压缩 |
| `activation` | 当前有多"热"（强度） | 命中提升、时间衰减 | 有封顶 |

混成一个字段会让「一周前被命中 100 次的条目」和「昨天被命中 1 次」无法区分——而这正是活跃度要表达的东西。

**为什么 `α` 默认 0**：扩散激活在单跳上容易把错误邻居带进来。默认关 = 合并前后逐条一致，出问题能一键退回，符合本仓库「新能力默认关」的既有原则。

**边界条件（必须挡）**：

1. **边数膨胀**：每条记忆最多保留 `relatedTopK`（建议 5）条边，按权重截断；否则 268 条库会生成 O(n²) 条边。
2. **自环与重复边**：写入前按 `id` 去重，禁止自指。
3. **只对 `active` 建边**：`archived` / `superseded` / 过期的条目不应成为邻居，否则扩散激活会把已失效的结论重新拉回。
4. **命中回写只写 `active`**：`must_not` 挡掉的条目不能因「被算过分」而升温。

**回滚**：`α=0` 且不写 `related` 即回到阶段 4 的行为；`activation` 作为纯新增字段，旧代码读不到也不受影响。

#### 5.1 实现结果（2026-10-30）

| 项 | 结果 |
|---|---|
| mapping | `personal_memory_xqh` 与 `team_knowledge` 两处 `PUT _mapping` 成功（`related: object/enabled:false`、`activation: float`） |
| 既有文档 | 279 条，读回时两个字段缺失——**不回填**，代码按 `related=[]` / `activation=0` 处理 |
| typecheck | 通过 |
| 单测 | 264 pass / 0 fail / 7 skipped |
| 评测 | 30 条**逐条名次与基线完全一致**（gate=off） |

**踩到的坑**：`embedding.url` 指向 `127.0.0.1:11434`，本机 ollama 没在跑时 30 条会全部走降级（只走 BM25），paraphrase 的 hit@1 从 88% 掉到 50%。**那不是回归，是环境问题**——看到"⚠️ 走了降级"就先起 ollama 再跑，别拿降级数字和基线比。

## 阶段 6 · 情绪维度（设计说明）

**为什么状态独立成索引**：一次心情是一个**短期**状态（半衰期按小时计），而记忆是长期事实。把状态写进 `personal_memory_<uid>` 会让它出现在检索结果里，且每次情绪变化都会污染记忆库的统计口径。

**为什么 `β` 默认 0**：情绪一致召回（mood-congruent recall）有一个已知反效果——**放大偏差**。心情差时更容易想起负面记忆，形成自我强化的回路。所以：

- 默认关，先只看不排序；
- 开启后 `β` 上限建议不超过 `0.15`，且**只做正向提权，不做负向压制**；
- 每次开 β 都要跑一遍评测，确认 `noise` 类误报率没有上升。

**为什么情绪不能由模型自述驱动**：模型会为了迎合用户而永远"开心"。状态只能由事件改（工具失败/超时、用户明确夸奖或批评），模型自述一律丢弃并记审计。

**回滚**：`valence` 为空即不参与排序；关掉状态索引读取即回到阶段 5 行为。

## 阶段 7 · 自我迭代（设计说明）

**为什么必须人在环**：人格级改写是唯一不可逆的改动。LLM 自我改写有三类已知失败：漂移（逐渐偏离初始设定）、迎合（向用户偏好坍缩）、崩塌（规则互相冲突后失去一致口吻）。所以提炼产物一律先进 pending 队列，**不直接进检索**。

**为什么复用现有审核台**：S9 的 `review.ts` 已经有 pending 闸、审计、`superseded_by` 链。造第二套审批流程会产生两份互相不知道的状态——这正是本仓库反复避免的那种漂移。

**锚点保护**：`identity` 条目里挑出一组标 `anchor: true`（名字、称呼、底线、语言偏好这类不该被"优化"的东西）。提炼任务命中锚点时拒绝写候选，并记一条审计说明为什么拒。

**与 `memory_promote` 的分工**：`promote` 是「这条个人记忆值得进团队库」；自我迭代是「这条候选 traits 值得成为我的自述」。两者共用队列机制，但审核口径与目标索引不同，不要合并成一个动作。

**回滚**：identity 走 `superseded_by` 链，回滚 = 把旧版本 `restore` 回 `active` 并清链（与 4.4 的实现一致）。

## 不做清单（增补）

除 [原清单](#不做清单复述避免跑偏) 外，阶段 5~7 追加四条：

1. **不上图数据库**：`related` 用 ES 的 `nested` 或 `keyword` 数组就够，几万条以内不需要 Neo4j。附录已论证分图方案的四条硬限制。
2. **不做自动替代（auto-supersede）**：阶段 3.2 已实测否决，自我迭代同样不例外。
3. **不做情绪驱动的负向压制**：只提权，不降权，避免自我强化回路。
4. **不让人格文本进记忆库**：人格归上层插件，记忆库只存"发生过什么"。两份真相是这类系统最常见的坏味道。
